# 资源异步上传实现方案

> 状态：方案设计（未实施）
> 日期：2026-08-16

## 1. 背景与动机

当前引擎所有资源上传都是**同步阻塞**的：

- `Texture::LoadFromFile` / `LoadFromMemory` / `LoadCubeMapFromFile` → 内部 `UploadPixels` / KTX 逐层上传
- `Mesh::LoadFromFile` → 内部 `UploadBuffer`（顶点/索引）
- `EnvironmentMap::LoadFromFiles` → 一次同步加载天空盒 + 预滤波 + BRDF LUT 三张图

这些函数内部都走 `VulkanDevice::m_CommandPool`（内建池）取一个临时 command buffer，录完 copy/blit 命令后
调用 `FlushCommandBuffer`，用 fence **阻塞等待** GPU 执行完成才返回。

后果：**主线程在加载大资源（尤其 IBL 环境图 KTX cubemap、大纹理）时会整个卡住**，期间渲染线程无法推进，
出现明显的加载卡顿/lag spike。

### 目标

- 把**文件解析/像素解码（stb_image / KTX / tinyobj）+ GPU 上传**都移到后台专职线程，主线程不再阻塞。
- `Load()` 立即返回资源对象；渲染时未就绪则跳过（Mesh）或回退默认纹理（Texture），后台完成后下帧自动可见。
- 不改动同步上传的既有正确逻辑，新增一条异步路径，可逐步迁移。

## 2. 已拍板的设计方向

| 维度 | 决策 |
|---|---|
| 异步粒度 | **解码 + GPU 上传全异步**，都丢后台线程 |
| 执行模型 | **独立专职上传线程**（非每帧 tick 驱动提交） |
| 未就绪策略 | **跳过 + 就绪后自动亮相** |
| 资源状态 | Texture / Mesh 增加原子 `m_Ready` + `IsReady()` |

## 3. 现状分析（关键事实）

- **无现成线程池**：全库仅 `VulkanResourceCache` 与 `PhysicsWorld` 使用 `std::mutex`，需自建上传基础设施。
- **`VulkanResourceCache` 已线程安全**：每个资源类别有独立互斥锁（`VulkanResourceCache.h`），后台线程创建
  sampler 安全。
- **staging buffer 生命周期**：同步时是局部 `unique_ptr<VulkanBuffer>`，靠 fence 等待保活后析构；异步必须
  把生命周期托管到 pending 列表，fence 完成才释放。
- **调用方契约**：`TextureManager::Load` / `MeshManager::Load` 返回**立即就绪**的指针，渲染时
  `Renderer3D` 直接 `GetImageView()` / `GetVertexBuffer()` 绑定。异步化必须引入就绪门控。
- **着色器 / 管线**由 `VulkanResourceCache` 全局缓存管理，与资源上传无耦合，不受影响。

## 4. 核心架构决策（线程安全的关键）

**后台线程只做"解码 + GPU 上传"，且只产出局部对象（local `VulkanImage` / `VulkanBuffer` / staging buffer），
通过 pending 列表把所有权交给主线程；后台线程绝不直接写 `Texture` / `Mesh` 的任何成员。**

所有成员写入都在主线程 `Poll()` 中完成。跨线程仅用一个 `std::atomic<bool> m_Ready` 门控。

```
主线程                          后台上传线程
  Load() ──► 创建空壳资源 ──► 提交任务 ──► 解码(CPU) + staging + 录命令 + 提交 + fence 等待
  IsReady()? ◄── false               │            │
  渲染跳过/占位                        └──► pending 列表（托管 staging + local image/buffer）
  每帧 Poll() ──► fence 完成 → 释放 staging → 创建 view/sampler → 安装成员 → m_Ready=true
```

## 5. 关键取舍（诚实说明）

- **Texture 全异步**（解码 + 上传）：直接覆盖用户痛点（环境图 / 大纹理解码卡顿）。
- **Mesh 仅 GPU 缓冲上传异步**：`MeshManager::Load`（`MeshManager.cpp:108-178`）在返回前同步读取
  `GetSubMeshes()` / `GetMaterialData()` 构建材质。若 tinyobj 解码也异步，材质构建必须整体迁移到
  就绪回调里，改动面与风险显著增大。**推荐保住既有材质逻辑，Mesh 解码保持同步**（OBJ 解码通常比大纹理
  解码快得多，不是卡顿主因）。

## 6. 新组件：`AsyncUploadManager`

位置：`GE/include/GE/Render/AsyncUploadManager.h` + `GE/src/Render/AsyncUploadManager.cpp`

职责：
- 持有**专职上传线程**（`std::thread`）。
- **环形 in-flight = 3**：每槽一个 `VulkanCommandPool` + 一个持久 fence（复用，避免每次 create/destroy）。
- 任务队列 `std::deque<Task>`；槽满时后台线程在 `m_slotCv` 上阻塞（自然背压）。
- 主线程 `Poll()`：`timeout=0` 检查各槽 fence，回收完成槽、执行 finalize，**从不阻塞**。

接口（与实现一致，见 `AsyncUploadManager.h`）：

```cpp
struct UploadTask {
    std::function<void()> decode;                       // 后台：文件解析/像素解码
    std::function<void(VulkanCommandBuffer&)> upload;   // 后台：录 copy/blit 命令
    std::function<void()> finalize;                     // 主线程 Poll：创建 view/sampler、安装成员、置 ready
    std::unique_ptr<VulkanBuffer> staging;              // 生命周期随 pending 托管，fence 完成才释放
};

class AsyncUploadManager {
public:
    explicit AsyncUploadManager(VulkanDevice &device);   // 启动后台线程
    ~AsyncUploadManager();                               // Shutdown() + join 线程
    void Submit(UploadTask task);                        // 后台线程执行 decode + upload
    void Poll();                                         // 主线程：回收完成槽，执行 finalize（非阻塞）
    void Shutdown();                                     // 排空队列、等待全部完成、join
    size_t GetInFlightCount() const;                     // 在飞上传数（调试）
private:
    enum class SlotState : uint8_t { Idle, Acquired, Submitted, Reclaiming };
    struct Slot { std::unique_ptr<VulkanCommandPool> pool; vk::Fence fence; UploadTask task; SlotState state; };
    void WorkerLoop();  void ReclaimSlot(Slot&, bool block);
    VulkanDevice &m_Device;  vk::Queue m_GraphicsQueue;
    std::thread m_Thread;  std::atomic<bool> m_RequestExit;
    std::mutex m_Mutex;  std::condition_variable m_CV, m_slotCv;
    std::deque<UploadTask> m_Queue;  std::array<Slot, 3> m_Slots;
    static constexpr size_t kMaxInFlight = 3;
};
```

## 7. 并发风险与对策

| 风险 | 对策 |
|---|---|
| 后台线程与主线程向同一图形队列并发提交 | **无需外部锁**：Vulkan 规范保证 `vkQueueSubmit` 对同一队列线程安全。异步上传不串行化提交，只保证数据就绪后再被渲染引用 |
| staging buffer 生命周期 | 随 pending 条目托管，fence 完成才 `reset()` |
| unload 时上传进行中 | 任务**值捕获 CPU 数据**（不持资源裸指针）→ 后台无 use-after-free；pending 持有 GPU 对象所有权 → 无 GPU 泄漏；finalize 用 `map.contains(key)` 门控 → 已卸载则跳过安装 |
| view/sampler 创建时机 | 主线程 Poll 创建（不依赖数据内容，且让成员写入全在主线程，避免跨线程写成员） |

## 8. 渲染消费改造

- **Mesh 未就绪** → `DrawSubMeshImpl` 入口跳过整批（天然规避空索引缓冲）。
- **Texture 未就绪** → 不跳批量，`GetEffective*Texture` 回退到默认纹理（网格始终可见，就绪后继帧换真图）。
- **环境图** → `Renderer3D::SetEnvironment` 改为异步加载，加载完成前 `m_EnvironmentMap` 为空（天空盒/IBL 不显示），
  就绪后自动切换。

## 10. 分步实现顺序

1. 新建 `AsyncUploadManager` 骨架（专职线程 + 环形池 + `Submit`/`Poll`/`Shutdown`）——**已实施**。
2. `Texture` 异步化（空壳构造 → 后台解码上传 → `Poll` 安装）。
3. `Mesh` 上传异步化。
4. `Mesh` 上传异步化。
5. `EnvironmentMap` 异步化 + `Renderer3D::SetEnvironment` 改造。
6. `Renderer3D` 渲染门控 + 纹理降级。
7. `Renderer::BeginFrame` 挂 `Poll`、`AssetManager` 转发。

## 11. 验证方式

- 运行编辑器，加载大环境图（IBL），确认主线程不再长时间卡顿（帧率 / `Profiler` 观察）。
- 加载后资源自动可见；未就绪期间 Mesh 跳过、Texture 显示默认纹理。
- 连续快速 unload / reload 同一资源，验证无崩溃、无 use-after-free、无 GPU 泄漏。
- 开启验证层，确认无 `vkQueueSubmit` 并发相关报错。
