> 状态：**计划中（未开工）**

## 0. 一句话架构

```
 server 进程（权威）                                  client 进程
════════════════════════════════                     ════════════════════════════
 Scene(Playing) + PhysicsWorld(60Hz)                 Scene(Playing)
        │                     ▲                            │              ▲
        │ 采集实体状态         │ 应用远端输入               │ 应用快照      │ 采样本地输入
        ▼                     │                            ▼              │
    NetWorld ──── 快照/事件(可靠+不可靠) ────► ◄──── 输入/事件 ──── NetWorld
   (每 Scene 一份)                                          (每 Scene 一份)
        │                     ▲                            │              ▲
        ▼                     │                            ▼              │
    NetContext ──────────────────────────────────── NetContext   ← Application 持有，全局一份
   (唯一碰 GNS 时序的层)                              (唯一碰 GNS 时序的层)
        │                                                              │
        ▼                                                              ▼
   GameNetworkingSockets  ══════════ UDP 单端口 ══════════  GameNetworkingSockets
```

- **NetContext（全局，Application 持有）**：封装 GameNetworkingSockets（GNS），负责库初始化、监听套接字、连接表、轮询收包与发送、连接事件。是**唯一**接触 GNS 类型与时序的层，头文件用前向声明 + `NetSocket` 接口隔离后端（决策 §5）。
- **NetSocket（接口）**：把「可靠/不可靠发送、收包、连接事件」抽象成纯虚接口，GNS 只是其中一个实现。目的是让上层（NetWorld 及以上）在传输后端失控时可整体换到 ENet，而**不改一行业务代码**。
- **NetWorld（每 Scene 一个实例）**：把 ECS 组件翻译成网络消息，并反向把收到的消息写回 ECS。平行 `PhysicsWorld` / `AudioWorld`，同样「纯数据组件 + 延迟命令队列 + 运行时映射表」。**所有网络标识一律用 `NetId`（会话级 uint32）或 `UUID`（资产级），绝不发送 `entt::entity` 整数**。
- **BitStream / NetProtocol**：手写位/字节流与协议表。协议是**唯一真相**，服务端与客户端共用同一份头文件，避免双端字段错位。
- **权威在服务器**：服务器跑真实 `PhysicsWorld`（60Hz 不变），以固定 tickRate 广播快照；客户端对网络实体**不步进物理**，只按快照插值渲染 + 上报输入。

**唯一的结构性缺口**是两处，必须在 P0 补：
1. `SceneSerializer` 只有整场景粒度，**没有实体级序列化 API** —— 而网络 spawn 必须能「把某一个实体的全部组件打成一个包发出去」；
2. `PhysicsWorld` 没有设置刚体目标位姿的公开 API —— 而远端实体必须被 Kinematic 驱动到服务器位置。

## 2. 技术选型

### 2.1 传输层：GameNetworkingSockets

| 候选 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **GameNetworkingSockets**（Valve） | 生产级（Steam 网络同源）：可靠+不可靠双通道、分片、连接生命周期、LAN/P2P/公网**同一套代码路径**、连接质量统计（ping/丢包/抖动）开箱即用、BSD-3 许可 | 依赖链重：protobuf + abseil（+ 可选 libsodium/WebRTC），首次构建时间长，CMake 选项多 | ✅ **已选定** |
| ENet | 极轻量，源码树小，可靠 UDP 成熟 | 无连接质量统计、无 NAT 穿透、无加密，可靠性语义比 GNS 粗 | 备选（§5 已留切换点） |
| 自研 UDP + 可靠性层 | 零依赖、完全可控、无黑盒 | 需自己实现 ACK/重传/分片/拥塞/心跳，**极易踩坑且难验证**，与「先把联机跑通」的目标冲突 | 不选 |
| TCP + 自定义协议 | 实现最简单 | 队头阻塞使实时位置同步体验差（一次丢包卡住后续所有快照） | 不选 |

**选型理由**
1. 需求是**实时位置同步**，必须有「不可靠但低延迟」的通道，TCP 直接出局；
2. 引擎是 Windows x64 / MSVC 单平台（`README.md:7,113`），GNS 原生支持且无跨平台顾虑；
3. 首版目标是**局域网**，但 GNS 让「局域网 → 公网专服 → NAT 穿透」成为纯配置推进，而不是推倒重来——这是相对 ENet 的决定性优势；
4. 连接质量统计（`GetQuickConnectionStatus`）直接喂给编辑器网络面板，省掉一整套自研统计。

**集成代价（必须正视）**：GNS 需要 protobuf 与 abseil（P2P 与加密还需 WebRTC/libsodium）。这些会显著拉长首次与增量构建。对策：
- 用 **`GE_ENABLE_NET` 编译开关门控**整个网络子系统（默认 OFF），让日常渲染/编辑器迭代的构建路径完全不受影响；
- 关闭无关特性（加密、P2P/WebRTC）时依赖链大幅收窄，**局域网探路阶段就用这个最小配置**；
- 精确的 CMake 选项名与依赖清单**以集成时的 GNS 版本为准**（见附录 A，本文档无法联网核对）。
- ⚠️ MSVC 运行时必须一致：根 `CMakeLists.txt:8` 在**所有** `add_subdirectory` 之前设 `CMAKE_MSVC_RUNTIME_LIBRARY "MultiThreaded...DLL"`（即 `/MD`），GNS/protobuf/abseil 会自动继承——这是集成能成立的前提，若出现 `RuntimeLibrary` 不匹配链接错误，先查此处。
- protobuf 生成的大 TU 可能需要 `/bigobj`；GNS 是独立 target，不受 GE 的 PCH（`:193`）影响，此点已有先例：`ge_lua` 单独成目标以隔离编译选项（`CMakeLists.txt:129-141`）。

### 2.2 同步模型：权威服务器 + 状态同步

| 维度 | 结论 |
|---|---|
| 权威方 | **服务器**。服务器跑完整的 `PhysicsWorld`（60Hz 固定步长不变，`FIXED_TIMESTEP = 1/60`，`MAX_SUBSTEPS = 5`），是位置/状态唯一真相 |
| 快照频率 | 建议 **20Hz**（可配），与渲染帧率**解耦**；服务器自带累加器驱动 tick |
| 客户端对网络实体 | **不步进物理**，按快照插值渲染；本地输入只上报，不本地应用 |
| 插值 | 客户端缓冲快照，渲染滞后一个插值延迟（默认 2×快照间隔 = 100ms） |
| 客户端预测 | **P0 明确不做**。代价：局域网手感约等于 RTT（通常 <5ms，可接受）。阶段 B 补预测 + 服务器和解 |
| 为什么不做帧同步 | Jolt 使用多线程 `JobSystemThreadPool`（`PhysicsWorld.cpp:294`），浮点与并行归约**不保证跨机确定性**。要做帧同步必须去并行 + 定点数大改物理，与现状冲突。权威服务器模型不需要确定性 |

### 2.3 序列化：手写 BitStream，不引 protobuf schema

- GNS 内部用 protobuf，但**游戏消息不引入 `.proto`**：那会让每次改协议都触发 codegen，且新增构建环节。
- 引擎已有手写二进制格式的先例（`.gemesh` 的 magic/版本/chunk 表 + 字符串池，`GE/include/GE/Render/GEMeshLoader.h`；`.geanim` 同构），网络消息沿用同一风格：`GE/include/GE/Net/BitStream.h`。
- **与 YAML 的分工要写清楚**：`.scene` YAML 管**资产级、低频、编辑期**持久化；BitStream 管**会话级、高频、瞬时**同步。二者不互相替代，`NetworkIdentity` 组件的作者配置仍走 YAML（§3.6）。
- 浮点量化从一开始就做进 BitStream 接口（`WriteVector3Quantized` / `WriteQuatSmallestThree`），否则后期加压缩要改全部消息——这是先立接口、再实现压缩的低成本做法。

### 2.4 线程模型：P0 主线程 pump，阶段 B 迁专用线程

| 阶段 | 方案 | 理由 |
|---|---|---|
| **P0** | `Application::Run()` 每帧调 `NetContext::Poll()`（`RunCallbacks` + `ReceiveMessagesOnPollGroup`），**全程主线程、无锁** | 无锁即无竞态，可断点单步，局域网延迟本来就低；先把功能跑通 |
| **阶段 B** | 照 `AsyncUploadManager.h:147-155` 模板建专用网络线程（`std::thread` + `atomic<bool>` 退出 + `mutex` + `condition_variable` + `deque`），主线程只 drain 收包队列 | 解除「帧率 ↔ 收包」耦合：掉帧不再累积延迟；高帧率下 RTT 取样更准；专服可独立 tick |

P0 主线程方案的**已知代价**（接受）：最小收发延迟受帧时间限制；一次长卡顿（如着色器编译）会堆积待处理包。阶段 B 解决。

### 3.2 全局 NetContext（Application 持有）

```cpp
// NetTypes.h（轻量，不引 GNS）
namespace GE::Net {
/// 会话内实体标识（服务器分配，单调递增）。0 = 无效。
using NetId    = uint32_t;
/// 会话内玩家/连接标识（服务器 accept 时分配）。0 = 服务器自身。
using PeerId   = uint32_t;
/// 服务器 tick 序号（1 起，单调递增）。
using Tick     = uint32_t;

inline constexpr NetId  kInvalidNetId  = 0;
inline constexpr PeerId kServerPeer    = 0;

/// 通道语义 → 映射到后端发送标志
enum class Channel : uint8_t {
    Reliable,            ///< 必达有序：spawn/despawn/RPC/握手
    Unreliable,          ///< 不可靠：快照/输入（允许丢、允许乱序，新的覆盖旧的）
    UnreliableNoDelay,   ///< 不可靠 + 不 Nagle：对延迟最敏感的小包
};

enum class SessionRole : uint8_t { None, Server, Client };
enum class SessionState : uint8_t {
    Idle, Listening, Connecting, Connected, Disconnected, Failed
};

/// 连接层事件（NetContext → 上层，主线程队列投递）
struct ConnectionEvent {
    enum class Type : uint8_t { Connected, Disconnected, ProblemDetected } type;
    PeerId    Peer = kServerPeer;
    int       EndReason = 0;      ///< 后端断开码，仅日志/UI 用
    std::string DebugText;        ///< 后端给出的人类可读原因
```

### 3.3 协议定义

```cpp
// NetProtocol.h —— 双端共用，协议唯一真相
namespace GE::Net::Protocol {
inline constexpr uint16_t kProtocolVersion = 1;
inline constexpr uint32_t kMaxPayloadBytes = 1200;   ///< 单消息上限，避免 IP 分片

/// 消息类型。头部布局：u8 type [+ 各消息自有载荷]
enum class MsgType : uint8_t {
    // —— 握手（可靠）——
    Connect        = 0x01,   // C→S: u16 version, str clientName
    ConnectAccept  = 0x02,   // S→C: u32 peerId, u8 tickRate, u32 serverTick, u64 worldSeed, u32 netIdHint
    ConnectReject  = 0x03,   // S→C: u8 reason
    // —— 生命周期（可靠）——
    Spawn          = 0x10,   // S→C: u32 netId, u32 ownerPeer, u8 authority, u16 blobLen, [entityBlob]
    Despawn        = 0x11,   // S→C: u32 netId, u8 reason
    OwnershipChange= 0x12,   // S→C: u32 netId, u32 newOwnerPeer
    // —— 高频状态 ——
    Snapshot       = 0x20,   // S→C 不可靠: u32 serverTick, u16 count, [record...]
    InputCommand   = 0x21,   // C→S 不可靠: u32 clientTick, u32 buttons, i16 moveX, i16 moveZ, i16 yaw, i16 pitch
    // —— 事件 ——
    Rpc            = 0x30,   // 双向 可靠:   u32 targetNetId(0=全局), u32 nameHash, [args...]
    RpcUnreliable  = 0x31,   // 双向 不可靠: 同上
    // —— 保活/统计 ——
    Ping           = 0x40,   // 双向 不可靠: u32 senderTimeMs
    Pong           = 0x41,   // 双向 不可靠: u32 senderTimeMs, u32 serverTick
    // —— 断开 ——
    Disconnect     = 0x7F,   // 双向 可靠:   u8 reason
};

/// 快照单实体记录：u32 netId, u8 fieldMask, [按掩码依次出现的字段]
enum SnapshotField : uint8_t {
    kFieldPosition = 1u << 0,   // 6B：3 × i16，量化（每单位 1/64 米，±512m 量程）
    kFieldRotation = 1u << 1,   // 4B：四元数 smallest-three（3 × 11bit + 2bit 索引）
    kFieldScale    = 1u << 2,   // 6B：可选，静态实体不写
    kFieldFlags    = 1u << 3,   // 1B：业务位（着地/动画状态/开火等）
};

/// 断开原因（Disconnect / ConnectReject 共用）
enum class DisconnectReason : uint8_t {
    Normal = 0, ServerShutdown, ProtocolMismatch, ServerFull, Kicked, Timeout,
};
}
```

握手时序（P0）：

```
client                                          server
  │  Connect{ver, name}            ──可靠──►      │  校验版本 → 分配 PeerId
  │                                                │
  │  ◄──可靠──  ConnectAccept{peerId, tickRate,    │
  │             serverTick, seed, netIdHint}       │
  │                                                │
  │  ◄──可靠──  Spawn × N（全部已复制实体的基线）    │  基线：全量实体
  │                                                │
  │  ──不可靠─► InputCommand{clientTick, ...}       │  ┐
  │  ◄─不可靠── Snapshot{serverTick, records...}    │  │ 稳态循环
  │  ◄──可靠──  Spawn/Despawn/Rpc（按需）           │  ┘
```

**P0 快照为全量（不做增量 delta）**：字段掩码 + 量化已能压到 ~15B/实体，局域网带宽绰绰有余（附录 C），而全量快照让丢失恢复、late-join、调试都简单得多。增量基线与确认机制放到阶段 D。

### 3.5 ECS 组件（Scene/NetComponents.h）

沿用音频的纪律：**组件存作者配置，运行时状态放 NetWorld 内部映射**（`AudioWorld.h` 的注释明确写了这条）。但变换插值有一个例外——它与 `TransformComponent` 的物理插值字段（`Components.h:63-65`）是同类运行时缓存，**放在组件里更好**，因为 `UpdateWorldTransforms` 的 DFS 只认组件字段。

**为什么 Transform 同步不直接复用 `TransformComponent`**：`TransformComponent` 已有物理插值字段（`m_PhysicsPosition`/`m_PreviousPhysicsPosition`），语义是「本机物理插值」。网络插值是**另一条来源**（远端快照），两个来源的插值缓冲必须分开，否则远端实体在服务器上跑物理时两边字段会互相踩。用独立组件 = 来源隔离 + 可单独开关同步轴。

| 标识 | 类型 | 生命周期 | 用途 |
|---|---|---|---|
| `IDComponent::UUID`(`Components.h:134`) | 32 字符 hex 字符串 | **跨会话持久**（随 .scene 落盘） | 父实体引用、皮肤/动画目标、存档、预制体身份 |

| `entt::entity` | uint32（带版本位） | 进程内，销毁后可复用 | **绝不联网传输**——句柄会被回收，收到远端句柄等于收到随机实体 |

### 3.6 实体级序列化重构（spawn 载荷）

**问题**：`SceneSerializer` 只有整场景 `Serialize(filepath)` / `Deserialize(filepath)`，实体块写在 `SceneSerializer.cpp:715-760+` 的循环体内部，无法单独取用。而 spawn 必须「把某一个实体的全部组件打成字节串发给客户端，客户端按同一套规则重建实体」。

**方案：把实体块抽成可复用的实体级 API（P0 必做，属重构非新功能）**

```cpp
// SceneSerializer.h 新增（与现有整场景 API 并存，整场景路径改为调用它们以保证单一实现）
class SceneSerializer {
public:
    // —— 新增：实体级（网络 spawn 载荷 / 未来预制体共用）——
    /// 序列化单个实体（含其组件块，不含子实体递归）。append 到给定 emitter。
    static void SerializeEntity(YAML::Emitter &out, Entity entity);

    /// 由实体块文本重建实体到目标场景。parentUuid/netId 等跨实体引用由调用方补齐。
    static Entity DeserializeEntity(Scene *scene, const YAML::Node &entityNode);
};
```

- 内部把现有循环体里的「Tag/Id/Parent/Transform/…」逐块代码**原样搬进** `SerializeEntity`，整场景路径改为循环调用它——**一次搬移，两处受益**，不存在两份会漂移的实现。
- 网络层用法：服务器 `RequestSpawn` → `YAML::Emitter` → `SerializeEntity` → 文本字节串 → `Spawn` 消息。客户端收到 → `YAML::Node` 解析 → `DeserializeEntity` → 补 `NetId`/`OwnerPeer` → `NetworkIdentityComponent`。
- **P0 的懒办法与代价**：YAML 文本当载荷，体积大（一个普通实体约 0.5–2 KB），但 spawn 是低频可靠消息，局域网完全无压力，且**复用零成本、调试可读**（能直接打印出来看）。阶段 C 再换成 BitStream 紧凑格式（需要为每类组件写字段级读写，工作量大），届时 `PrefabId` + 预制体资产化一并做。
- 依赖顺序：`Spawn` 后的**父子关系**与**组件间跨实体引用**（动画 clip 目标、皮肤关节）需要二次补齐。P0 简化：**网络复制只支持平铺实体（无父链、无跨实体引用）的全量载荷**，复杂层级放阶段 C。这个限制必须写进文档与编辑器提示，否则会踩坑。

### 3.7 快照与插值

```
服务器时间轴（tickRate = 20Hz，间隔 50ms）
  T0      T1      T2      T3
  ●───────●───────●───────●      Snapshot(T1) 内容 = T1 时刻状态
                          ↑
                    客户端收到 T1、T2 后

客户端渲染时间轴（插值延迟 = 2 × 50ms = 100ms，即"过去 100ms"处取状态）
  t_now - 100ms 位于 [T1, T2] 之间 → alpha = (t - T1)/(T2 - T1)
  pos = lerp(T1.pos, T2.pos, alpha)，rot = slerp(T1.rot, T2.rot, alpha)
```

- 插值延迟取 **2 × 快照间隔**：容忍一次快照丢失而不出现「插值穿越」（快照缓冲见底时钳制 alpha = 1，宁可停顿也不外插）。
- 谁写 `TransformComponent`：客户端 `UpdateApply` 里 `InterpolateNetworkTransforms` 把插值结果写进远端实体的 `Translation`/`Rotation`，随后 `UpdateWorldTransforms`（`Scene.cpp:841`）自然算出世界矩阵——**不需要动 DFS，也不需要动渲染**。这是插值放在 `UpdateApply` 而不是渲染阶段的唯一理由。
- 本地玩家实体在客户端也走同一条路（收到服务器下发的自身位置 → 插值显示）。P0 无预测，所以自己的角色有约 RTT 的响应延迟——局域网可接受，**这就是不预测的可见代价**，阶段 B 用预测+和解消除。
- 服务器侧的累加器独立于 `PhysicsWorld` 的 60Hz 累加器（后者在 `PhysicsWorld.h:292`），网络 tick（20Hz）只决定**发送频率**，不改变物理步长。

### 3.8 远端实体的物理表示

三种选择，P0 采用第 2 种：

| 方案 | 做法 | 评价 |
|---|---|---|
| 1. 远端实体无刚体 | 只写 `TransformComponent` 插值 | **不可取**：本地玩家会穿过远端玩家（本地物理世界不知道其存在） |
| 2. **远端实体加 Kinematic 刚体，服务器位置驱动**（P0） | 远端实体带 `RigidBodyComponent`（`Type = Kinematic`），每帧 `MoveKinematic` 到插值位置 | ✅ 本地物理仍能与之碰撞；需要 `PhysicsWorld` 新增一个 API（下） |
| 3. 远端实体也跑物理 + 网络和解 | 本地模拟远端实体再用服务器状态纠偏 | 阶段 B/C 的事，P0 过重 |

**需要的小改动**：`PhysicsWorld` 目前有 `RequestCreateRigidBody`(`PhysicsWorld.h:123`) / `DestroyRigidBody`(`:129`)，但**没有**设置刚体目标位姿的公开 API。新增：


## 4. 阶段计划

| 阶段 | 内容 | 依赖 | 优先级 |
|---|---|---|---|
| **A** | 传输层打通：GNS 集成进构建、`NetSocket`/`NetContext`、单机回环（localhost 两进程握手 + Ping/Pong） | 无 | P0 |
| **B** | 复制与同步：实体级序列化重构、`NetworkIdentity/Transform/Input` 组件、`NetWorld` spawn/despawn/快照/插值、远端 Kinematic 驱动、Scene 生命周期 | A | P0 |

### 4.1 阶段 A：传输层打通（详细）

1. Vendored GNS 源码树到 `GE/third_party/GameNetworkingSockets/`，含其依赖子模块（protobuf / abseil，按需 libsodium/WebRTC）。**版本锁定并记录**（GNS 无稳定 ABI，跟 tag 而非 master）。
2. CMake：`GE_ENABLE_NET` 开关（默认 OFF）→ `add_subdirectory` → 链接 → 加 `GE/src/Net/*.cpp` glob。用**最小配置**先跑通：关掉加密与 P2P/WebRTC（选项名核对附录 A）。
3. `NetTypes.h` / `NetSocket.h` / `NetContext.h` 定义接口；`GE_ENABLE_NET=0` 时提供空实现（上层无需 `#ifdef`）。
4. `NetSocketGNS.cpp`——**全工程唯一** include GNS 头的文件：`GameNetworkingSockets_Init` / `…_Kill`、`CreateListenSocketIP`、`ConnectByIPAddress`、`AcceptConnection`、`CreatePollGroup` + `SetConnectionPollGroup`、`ReceiveMessagesOnPollGroup`、`SendMessageToConnection`、连接状态回调、`GetQuickConnectionStatus`。
5. `NetContext`：连接表（`PeerId` ↔ 后端连接句柄，含 `k_ESteamNetworkingConfig_ConnectionUserData` 承载 PeerId）、事件队列、`PollFrame`。
6. `Application` 接入：`m_NetContext` 创建/销毁 + `Run()` 每帧 `PollFrame()`。
7. **验证（阶段 A 的唯一验收物）**：写一个临时调试入口（编辑器菜单或命令行参数），在一个进程 Host 另一个进程 Join，双方各按固定频率发 `Ping`/`Pong`，控制台打印 RTT 与丢包。**这一步跑通才继续 B。**

### 4.2 阶段 B：复制与同步（详细）

8. **验证**：Host 一个含若干复制的场景，客户端 Join → 远端实体出现在正确位置并平滑移动；服务器移动实体客户端跟随；服务器销毁实体客户端消失；断开后客户端清空远端实体；自己退出无崩溃/无泄漏。

## 5. 风险与决策记录

| 决策 | 结论 | 理由 |
|---|---|---|
| 同步模型 | **权威服务器 + 状态同步** | 最通用且不需要物理确定性；与现有 `PhysicsWorld` 60Hz 权威模拟天然契合 |
| 客户端预测 | **P0 不做**，阶段 B 做 | 预测+和解是第一版最大的复杂度来源；局域网 RTT 低，不做也能用 |
| 传输后端 | **GameNetworkingSockets** | 生产级可靠/不可靠通道 + 连接统计 + 局域网→公网同一路径 |
| 后端隔离 | **`NetSocket` 纯虚接口**，GNS 只是实现之一 | GNS 的 protobuf/abseil 依赖链是最大集成风险，留出整体换 ENet 的退路，**换后端不改 NetWorld 及以上任何代码** |
| 构建门控 | `GE_ENABLE_NET` 默认 OFF，空实现保证上层零 `#ifdef` | 不能让日常渲染迭代被 protobuf 拖慢；条件编译不得扩散到 Scene/编辑器/脚本 |
| 网络标识 | **只用 `NetId`/`UUID`/`PeerId`**，绝不传 `entt::entity` | entt 句柄带版本位且会回收，传远端句柄 = 传随机实体 |
| 游戏消息序列化 | **手写 BitStream**，不引 `.proto` | 避免每次改协议触发 codegen；引擎已有 `.gemesh`/`.geanim` 手写格式先例 |
| YAML vs BitStream 分工 | YAML = 资产/低频/持久；BitStream = 会话/高频/瞬时 | 二者不互相替代，`NetworkIdentity` 作者配置仍走 YAML |
| 快照内容 | **P0 全量 + 字段掩码 + 量化**，不做增量 | 局域网带宽足够；全量让丢包恢复、late-join、调试都简单 |
| 插值延迟 | 默认 2 × 快照间隔（20Hz → 100ms） | 容忍丢一次快照；缓冲见底时钳制不外插 |
| 插值写入时机 | `UpdateApply` 写 `TransformComponent`（`StepPhysics` 前） | 复用 `UpdateWorldTransforms` 的 DFS，不动渲染与 DFS 一行 |
| 远端实体物理 | **Kinematic 刚体 + `MoveKinematic`**（需新增 `PhysicsWorld::SetKinematicTarget`） | 本地物理仍能与之碰撞，且不引入第二套模拟 |
| 网络线程 | **P0 主线程 pump**，阶段 B 迁专用线程（照 `AsyncUploadManager`） | 无锁无竞态、可断点；代价（帧率耦合）在局域网可接受 |
| NetContext 归属 | **Application**（不是 Scene 也不是 Renderer） | 会话是进程级；编辑器 Host 时进程即服务器；生命周期须早于 Scene |
| NetWorld 归属 | **Scene**（每场景一份，平行 PhysicsWorld/AudioWorld） | 与音频完全同构，复用已确立的子系统范式 |
| 编辑态同步 | **门控：仅 Playing 收发** | Host 时编辑器即服务器，编辑态同步会把编辑操作广播出去 |
| spawn 载荷 | P0 用 **YAML 实体块文本**（复用实体级序列化） | spawn 低频，体积可接受；复用零成本且可读易调试 |
| 复制范围 | P0 **只支持平铺实体**（无父链、无跨实体引用） | 层级与跨实体引用的二次补齐放阶段 C；先跑通再扩展 |
| 组件运行时状态 | `NetId`/`OwnerPeer`/插值缓冲**不序列化**；插值缓冲留在组件内 | 照音频纪律；但插值缓存与 `TransformComponent` 物理插值字段同构，留组件利于 DFS |
| 当前协议版本 | `kProtocolVersion = 1`，握手校验不一致即拒 | 协议会随阶段演进，双端错位必须早失败 |

### 主要风险

1. **GNS 构建集成（最高风险，可能推翻方案）**：protobuf + abseil（+ 可选 WebRTC/libsodium）会显著加重构建，且 MSVC/`/MD`/PCH 交互容易出问题。**对策**：① 阶段 A 就单独验证构建，不写业务；② `GE_ENABLE_NET` 默认 OFF 隔离日常构建；③ 关加密与 P2P 用最小配置；④ `NetSocket` 接口留 ENet 退路。**注意 `/MD` 一致性由根 `CMakeLists.txt:8` 在全部 `add_subdirectory` 之前设定，是集成成立的前提。**
2. **`SceneSerializer` 重构的回归风险**：把整场景循环体抽成实体级 API 时极易漏字段或改变写序，导致已有 .scene 读不出来。**对策**：重构后立刻用现有 `.scene`（如 `assets/scenes/3.scene`）做保存→加载往返自测，**在写任何网络代码之前完成并验证**。
3. **P0 无预测的手感**：自己的角色响应有约 RTT 延迟。局域网（<5ms）可接受；若首版就上公网会明显发飘。**这不是 bug，是明确的 P0 取舍**，需在文档与面板提示中说明。
4. **实体级序列化的边界**：平铺实体限制一旦被遗忘，带父链的实体 spawn 后会错位/丢引用。**对策**：`RequestSpawn` 检查父链与跨实体引用并**明确告警拒绝**，而非静默生成半个实体。
5. **主线程 pump 与帧率耦合**：长卡顿会堆积待处理包、最小 RTT 受帧时间限制。**对策**：`NetMessage` 携带后端到达时刻 `RecvTimeMs`，插值用后端时间戳而非帧时间；阶段 B 迁线程解决。
6. **不可信输入的解析安全**：客户端报的 `InputCommand`、RPC 参数、以及一切远端字节流都不可信。**对策**：`BitStream::Read*` 必须做长度校验并返回失败；服务器永不采信客户端上报的位置（只采信输入）；`kMaxPayloadBytes` 限长。
7. **多 Scene / 编辑器双态**：门控只做在 `IsPlaying()` 上，`Play→Stop→Play` 反复切换时 `NetWorld` 的映射表必须清干净，否则复用旧 `NetId` 指向已销毁实体（悬垂）。**对策**：`OnStop` 清空 `Impl` 全部映射与快照缓冲，`OnPlay` 重建。

## 7. 验收标准（每阶段自测）

- **A**：`GE_ENABLE_NET=ON` 可构建；`NetContext::Init` 成功；编辑器/命令行 Host + Join 两进程握手成功；`Ping/Pong` RTT 打印合理（局域网 <5ms）；对端异常退出能收到断开事件；进程退出无泄漏（`GameNetworkingSockets_Kill` 正确调用）；`GE_ENABLE_NET=OFF` 时全量构建与现有行为**完全不变**。
- **B**：含复制实体的场景 Host 后客户端 Join → 远端实体出现在正确位置并**平滑**移动（无抖动/无穿越）；服务器移动实体客户端跟随；服务器销毁实体客户端消失；客户端玩家输入能驱动服务器上的角色移动；远端实体的 Kinematic 刚体能被本地玩家正确碰撞；`Play→Stop→Play` 反复切换无悬垂/崩溃；保存/重载场景不丢网络组件；协议版本不匹配时拒绝连接并给出可读原因。
- **C**：NetworkPanel 可完成 Host/Join/Kick 全流程并显示 peer 与统计；三个组件可从 Add Component 添加、属性可编辑、随 .scene 保存重载；Lua 可用 `net.spawn/despawn/net_id/owner/send_rpc` 且 `OnNetRpc` 被正确派发；独立专服 exe 与编辑器客户端互通。
- **D**（若做）：预测下本地玩家响应无感知延迟且服务器和解无可见回弹；增量快照在丢包下能恢复；带宽随实体数可控；加密连接可用。

## 附录 B：P0 协议草案（完整消息表）

| Type | 名称 | 方向 | 通道 | 载荷字段 |
|---|---|---|---|---|
| `0x01` | Connect | C→S | Reliable | `u16 version`, `str clientName` |
| `0x02` | ConnectAccept | S→C | Reliable | `u32 peerId`, `u8 tickRate`, `u32 serverTick`, `u64 worldSeed`, `u32 netIdHint` |
| `0x03` | ConnectReject | S→C | Reliable | `u8 reason`(DisconnectReason) |
| `0x10` | Spawn | S→C | Reliable | `u32 netId`, `u32 ownerPeer`, `u8 authority`, `u16 blobLen`, `[entityBlob]`（YAML 实体块文本，P0） |
| `0x11` | Despawn | S→C | Reliable | `u32 netId`, `u8 reason` |
| `0x12` | OwnershipChange | S→C | Reliable | `u32 netId`, `u32 newOwnerPeer` |
| `0x20` | Snapshot | S→C | Unreliable | `u32 serverTick`, `u16 count`, `[u32 netId, u8 fieldMask, fields…] × count` |
| `0x21` | InputCommand | C→S | Unreliable | `u32 clientTick`, `u32 buttons`, `i16 moveX`, `i16 moveZ`, `i16 yaw`, `i16 pitch`（角度量化到 i16） |
| `0x30` | Rpc | 双向 | Reliable | `u32 targetNetId`(0=全局), `u32 nameHash`, `[args…]` |
| `0x31` | RpcUnreliable | 双向 | Unreliable | 同上 |
| `0x40` | Ping | 双向 | Unreliable | `u32 senderTimeMs` |
| `0x41` | Pong | 双向 | Unreliable | `u32 senderTimeMs`, `u32 serverTick` |
| `0x7F` | Disconnect | 双向 | Reliable | `u8 reason` |

**BitStream 原语约定**：多字节整数**小端**；`str` = `u16 len` + UTF-8 字节（**不含**结尾 `\0`）；`Vector3Quantized` = 3 × `i16`，缩放因子 64（量程 ±512m，精度 1.56cm）；`QuatSmallestThree` = 丢弃最大分量（2bit 索引）+ 其余三个各 11bit 有符号，共 35bit（对齐到 5 字节）。所有 `Read*` 在越界时返回失败，由调用方丢弃整条消息并记日志——**远端数据一律按不可信输入处理**。

## 附录 C：带宽估算（P0 配置，用于确认方案可行）

单实体快照记录（含位置+旋转，不含缩放）：

| 字段 | 字节 |
|---|---|
| `netId` | 4 |
| `fieldMask` | 1 |
| 位置（3 × i16 量化） | 6 |
| 旋转（smallest-three，5B 对齐） | 5 |
| **合计** | **16** |

场景：32 个复制实体、快照 20Hz、单客户端：

```
32 实体 × 16 B × 20 Hz ≈ 10.2 KB/s ≈ 82 kbps（单向，服务器→客户端）
```

加上 GNS 包头（每消息约数十字节，因整帧打包成**一条** `Snapshot` 消息而摊薄）、可靠通道状态与 `Ping`，实测预期 **12–20 KB/s**。三客户端局域网 ≈ **300–500 kbps** 上行——同一条千兆局域网余量充足。结论：**P0 全量快照在局域网完全可行，不需要增量压缩**。

（对照：位置精度 1.56cm、旋转精度约 0.1°，对同步显示绰绰有余。若阶段 D 上公网，再按需降频远实体 + 距离分级。）

## 附录 D：术语表

| 术语 | 含义 |
|---|---|
| **权威（Authority）** | 某实体状态的最终裁决方。P0 固定为服务器 |
| **PeerId** | 会话内玩家/连接标识；`0` 保留给服务器自身 |
| **NetId** | 会话内实体标识，服务器分配递增；**唯一允许在线上出现的实体引用**；`0` = 无效 |
| **UUID** | `IDComponent::UUID`，资产级持久标识（跨会话/存档/预制体），与 NetId 分工不重叠 |
| **OwnerPeer** | 实体的归属玩家；`0` = 服务器持有 |
| **Tick** | 服务器逻辑帧序号，驱动快照节奏；与 60Hz 物理步长解耦 |
| **Snapshot** | 一次 tick 的全部复制实体状态包（P0 全量） |
| **插值延迟** | 客户端渲染相对服务器时间的滞后量，默认 2 × 快照间隔 |
| **和解（Reconciliation）** | 阶段 B：客户端把服务器真实状态与自己预测状态对比并回滚重放 |
| **基线（Baseline）** | 阶段 D：双方确认的共同历史快照，增量快照据此做差 |
