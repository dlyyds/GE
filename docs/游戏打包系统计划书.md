## 0. 一句话架构

```
   编辑器内「构建」──┐
   或命令行直接调    ├──► gepack (CLI)
                    │      1. 读入口 .scene
                    │      2. 走依赖图 → 收集资产清单
                    │      3. 校验：绝对路径 / 缺失 / 未烘焙 / 越界引用
                    │      4. 拷贝到 <输出>/assets + 写 manifest.json
                    └──────────────────────┬───────────────────────
                                           ▼
                    <输出>/                          ← 整个文件夹拷走即可运行
                      ├─ GE_Runtime.exe             ← 阶段 B 新增的播放器
                      ├─ *.dll                      ← VC 运行时（/MD）
                      ├─ game.cfg                   ← 入口场景 / 窗口 / 图标
                      ├─ manifest.json              ← 资产清单 + 引擎版本 + 校验和
                      └─ assets/                    ← 只含被引用到的资产
```

**关键约束**：打包的正确性建立在**路径决定论**上——同一份发行版，放在任意目录、以任意工作目录启动，都必须解析到同样的资产。当前引擎两条都不满足（根按 CWD 解析 + 场景内嵌绝对路径），所以**阶段 A 是一切的前提，不能跳**。阶段 A 独立交付的价值也足够明显：把 `bin/` 和 `assets/` 一起拷到别处就能跑，不再要求"必须从仓库根启动"。

## 3. 阶段 A：资产根决定论 + 路径规范形

### 3.1 资产根：从"工作目录"改到"可执行文件目录"

`AssetManager` 已有 `SetAssetRoot()`（`AssetManager.cpp:38`）但从未被调用，根固定为 `"assets"`。而 `CMAKE_RUNTIME_OUTPUT_DIRECTORY = ${CMAKE_SOURCE_DIR}/bin`（`CMakeLists.txt:16-19`），`bin/` 下**没有** `assets/`，`build.bat` 也不拷贝 assets——所以现在**只有从仓库根启动才能跑**，从 `bin/` 启动全部资产路径失效。

改动：

1. 新增 `PlatformUtils::GetExecutableDirectory()`（放 `GE/include/GE/Platform/Windows/WindowsPlatformUtils.h`，实现走 `GetModuleFileNameW`；非 Windows 分支后续补）。
2. `Application` 构造函数内**在构造 `Renderer` 之前**完成根决策，并把结果**注入 `Renderer` 构造函数**：

```cpp
// 优先 exe 同级 assets（发行版布局）；不存在则回退 CWD/assets（开发期从仓库根启动）
std::filesystem::path root = PlatformUtils::GetExecutableDirectory() / "assets";
if (!std::filesystem::exists(root))
    root = std::filesystem::current_path() / "assets";   // 开发回退
m_Renderer = std::make_unique<Renderer>(*m_Window, root);   // 注入，而非构造后设置
```

> **为什么必须注入构造函数（实现时修正）**：本文初稿判断"构造后再 `SetAssetRoot` 即可，中间窗口期足够安全"，**该判断不成立**。`Renderer` 构造的最后一步会 `ImGuiLayer::OnAttach()`（`Renderer.cpp:64-65`），而它立刻用资源根解析字体（`ImGuiLayer.cpp:41-42` 取 `AssetPaths::Fonts + "/OpenSans-Regular.ttf"`）。构造函数返回时字体已加载完毕，此后设置资源根已太晚。故 `Renderer` 构造函数签名加一个 `assetRoot` 参数，在创建 `AssetManager` 之后、ImGui 初始化之前调用 `SetAssetRoot`。`Renderer` 全仓库只有 `Application.cpp` 一处实例化，改动收敛。

3. 同时修掉两处**绕过 `ResolvePath` 的硬编码根**：
   - Lua 脚本目录：`ScriptEngine.Init(this, "assets/scripts")` 写死在 `Scene.cpp:282`，改为 `AssetPaths::Scripts` 拼资源根（或新增 `AssetPaths::Scripts` 常量，与 `AssetManager.h` 的 `AssetPaths` 命名空间并列）。
   - 文件对话框初始目录：`FileDialogs::OpenFile(filter, "assets/scenes")` 写死在 `SceneLayer.cpp:1196`（实现 `WindowsPlatformUtils.cpp:14`），改为由资源根拼出。

**验收**：把 `bin/`（exe + 依赖）与 `assets/` 并排放进 `D:\test_dist\`，从 `C:\` 作为工作目录启动 `D:\test_dist\GE_Editor.exe`，默认场景 `2.scene` 正常加载、贴图/音频/脚本齐全。当前**必定失败**，这是阶段 A 的核心验收点。

### 3.2 路径规范形

定义**唯一规范形**（写入新的 `GE/include/GE/Render/AssetPathUtil.h`）：

- **资产引用** = `<相对资源根>/<子路径>`，**正斜杠**，**无 `assets/` 前缀**，**无盘符**，不含 `.`/`..`（`lexically_normal` 后）。
- **伪键** `builtin:*` / `solid:*` 原样保留，不参与文件解析（沿 `AssetManager.cpp:49` 现有语义）。
- **例外**：`ScriptPath` 保持"相对 `assets/scripts`"（现语义，是独立挂载点，不改以免动序列化语义），但在校验阶段一并检查。

三个函数：

```cpp
namespace AssetPathUtil {
    // 绝对/带前缀/带反斜杠 → 规范形；无法归一到根内时返回空 optional（校验报错用）
    std::optional<std::string> ToCanonical(const std::string &raw,
                                           const std::filesystem::path &assetRoot);
    // 规范形 → 绝对路径（= ResolvePath，交由 AssetManager 做）
    bool IsPseudoKey(const std::string &p);          // builtin: / solid:
    bool IsUnderRoot(const std::filesystem::path &abs, const std::filesystem::path &root);
}
```

### 3.3 加载期自愈（向后兼容旧场景）

`ResolvePath`（`AssetManager.cpp:43-66`）当前对绝对路径**直接返回**（`p.is_absolute() → p.lexically_normal()`）——这正是旧场景能带病运行的原因。改为：

- 绝对路径**若在资源根之下** → 转成规范形再解析（相对化）。这样 `2.scene:62` 的 `F:\...\assets\textures\Checkerboard.png` 无需改文件即可正确加载，且**换机器仍有救**（只要资产在包内相对位置一致）。
- 绝对路径**若在资源根之外** → 记一条 `GE_CORE_ERROR`（含原始串与场景文件提示），返回原路径。**这是打包校验必须拦下的情况**，见 §5.3。
- **唯一绕过 `ResolvePath` 的资产消费者已在本次一并接上**：`AnimationClipManager::LoadByKey` 把源键的文件路径部分直接喂给 `GLTF::LoadModel`（`AnimationClipManager.cpp:131-138`），不经资源根；且 `.geanim` 烘焙产物路径由该键派生，落点也跟着错。若不修，`Clip:` 一旦归一成相对路径，发行版就读不到模型。现改为在 `LoadByKey` 内先 `ResolvePath`。其余消费者（网格/纹理/声音）本就走 `AssetManager::LoadMesh / LoadTextureAsync / LoadSound`，天然解析——**这条是排查"还有谁没走资源根"时的通用检查方法**：看它是否经 `Renderer::GetAssetManager()`。
- 新增"根内绝对路径 → 规范形"的**写回**：见下。

### 3.4 序列化归一（治本）

`SceneSerializer::Serialize` 在写每个资产引用前统一过 `ToCanonical`，把绝对路径/带前缀形态落成规范形。这样打开一次旧场景再保存，脏路径即被洗净——是成本最低的批量迁移手段。

**涉及文件**：`GE/include/GE/Platform/Windows/WindowsPlatformUtils.h`（实际落在 `GE/include/GE/Utils/PlatformUtils.h`）、`GE/src/Platform/Windows/WindowsPlatformUtils.cpp`、`GE/src/Core/Application.cpp`、`GE/include/GE/Render/Renderer.h`、`GE/src/Render/Renderer.cpp`、`GE/src/Render/AssetManager.cpp`、`GE/include/GE/Render/AssetManager.h`、新增 `GE/include/GE/Render/AssetPathUtil.h`（+ 可选 .cpp）、`GE/src/Scene/SceneSerializer.cpp`、`GE/src/Scene/Scene.cpp`、`GE/src/Animation/AnimationClipManager.cpp`、`GE_Editor/src/SceneLayer.cpp`。

- 载入 `2.scene`（含 5 处绝对路径 + 2 处根外引用），根内引用全部命中；根外引用在日志里有明确 ERROR，不静默失败。

## 4. 阶段 B：运行时播放器 `GE_Runtime`

### 4.1 为什么必须新增 exe

打包的产物不应包含编辑器。`GE_Editor` 挂着 DockSpace、层级面板、资源面板、ASM 图、Gizmo、Stats 等一大堆编辑器层（`EditorApp.cpp:16-42` 一次性 push 了 7 个 layer），既臃肿又暴露编辑器 UI。引擎已有干净的入口抽象：`EntryPoint.h:10-19` 生成 `main()`，各 exe 只需定义 `CreateApplication`（编辑器版在 `EditorApp.cpp:47`）。

新增 target `GE_Runtime`（`CMakeLists.txt` 追加，参照 `:227-259` 的 `Editor_SRC` 写法），源码放 `GE_Runtime/src/`：

- `RuntimeApp.cpp`：`RuntimeApp : Application`，只 push **一个** `GameLayer`，并定义 `CreateApplication`。
- `GameLayer.cpp/.h`：非编辑器游戏层——加载入口场景、驱动游戏相机、处理输入、无 ImGui 面板。

### 4.2 启动配置 `game.cfg`

发行版根目录放一份 YAML（复用已链接的 yaml-cpp），`GameLayer::OnAttach` 读取：

```yaml
# game.cfg（实际实现的键；省略某键 = 不覆盖引擎默认值）
scene: scenes/2.scene        # 相对资源根，规范形
window:
  title: "我的游戏"
  width: 1600
  height: 900
  vsync: true
  fullscreen: false
rendering:
  deferred: true             # 延迟渲染（GBuffer 链）
  tonemap: true
  bloom: true
  culling: mesh              # 视锥剔除粒度：mesh | submesh
```

> **修正（实现后回填）**：本文早期版本在这里写过 `environment:` 键，**不成立**——天空盒/IBL 由场景内的 `EnvironmentComponent` 驱动（`EnvironmentComponent.Name` 是 `assets/environments/` 下的目录名），已随场景序列化。`game.cfg` 里**没有**也不该有 `environment` 键，否则会出现两处真相。运行时在场景缺该组件时兜底用 `environments/_default_cube/skybox.ktx2`。

**命令行覆盖**：

```
GE_Runtime.exe [--scene <规范形路径>] [--fullscreen] [--free-camera]
```

`--scene` 覆盖 `game.cfg`，是"编辑器里点运行 → 立刻看效果"的最短回环（见 §7）。

### 4.3 与编辑器共享启动逻辑（防漂移）

窗口 / 音频 / `Renderer` / ImGui 的初始化都在 `Application` 基类里（`Application.cpp:25-53`），`RuntimeApp` 直接继承即可复用。**唯一需要抽出来共享的是"从文件加载场景"**：现在该逻辑长在 `SceneLayer::OnAttach`（`SceneLayer.cpp:94-120`）里，与编辑器状态恢复混在一起。建议把"解析入口场景路径 → `SceneSerializer::Deserialize`"提炼为 `Scene::LoadFromFile(path)` 之上的一个薄函数（`SceneLoader::LoadEntryScene`），编辑器与运行时各自调用，避免两份加载逻辑各自演化。

> **相机**：`FollowCamera第三人称相机计划书.md` 里的相机若已落地，`GameLayer` 直接复用；否则先用现有的 `Camera` 自由视角，不阻塞本阶段。

### 4.4 验收

- 命令行 `bin\GE_Runtime.exe --scene scenes/2.scene` 能起窗口、加载场景、按 `game.cfg` 的渲染开关出图，无任何编辑器 UI。
- `--fullscreen` / `--scene` 覆盖生效；未知参数打 WARN 不崩。
- 与编辑器同场景对比：模型、材质、光照、音频、脚本行为一致（脚本系统在运行时同样初始化）。

**涉及文件**：`CMakeLists.txt`、新增 `GE_Runtime/src/RuntimeApp.cpp`、`GE_Runtime/src/GameLayer.cpp`、`GE_Runtime/src/GameLayer.h`、`GE_Editor/src/EditorApp.cpp`（仅当抽取共享加载函数时）、`GE/src/Scene/*`（共享 `SceneLoader`）。

## 5. 阶段 C：依赖收集 + 打包 CLI `gepack`

### 5.1 目标与形态

新增 CLI target `gepack`（`CMakeLists.txt` 里照 `gemesh` 的写法声明 `GEpackTools_SRC` + `add_executable` + 链接 `${GE_NAME}`；**`tools/` 不在 `GE_SRC` 的 glob 列表内，必须显式列出**）。

实际实现的命令行：

```
gepack [--project game.cfg] [--scene scenes/2.scene] [--asset-root assets]
       [--out dist] [--runtime bin/GE_Runtime.exe] [--rules gepack_rules.yaml]
       [--dry-run] [--strict]
```

职责：读入口场景 → 依赖图 walk → 校验 → 拷贝 → 写 `manifest.json` 与 `game.cfg`。

> **对本文早期设计的两处修正**：
>
> 1. **不能复用 `SceneSerializer` 读场景**（原文写的是「复用 SceneSerializer 与各 Manager，不重复实现一套解析」）。实测：`SceneSerializer::Deserialize` 全程调 `Renderer::GetAssetManager()`（该函数断言 Renderer 已初始化），并经 `LoadMesh`/`LoadTextureAsync`/`ApplyMaterialNode`/`SetEnvironment` 触达 GPU 纹理创建——**根本不存在无 GPU 的读场景路径**。改为在 `GE/src/Scene/SceneAssetScanner.{h,cpp}` 里实现一份**只读 YAML 扫描器**（只依赖 yaml-cpp），由打包侧调用。代价是资产字段名有两处（序列化器写、扫描器读），缓解办法是 `SceneSerializer` 与 `MaterialSerializer` 的每个资产字段写出点都加了一行注释回指扫描器。
> 2. **去掉 `--config` 与 `--pack`**。本构建布局只有一个 `bin/` 输出目录（Debug/Release 由 `build.bat` 决定，且缓存目录不同），`--config release` 无从下手；`--pack` 是阶段 D 的单文件包开关。`--strict` 的语义也改为「把**告警**当错误」——有 Error 时无论是否 strict 都不产出 dist（原文把「根外引用=Error」与「`--strict` 下构建失败」并列，逻辑上互相矛盾：既然校验不过，就不该产出半成品包）。
>
> 另外把「失败时不要留下半成品」落进了实现：先建 `<out>.staging` 同级目录，全部就绪后 `rename` 换入（旧的让位成 `<out>.old` 再尽力删除），`manifest.json` 在 staging 内**最后写**，作为「这份包完整」的标记。原地拷贝一旦中途失败，半成品 dist 与完整 dist 无法区分。

### 5.2 依赖图：边的定义

场景里的资产引用形态由 `SceneSerializer` 读写两端确定（**本表以符号名为准**，行号随重构漂移，不再列）：

| 源字段 | 写出/读入符号 | 收集动作 |
|---|---|---|
| `MeshRenderer.Mesh` | `Serialize` 的 mesh 写出端 / `LoadMesh` | 伪键（`builtin:*`/`solid:*`）跳过；否则收 `.gemesh` |
| `Skin.Mesh` | 同上（蒙皮网格） | 同上，常与 `MeshRenderer.Mesh` 同指一份 |
| `SpriteRenderer.Texture` | 精灵写出端 / `LoadTextureAsync` | 收贴图 |
| `Water.NormalMap`、`Water.ColorMap` | 水面写出端 / `LoadTextureAsync` | 收贴图（仅部分场景有水面组件） |
| `AudioSource.Sounds[].SoundPath` | 音频写出端 / `AudioWorld::PlaySlot` | 收音频（`.wav`/`.mp3`） |
| `Script.ScriptPath` | 脚本写出端 / `ScriptEngine` | 基准是 **`assets/scripts`**（不是资源根）→ 整目录收录即可，见 §5.3 |
| `Animation.Clips[].Clip` | 动画写出端 / `AnimationClipManager::LoadByKey` | 源键 `"path#N"` → 收 `DeriveAnimationBakePath` 派生的 `.geanim`（同目录 `foo.geanim` / `foo_N.geanim`）；**缺烘焙产物**时回退收源 glTF 闭包（`.gltf` + `buffers`/`images` 的 `uri`） |
| 材质覆写（内联形态） | `MaterialSerializer::WriteMaterialNode` / `ApplyMaterialNode` | 收四槽贴图 `AlbedoTexture`/`NormalTexture`/`EmissiveTexture`/`MetallicRoughnessTexture` |
| 材质覆写（引用形态） | 覆写写出端只写一行 `Material: materials/x.gemat` | **先收 `.gemat`，再按它的四槽收贴图**（见下注） |
| `Environment.Name` | 环境写出端 / `Renderer3D::SetEnvironment` | 是**目录名**：收 `environments/<name>/skybox.ktx2` + `prefilter.ktx`（`Enabled: false` 也照收，体积换确定性） |
| `.gemesh` 内嵌（不是场景字段） | `GEMeshLoader` 的材质 chunk | 收每份材质的五个贴图槽；`META.sourceAsset` 是开发期追溯信息，**运行时不需要**，故不作为边 |
| 着色器 | **不在场景里**，28 处硬编码文件名 | 固定收 `shaders/glsl/**/*.spv` |
| 字体 | **不在场景里**，`ImGuiLayer` 初始化即加载 | 固定收 `fonts/opensans/OpenSans-Regular.ttf` |

> **`.gemat` 必须递归展开。** 材质改为可独立落盘后，一个材质的贴图引用可能**只存在于 `.gemat` 文件里**——场景文件里只看得到一行 `Material: materials/x.gemat`。收集器必须把 `.gemat` 当节点读开，再按其各槽贴图收纹理；只扫场景会漏掉这些贴图。
>
> **`.gemesh` 也必须展开**（本轮实测新增）。它同样不是自包含格式：材质贴图槽以字符串写进文件，运行期由 `MeshManager` 直接拿去 `TextureManager::LoadAsync`。收集器用 `ParseGEMesh`（纯 CPU）取这些槽；**并且它们必须是规范形**——旧资产里残留绝对路径时，收集器报 Error 并提示重烘（见 §9.5）。

**三个"不在场景里"的特例必须显式处理**：

1. **着色器按文件名写死在代码里**（`Renderer3D_Lifecycle.cpp` 26 处 + `Renderer2D.cpp` 2 处，共 **28 个 `.spv`**，无任何动态枚举），场景不引用它们，依赖图无法发现。策略：**全量收 `assets/shaders/glsl/**/*.spv`**（体量小，安全优先）。运行期只读 `.spv`；`.vert/.frag/.glsl/.comp` 是编译期源，排除。后续可做"按渲染特性裁剪"作为体积优化——但那要先把这批字符串改成一份集中的「管线→着色器」表，**别和打包捆在一个阶段里**。
2. **IBL 环境**由场景的 `EnvironmentComponent` 决定（**不是** `game.cfg`，见 §4.2 的修正）。`assets/environments/<env>/` 下 `source.exr` 与 `preview.png` 是编辑期资产，排除；运行时只需 `skybox.ktx2` + `prefilter.ktx`。另有**兜底环境** `environments/_default_cube/skybox.ktx2`（场景无该组件时渲染器用它）与**共享** `environments/brdf_lut.png`，两者都固定收——漏掉它们，"换台机器也能跑"的验收会在没有环境组件的场景上失败。
3. **字体**由 ImGui 初始化加载（`GE_Runtime` 与编辑器共享 `Application` 初始化链，ImGui 帧照常构建），固定收一份 `OpenSans-Regular.ttf`。

**排除项**（写在 `tools/gepack/gepack_rules.yaml`，支持 `**`/`*`/`?` glob）：`Screenshot/**`、`cache/**`（实为空壳，无任何代码引用，见 §9.4）、`environments/**/source.exr`、`environments/**/preview.png`、`shaders/glsl/**/*.{vert,frag,glsl,comp}`、`**/*.ilk`、`**/*.pdb`。

> 排除规则**只作用于整目录收录与"未引用资产"统计**，不作用于被显式引用的资产：少一个被引用的文件，包就是坏的；"没被需要的东西"才是排除的对象。

### 5.3 Lua 脚本闭包问题（必须正视）

脚本按 `ScriptPath` 能收到**入口文件**，但 Lua 的 `require` 会在运行期沿 `package.path`（`ScriptEngine` 的 `Init(scene, scriptsBaseDir)`，根为 `GetAssetRoot()/scripts`）拉入任意依赖，**静态分析不可靠**。初版策略：**整个 `assets/scripts/` 目录全量打包**（脚本是文本，体积可忽略），并在 manifest 里标记为 `scripts: "whole-dir"`。等脚本规模上来再做 `require` 图扫描。

### 5.4 校验（`gepack` 最有价值的部分）

打包前扫一遍，问题分级输出：

| 级别 | 检查项 | 处理 |
|---|---|---|
| **Error** | 资产引用解析后落在资源根**之外**（`ToCanonical` 返回 nullopt） | 列出原始串 + 引用位置；**一律非零退出**（有 Error 就不产出 dist） |
| **Error** | 引用的文件不存在 | 同上 |
| **Error** | `.gemesh` 内嵌的贴图串是根外路径（旧资产烘焙残留） | 报出该串并提示重烘（`gemesh --asset-root`） |
| **Error** | 入口场景不存在 / 资源根不存在 / `.gemat` 与源 glTF 解析失败 | 前置条件失败，不做任何拷贝 |
| **Warn** | 网格仍是 `.obj`/`.gltf`（未烘焙） | 报告 + 改收源 glTF 闭包；**不在打包期自动烘焙**（工具不该偷偷写资产） |
| **Warn** | 动画缺 `.geanim` 烘焙产物 | 回退收源 glTF 闭包（运行时要搬整份源文件，故值得修） |
| **Warn** | 环境缺 `prefilter.ktx`（如 `_default_cube`） | 报告，不算错（该环境本就不提供 IBL 预过滤） |
| **Warn** | 未被引用的资产（场景未引用） | **仅报告不剔除**，避免误伤脚本/动态加载；列前 20 条 |
| **Info** | 资产总数 / 总字节 / 按类型分布 | 打日志 |

`--strict` 的作用是**把 Warn 升为 Error**（CI 用）；Error 本身不需要 `--strict` 就已经拦下构建。

## 6. 阶段 D（可选）：单文件资源包 `.gepak` + 虚拟文件系统

> **明确说明**：阶段 A–C 做完就已经"能发布"（一个文件夹）。本阶段解决的是**单文件分发**、轻微防篡改、以及"海量小文件拷贝慢"的问题。**不是必需的**，慎开工。

### 6.1 格式

```
.gepak
├─ Header   : magic "GEPK" + formatVersion + entryCount + indexOffset + indexSize
├─ Entries  : 逐条原始字节（可选 LZ4/deflate 压缩）
└─ Index    : entryCount × { pathHash | path | offset | size | rawSize | flags }
```

初版不加密（若后续需要，就是在 entry 层加一层对称变换——**只留接缝，不先实现**）。索引常驻内存，支持 `ReadFile(name) → std::vector<byte>`。

### 6.2 VFS 层（本阶段的主要工作量）

当前引擎**没有 I/O 抽象**：`FileSystem.h` 全部内容只有一个 `ReadBinaryU32`（唯一消费者 `VulkanShaderModule.cpp:73`），其余约 20 处 loader 各自直接开文件：

| loader | 当前调用 | 迁移目标（内存变体，均已存在） |
|---|---|---|
| stb 图像 | `stbi_load`（`Texture.cpp:385,589`） | `stbi_load_from_memory` |
| KTX | `ktxTexture_CreateFromNamedFile`（`Texture.cpp:309,422,559,809`） | `ktxTexture_CreateFromMemory` |
| tinygltf | `LoadBinaryFromFile`（`GLTFLoader.cpp:389,391`） | `LoadBinaryFromMemory` |
| tinyobj | `LoadObj`（`OBJLoader.cpp:37`） | istream 重载 |
| miniaudio | `ma_decoder_init_file`（`SoundAsset.cpp:22`） | `ma_decoder_init_memory` |
| yaml-cpp | `YAML::LoadFile`（`SceneSerializer.cpp:1279`） | `YAML::Load(std::string)` |
| 自研二进制 | `std::ifstream`（`GEMeshLoader.cpp:393,416`、`AnimationClipLoader.cpp:134,155`、`FileSystem.cpp:10`） | 走 VFS |
| Lua | `ReadFileContents`（`ScriptEngine.cpp:117`）+ `require` 的 `package.path` | 走 VFS **并需自定义 Lua searcher**（见风险 §8.2） |

设计：

```cpp
// GE/include/GE/FileSystem/VirtualFileSystem.h
class VirtualFileSystem {
public:
    static bool MountPack(const std::filesystem::path &pak);   // 挂载 .gepak
    static void UnmountAll();
    static bool Exists(const std::string &assetRelPath);
    static std::optional<std::vector<char>> ReadBinary(const std::string &p);
    static std::optional<std::string>       ReadText(const std::string &p);
    // 未挂载 pak 时天然回退真实文件系统 → 开发期零感知
};
```

**关键设计点**：`ReadBinary/ReadText` 在**未挂载任何 pak** 时直接走真实 FS。这样开发期（编辑器、`--scene` 回环）完全不受影响，VFS 成为纯粹的发行期加速层——这是本阶段能低风险推进的核心。

### 6.3 验收

- 不打 pak（开发期）：编辑器与运行时行为与阶段 C 完全一致（回归零差异）。
- `gepack --pack` 产出单个 `assets.gepak` + 不带 `assets/` 目录的 `dist/`，运行时能完整加载场景（模型/贴图/音频/脚本/着色器全通）。
- 加载耗时对比：小文件多的场景（如 `shayv` 模型目录）打成单包后启动应更快。

**涉及文件**：新增 `GE/include/GE/FileSystem/VirtualFileSystem.h`、`GE/src/FileSystem/VirtualFileSystem.cpp`、新增 `GE/include/GE/FileSystem/AssetPack.h`、`GE/src/FileSystem/AssetPack.cpp`，以及上表全部 loader 的调用点。

## 7. 阶段 E：编辑器「构建」菜单

- **菜单位置**：顶部菜单栏在 `DockSpaceLayer`（`EditorApp.cpp:30` 注入、`:36` 用 `SetSceneLayer` 把场景操作绑到「文件」菜单）。新增一级菜单 **「构建」**，挂在同一处，风格与现有条目一致。

## 9. 风险与开放问题

1. ~~**根外引用是遗留数据债**~~ —— **已处理（`eac2f39c`）**：4 处指向 `C:\Users\...\Desktop\models\shayv\` 的动画 clip 引用，源文件（`.gltf`/`.bin`/`.geanim`）已搬进 `assets/models/shayv/` 并改写为规范形；同一提交顺带清掉 `3.scene`/`4.scene` 的 31 处根内绝对路径。注意 `assets/models/` 等目录在 `.gitignore` 里，**仓库本身不含模型资产**（体积取舍）——克隆下来的仓库里场景引用是悬空的，`gepack` 会如实报「文件不存在」。

2. **Lua `require` 闭包静态收集不可靠**：`package.path` 是运行期机制（`ScriptEngine.cpp`），任何静态扫描都会漏。初版全量打包 `assets/scripts/` 规避（`gepack` 已如此实现，manifest 记 `scripts: "whole-dir"`）；阶段 D 引入 VFS 后，Lua 的 `require` 会绕过 VFS 直接命中真实文件系统，**必须补一个自定义 Lua searcher** 从 VFS 读，否则打成 pak 后脚本全失效。这是阶段 D 最容易被漏掉的一处。另注意 `ScriptPath` 的基准是 `assets/scripts`（不是资源根），收集器必须补前缀。
   **✅ 已落地（M2.5，`c1aa0c6c`）**：`ScriptEngine::Init` 往 `package.searchers` 插了一个 VFS 查找器（`luaL_loadbuffer`）；`baseDir` 由"资源根拼出的绝对路径"改为规范形 `"scripts/"`，脚本文件读取也一并走 VFS。`package.path` 不再被覆写（保留 Lua 原值）。

3. **着色器与场景解耦**：28 处硬编码文件名（`Renderer3D_Lifecycle.cpp` 26 + `Renderer2D.cpp` 2），依赖图看不见。全量收录是当前唯一稳妥解；若日后要做体积裁剪，得先把这批字符串改成一份集中的"管线→着色器"表（这本身是个值得独立做的小重构，但**不要和打包捆在一个阶段里**）。

4. **`assets/cache/` 是空壳**：只有空的 `assets/cache/shader/opengl/` 目录，全仓库零引用（grep `assets/cache`/`ShaderCache` 无命中）。打包直接排除；它原本大概是想做着色器缓存但没落地——**别误以为是可用的缓存机制**。

5. ~~**`.gemesh` 是否自包含**~~ —— **已确认：不自包含**。`GEMeshLoader` 的材质 chunk 把 `albedoMap`/`normalMap`/`emissiveMap`/`metallicMap`/`roughnessMap` 与 `META.sourceAsset` 当字符串存盘，运行期 `MeshManager` 直接拿去 `TextureManager::LoadAsync`。根因是 `GLTFLoader` 的贴图路径按「源文件所在目录」拼，**烘焙时输入是绝对路径就写出绝对路径**（当时实测：`people.gemesh` 4 处、shayv 7 个文件各 1~2 处）。

    **⚠️ 本条的"根治"当时只做了一半，M2.5 才发现（见 Android 计划书 §10 风险 19）**：`CanonicalizeGEMeshEmbeddedRefs` 只加在**烘焙出口**（`ConvertToGEMesh` / `BakeSourceToGemesh`），**运行期从不调用**，所以存量资产照旧带绝对路径 —— 实测 `dist/assets/models/shayv/未命名.gemesh` 里仍是 `F:\yxy\project\GameEngine\assets\models\shayv\Ellen_Body_Map1_D.png`，说明这 7 个网格是在归一代码落地**之前**烘的，重烘没做。而它依赖资源根的绝对形，Android 上不存在这个锚点，归一必然失败。

    这个漏洞的症状在桌面上也是隐形的：`dist/` 拷到别处跑时，归一失败后旧代码会**静默去读开发机上的那份资产**（绝对路径在开发机上真实存在），看起来一切正常；只有换机器才断。**这正是「dist 隔离」这条验收判据的价值** —— 它一直被列在待办里而没做（见本计划书 §5.7 后的验证清单）。修法：`AssetPathUtil::CanonicalCandidates`（根无关）+ 由 `VFS::Exists` 定夺，运行期在 `MeshManager` 的 decode 与 `FinalizeGLTFMesh` 收口。**仍建议用 `bin/gemesh.exe --asset-root assets` 重烘那 7 个 `.gemesh`**：代码兜底是给第三方/用户自烘的网格用的，包内数据本身也该干净。

6. ~~**`.geanim` 与源 glTF 的关系待确认**~~ —— **已确认**：场景 `Clips[].Clip` 存的是源键 `"path#N"`，运行期 `AnimationClipManager::Load` **优先读 `DeriveAnimationBakePath` 派生的 `.geanim`**，仅当烘焙产物缺失/损坏时才回退源 glTF 并重建。故依赖图收派生的 `.geanim`（缺失时才回退收源 glTF 闭包并告警）。

7. **编辑器/运行时启动逻辑漂移**：`RuntimeApp` 与 `EditorApp` 共享 `Application` 基类，但"加载入口场景"若各写一份，迟早不一致。§4.3 抽出 `SceneLoader::LoadEntryScene` 共享是低成本的预防。

8. **`GE_EDITOR_BUILD_SCENE_FROM_CODE` 编译开关**（`SceneLayer.cpp`）：这是程序化建场景的开发开关，与"从文件加载"互斥。打包路径**必须**走文件加载分支，构建发行版时应断言该开关为 OFF，避免产出"没有场景文件依赖"的假通过。

9. **平台目标**：当前只有 Windows（`EntryPoint.h` 整个 `main` 包在 `#ifdef _WIN64` 里，`Platform/Windows/` 独占）。本计划只承诺 Windows；`GetExecutableDirectory` 等平台相关的点做条件编译预留，不做 Linux/macOS 实现。

10. **非 ASCII 路径与命令行编码（阶段 C 已知限制）**：资产名里有中文（`未命名.gltf`、中文 `.wav`），YAML 与文件名都是 UTF-8 字节串；`gepack` 内部与源 glTF 的 `uri` 都按 UTF-8 处理（`uri` 里的百分号编码会先解码）。但 `main(argv)` 拿到的是 ANSI 代码页的字节，**`--scene`/`--out` 传中文路径会乱码**——路径以 UTF-8 的 `game.cfg` 为准即可绕开。宽字符 argv 与 >260 长路径（`\\?\` 前缀）留到阶段 F。

11. **`manifest` 无 `sha256`（阶段 C 已知取舍）**：仓库无第一方哈希实现，本轮只做到「资产数/字节数对账」。增量打包（比哈希决定重拷）与运行时启动自检（缺资产/版本不匹配早失败）依赖它，随阶段 D 一起做。

12. **【首次实跑发现】单个环境贴图占全包 80%，直接顶高 APK 体积**：`environments/DaySkyHDRI065B/skybox.ktx2` 单文件 **192 MB**，而 `2.scene` 的完整包才 216 MB。这**不是打包 bug，是资产本身的体积**——但对下游影响很大：Android 计划书阶段 G 要把这棵树塞进 APK，**APK 会到 ~250 MB**（远超 Play 常规预期，且 `assets/` 在 APK 内默认还是压缩存储，解压与首帧加载都会慢）。
    **⚠️ 下面这段的病因判断被 M2.5 实跑证伪，已修正 —— 别再按"降分辨率"去做**：运行日志给出 `cubemap 异步解码完成: …/skybox.ktx2 (2048x2048 mip=1)` + `格式=R16G16B16A16Sfloat`。它是 **2048² 的 6 面 cubemap、16 位浮点、未压缩、无 mip 链**：2048×2048×8 B×6 = 201,326,592 B，正好是清单里的 201,326,848 B。**所以问题不是"6.5K 过采样"，而是格式没压缩；2K 对天空盒是合理分辨率。**
    **可选方向**（按代价从低到高）：① **BC6H 压缩**（`BC6H_UF16` 专为 HDR 设计，8 位/像素 → ≈ **25 MB，约 8:1**；引擎已链 KTX，`Texture.cpp::PrepareKtxForUpload` 里现成的 BC7 能力探测可照搬）—— 对症的一刀；② 降分辨率到 1K（201→50 MB，仅 4:1，且真损细节）；③ Play Asset Delivery 分包。另注意它**没有 mip 链**，重烘时一并补上。
    **建议**：先做 ①。另外 M2.5 发现 VFS 的内存路径（整份读入 + libktx 再拷一份）让这 192 MB 的加载瞬时占用约 2× ≈ 400 MB，**手机上可能直接 OOM** —— 这让"先压缩"多了一条比体积更硬的理由。详见 Android 计划书 §10 风险 14。

13. **【本轮教训】「定义了但没人调用」的静默漏收，缺乏自动防线**：§5.7 那个 bug 的形态是「`AddRef` 函数体完好、零调用点」，编译器不会警告，没有测试也不会拦。同类风险对打包工具而言是致命的（产物不完整却报成功）。**可加的防线**（按性价比）：① 打包前后做**数量级对账**——`dist/assets` 的文件数/字节数若与「未引用资产」比例异常（如本例 13130 未引用 vs 40 已收），应升级为 Error 而非 Warn；② 给 `2.scene` 这类已知场景录一份**期望资产基线**（数量 + 关键路径清单），`--strict` 模式下比对；③ `AddRef` 这类桥接函数若长期零调用，靠 review 或定期 grep 发现。**至少先做 ①**，它能把同类问题从「静默」变成「刺眼的」。
