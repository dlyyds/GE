# 计算管线实现计划书

> 状态：**已实现（2026-09-09）** / 待首个消费端接入验证
>
> 目标：让 GE 引擎的计算管线从「占位桩（构造即抛异常）」变成「可用能力」——补齐 `VulkanComputePipeline` 的真实创建，并打通「缓存 → 命令缓冲 eCompute 绑定」整条链路。本次**只做能力打通，不落地任何实际 dispatch 调用点**（首个消费端另立计划，如水体焦散 / 物理 / 后处理）。
>
> 背景结论（来自评审）：
> - 计算管线的 Vulkan 状态只有「1 个 compute 阶段 + pipeline layout」两个要素，**不需要图形管线的整份 `VulkanPipelineState`**（顶点输入 / 光栅化 / 深度模板 / 混合等对它全是无效字段）。
> - 本引擎中着色器阶段本来就不存在 State 里，而是由 `VulkanPipelineLayout::GetShaderModules()` 提供（`VulkanPipelineState.cpp:379-392` 的 `buildCommon()` 从 layout 提取阶段）。故「计算管线 = 只挂一个 CS 模块的专属 layout」。
> - 结论：计算管线构造与去重一律**以 `VulkanPipelineLayout` 为身份**，不再接受 `VulkanPipelineState`。
>
> 关联：`VulkanPipelineState`（图形管线状态机）、`VulkanResourceCache`（全局去重缓存）、`VulkanCommandBuffer`（惰性刷入）。

## 1. 目标与范围

### 1.1 达成后能力

| 能力 | 说明 |
|---|---|
| 计算管线创建 | `VulkanComputePipeline` 依据一个「只含 CS 模块」的 layout 真实创建 `VkPipeline` |
| 去重缓存 | 计算管线仍走 `VulkanResourceCache` 的 `RequestComputePipeline`，key = layout 身份 |
| 命令缓冲分发 | `Dispatch()` → `FlushPipelineState(eCompute)` 经缓存取管线并 `bindPipeline` |
| 全链路复用 | push constants、descriptor set 绑定、队列族全部复用现有通路，不改 |

### 1.2 明确不做

- **不做任何实际 dispatch**（无渲染器/场景调用点，避免引入无法验收的死代码）。
- **不做 storage image 写路径**：`FlushDescriptorState` 当前所有 image descriptor 统一 `eShaderReadOnlyOptimal`（`VulkanCommandBuffer.cpp:534`），不满足「写 storage image（需 `eGeneral`）」的 compute 场景。消费端如需写图，另行扩展 `BindImage`/新增 `BindStorageImage`（见 §6.2）。
- **不做 specialization constants**：引擎目前没有任何 `pSpecializationInfo` 装配（`buildCommon` 也不设），属引擎级缺口，另立范围。
- **不改 `VulkanPipelineState`**：不为其加 compute 构建方法，计算信息不从 State 读。
- **不改队列族选择**：`VulkanDevice.cpp:265` 已按 `Graphics | Compute` 请求队列族，无需动。

## 3. 核心决策

### 3.1 决策一：计算管线身份 = layout，不背整份 PipelineState

- `vk::ComputePipelineCreateInfo` 只需 stage + layout 两个要素；State 里的图形字段对计算无效，且 `VulkanPipelineState::hash()`（`VulkanPipelineState.cpp:528` 起）把附件格式/顶点输入/装配拓扑全算进 key —— 若以 state 为 key，同一计算任务只因某图形字段不同就重复建管线，去重被污染。
- 因此 ctor 与缓存 key 均只认 `VulkanPipelineLayout`。

### 3.2 决策二：缓存 key = layout 句柄 hash，靠 layout 缓存保证精确

- `RequestResource` 对实参做 `hash_param`，`std::hash<VulkanPipelineLayout>` 已存在（`ResourceCaching.h:203-210`，按 `GetHandle()` 即 layout 句柄）。
- 精确性依赖一个已成立的不变量：layout 由 `RequestPipelineLayout` 按「模块指针序列」去重（`VulkanResourceCache.cpp:57-60`），**内容相同 ⇒ 同一 layout 对象 ⇒ 同一句柄**。所以「按句柄去重」=「按内容去重」，不多不少。
- 约束：所有调用必须走 `RequestPipelineLayout` 拿 layout，禁止绕过缓存手工构造等值对象。

### 3.3 决策三：compute 必须用「只含 CS 的专属 layout」

- Vulkan 规定：图形管线不得含 compute 阶段，计算管线必须恰有 1 个 compute 阶段。当前 `buildCommon()` 会把 layout 内**全部**模块塞进管线阶段（`VulkanPipelineState.cpp:382-391`），所以同一个 layout 绝不能被图形与计算混用。
- ctor 内校验「layout 模块数 == 1 且 stage == eCompute」，不满足即抛带说明的错误 —— 既防混用，也兜住误用图形 layout 调 `Dispatch` 的情况。

## 5. 关键实现细节

### 5.1 `VulkanComputePipeline` ctor（替换 `VulkanPipeline.cpp:85-89`）

```cpp
VulkanComputePipeline::VulkanComputePipeline(VulkanDevice &device,
                                             VulkanPipelineLayout &pipeline_layout,
                                             VkPipelineCache pipeline_cache) : VulkanPipeline(device) {
    const auto &modules = pipeline_layout.GetShaderModules();
    if (modules.size() != 1 || modules[0]->get_stage() != vk::ShaderStageFlagBits::eCompute) {
        throw std::runtime_error(
            "Compute pipeline requires a layout containing exactly one compute shader module");
    }
    VulkanShaderModule *cs = modules[0];

    vk::PipelineShaderStageCreateInfo stage{
        .stage  = vk::ShaderStageFlagBits::eCompute,
        .module = cs->GetHandle(),
        .pName  = cs->get_entry_point().c_str(),   // 模块存活期 > 同步创建调用，安全
    };
    vk::ComputePipelineCreateInfo info{
        .stage  = stage,
        .layout = pipeline_layout.GetHandle(),
    };

    auto result = GetDevice().GetHandle().createComputePipeline(
        vk::PipelineCache{pipeline_cache}, info);
    if (result.result != vk::Result::eSuccess) {
        throw std::runtime_error("Failed to create compute pipeline");
    }
    SetHandle(result.value);
}
```

- 错误风格与图形管线一致（`VulkanPipeline.cpp:61-67`）。
- `pipeline_cache` 参数保留默认 `VK_NULL_HANDLE`，与 `RequestGraphicsPipeline` 现状对称。
- 只读 layout / 模块的句柄做同步创建，无须在管线对象内保存引用。

### 5.2 命令缓冲 eCompute 分支（替换 `VulkanCommandBuffer.cpp:374-377`）

```cpp
} else if (pipeline_bind_point == vk::PipelineBindPoint::eCompute) {
    auto *layout = m_PipelineState.getPipelineLayout();
    if (!layout) {
        throw std::runtime_error("Compute dispatch requires a bound pipeline layout");
    }
    auto &pipeline = cache.RequestComputePipeline(*layout);
    GetHandle().bindPipeline(vk::PipelineBindPoint::eCompute, pipeline.GetHandle());
}
```

### 5.3 缓存侧（`.h:107-110` / `.cpp:74-77`）

```cpp
VulkanComputePipeline &RequestComputePipeline(VulkanPipelineLayout &pipeline_layout);
// cpp:
return RequestResource<VulkanComputePipeline>(m_ComputePipelineMutex, m_ComputePipelines, pipeline_layout);
```

key 由 `std::hash<VulkanPipelineLayout>`（按 layout 句柄）产出；模板容器、mutex、`Clear/ClearPipelines` 原样复用。

### 5.4 复用即免费的链路（无需改动）

- **push constants**：`FlushPushConstants` 经 `layout->GetPushConstantRangeStage(size)` 查阶段（`VulkanCommandBuffer.cpp:388-403`），CS 的 push range 由 layout 反射自动生成。
- **descriptor set**：`FlushDescriptorState` 按 `layout->GetShaderSets()` 逐 set 请求并绑定（`.cpp:408-568`），compute 模块反射出的 set 走同一逻辑；绑定点的 `bindDescriptorSets` 已按传入的 `pipeline_bind_point` 分派（`.cpp:561`）。
- **队列族**：`Graphics | Compute` 已就绪（`VulkanDevice.cpp:265`）。

## 6. 风险与边界

1. **混用布局防护**：误用带 VS/FS 的 layout 触发 `Dispatch` → ctor 校验抛错（§5.1），错误信息明确；正确用法是 compute 专属 layout。
2. **storage image 写（`eGeneral`）不支持**：`FlushDescriptorState` 硬编码 `eShaderReadOnlyOptimal`（`VulkanCommandBuffer.cpp:534`）。compute 若只读（如全屏只读采样）可用；要写则需后续为 image 记录目标布局。**本次范围外**。
3. **specialization constants 缺失**：引擎无 `pSpecializationInfo` 装配，compute 想用 spec constant 调整 workgroup 属引擎级缺口。**本次范围外**。
4. **缓存 key 语义 = layout 身份**：正确性依赖「一律走 `RequestPipelineLayout`」的不变量（§3.2），绕过缓存手工构造等值 layout 会导致重复管线 —— 在文档与调用约定中写死。
5. **无真实 dispatch 调用点**：本次是纯能力落地，现有图形路径行为零变化；验收需临时冒烟（见 §7）。
6. **`.spv` 供给**：首个消费端需提供已离线编译的 compute `.spv`（引擎加载 `.spv` 后按 stage 反射，`VulkanShaderModule.cpp:72-90`）；编译 `.comp → .spv` 的工具链属资产管线，不在本范围。

## 7. 验收与示例用法

### 7.1 验收标准

1. 引擎照常编译、运行，现有水面/后处理/场景画面无回归（无 dispatch 调用，纯能力改动不应影响图形路径）。
2. 代码评审确认：`RequestComputePipeline` 不再接受 `VulkanPipelineState`；ctor 不再抛「not yet implemented」。
3. 临时冒烟（自选，验证后移除或留作首个消费端）：录制一个写死输出色的最简 compute dispatch，读回/上屏确认管线创建与绑定成功、结果正确。

### 7.2 首个消费端接入模板（供未来使用，非本次改动）

```cpp
// 1) 加载 CS 模块（cache 按 stage+source+entry+variant 去重）
auto &cs = cache.RequestShaderModule(vk::ShaderStageFlagBits::eCompute,
                                     ShaderSource{AssetPaths::Shaders + "/xxx.comp.spv"}, "main");
// 2) 请求「只含该 CS」的专属 layout（反射 descriptor set / push range）
auto &layout = cache.RequestPipelineLayout({&cs});
// 3) 每帧录制：绑定 layout → 绑资源 → 推常量 → 分发（触发惰性 flush）
cmd.BindPipelineLayout(layout);
cmd.BindBuffer(/* ssbo */...);
cmd.BindImage(/* 只读 storage image 或输入纹理 */...);
cmd.PushConstants(/* CS push 块 */);
cmd.Dispatch(workgroup_x, workgroup_y, workgroup_z);
```
