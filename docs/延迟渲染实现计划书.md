# 延迟渲染实现计划书（基于 RenderGraph 的接入设计）

> 注：旧版《延迟渲染方案计划书》已废弃，本文以当前已落地的 RenderGraph（声明序执行 +
> 自动屏障）架构为唯一基准，重新梳理延迟渲染的接入点、前置缺口与实施步骤。

---

## 1. 目标与范围

在不透明材质上引入 G-Buffer + 光照 Pass 的延迟管线，透明材质保留前向混合管线
（混合管线并存）。阶段 1 完成后：

- 不透明（Opaque + Mask）走 GBuffer Pass → Lighting Pass；
- 透明（Blend）走独立 Transparent Pass，沿用现有前向光照着色器；
- 天空盒并入 Lighting Pass 的天空分支（保持"环境图直接输出、不 tonemap"的现状语义）；
- 保留前向/延迟双路径开关，随时回退比对；
- 覆盖现有全部材质能力：PBR / Blinn-Phong、法线贴图、自发光、MASK 裁剪、
  doubleSided、蒙皮（mesh_skinned.vert 复用）。

**阶段 1 不做**（见 §10）：IBL 延迟光照、HDR 中间缓冲 + 独立 tonemap、SSAO、
阴影贴图、RenderGraph 虚拟资源分配/别名、光源剔除。

## 2. 现状梳理：一帧的渲染图

当前每帧的 pass 链（声明序即执行序）：

```
BeginFrame（Renderer.cpp:93）
  └ m_FrameGraph.Reset()
SceneLayer::OnUpdate（SceneLayer.cpp:163）
  ├ Import ViewportColor / ViewportDepth（SceneViewport 离屏目标）
  ├ AddPass "Scene3D"：颜色 eClear + 深度 eClear → Renderer3D::FlushScene
  │    （前向：天空盒背景 → 不透明段 → 透明段，光照全在片元着色器里算）
  └ AddPass "Scene2D"：颜色 eLoad + 深度 eLoad → Renderer2D::FlushScene
       （颜色 finalLayout = ShaderReadOnlyOptimal 供 ImGui 采样）
EndFrame（Renderer.cpp:114）
  ├ AddPass "UIPass"：swapchain eClear，采样视口颜色，finalLayout = PresentSrc
  └ Compile() → Execute(cmd, frame)
```

关键现状事实（决定接入方式）：

| 事实 | 位置 | 对延迟渲染的影响 |
|---|---|---|
| 虚拟资源只登记不分配，屏障与录制均跳过非 external 资源 | `RenderGraph.cpp:313-317` | GBuffer 纹理不能走 `CreateVirtualResource`，需持久持有再 Import |
| pass 声明处只有编辑器 SceneLayer 一处（+ EndFrame 的 UIPass） | `SceneLayer.cpp:247-291` | 改动面集中，运行时侧无第二声明点 |
| `colorAttachments` 是 vector，动态渲染 MRT 天然支持 | `RenderGraph.cpp:405-422` | GBuffer 多附件声明无需改图本体 |
| `PassExecuteContext` 只透传**首个**颜色附件视图 | `RenderPassDesc.h:84` | MRT 管线需要全部附件格式 → 必须扩展 |
| Renderer3D 采集/录制分离已就位（EndScene 只采集，FlushScene 录制） | `Renderer3D.cpp:462-491` | 拆 pass 只动 FlushScene，采集 API 不变 |
| 批次按 passId（不透明/透明）已是连续前缀，首个 Blend 批次切分两段 | `Renderer3D.cpp:507-517` | GBuffer 段与 Transparent 段直接取两段批次，排序逻辑复用 |
| FlushScene 末尾 `m_Meshes.clear()` | `Renderer3D.cpp:490` | 拆成两个 pass 后批次要跨 pass 消费，清空时机必须后移 |
| 深度被 Scene2D 读做遮挡（eLoad），颜色被 ImGui 采样 | `SceneLayer.cpp:269-288` | 延迟链必须保证最终的视口颜色/深度资源语义不变 |

## 3. 接入点：延迟渲染插在哪

**接入点就是 `SceneLayer::OnUpdate` 里的 pass 声明段（SceneLayer.cpp:246-291）。**
渲染图是逐 pass 声明的编排层，延迟渲染不改动图本体（屏障推导已够用，见 §5.4），
只把原来的一张 Scene3D pass 替换为三张 pass：

```
现状：  Scene3D(前向) ──────────────→ Scene2D → UIPass

延迟：  GBuffer ──→ Lighting ──→ Transparent ──→ Scene2D → UIPass
        MRT+深度   全屏光照      透明前向管线
        eClear     写视口颜色     颜色/深度 eLoad
        Opaque/Mask （含天空分支）   （沿用现有管线）
```

- **GBuffer Pass**：3 张 GBuffer 附件（eClear）+ 视口深度（eClear），只录制
  不透明段批次（Opaque + Mask），混合关、深度写开。
- **Lighting Pass**：全屏三角形，`readImages` 声明读 G0~G2，颜色附件 = 现有
  视口颜色图（eClear，语义与现在 Scene3D 的清屏完全一致）。逐像素读 GBuffer
  做光照；天空像素（G0.a 哨兵）直接采样环境全景图输出。
- **Transparent Pass**：颜色 eLoad（叠在光照结果上）+ 深度 eLoad（测试不写），
  录制透明段批次，沿用现有前向管线路由（`ConfigureMeshPipeline(transparent=true)`）。
- **Scene2D / UIPass**：零改动。视口颜色与深度仍是原来那两张外部资源。

委托给 Scene 的采集 API（`BeginScene / DrawMesh / EndScene`）完全不变。

## 4. 两个必须先补的前置缺口

### 4.1 GBuffer 纹理从哪来（RenderGraph 虚拟资源尚未实现）

`CreateVirtualResource` v1 只登记描述，不分配 GPU 内存，执行期对非 external
资源直接跳过。GBuffer 是帧内瞬态资源，理想归宿是渲染图虚拟资源分配（渲染图
计划书的阶段 2），但那是一次独立的基建工程，不应阻塞延迟渲染落地。

**决策：阶段 1 用持久 GBuffer 纹理 + 每帧 Import**（方案 b）：

- 新建 `GBuffer`（或并入 Renderer3D）管理类，仿照 `SceneViewport`
  （`GE_Editor/src/SceneViewport.h:23`）的模式：持有 3 张离屏图 + view，
  `Prepare(device, extent)` 惰性创建、尺寸变化时重建；
- SceneLayer 每帧 `b.Import(&view)` 三张 GBuffer view —— 与现在 Import
  ViewportColor/Depth 同一模式，屏障布局记忆经 VulkanImage 跨帧承载，零新增图逻辑；
- 代价是 3 张纹理常驻（约 28B/px，见 §5.2）且不做别名/复用 —— 可接受，
  后续渲染图阶段 2 实现虚拟资源后再迁入。

### 4.2 PassExecuteContext 不支持 MRT

`ctx.colorAttachmentView` 只有首个颜色附件（`RenderPassDesc.h:84`，
`RenderGraph.cpp:402-420`），而 GBuffer 管线创建需要**全部**附件格式
（`setRenderingFormats` 收 vector）。改动：

- `PassExecuteContext` 增加 `std::vector<VulkanImageView *> colorAttachmentViews;`
  （填充全部颜色附件视图，与现有单视图字段并存过渡）；
- `RenderGraph::Execute` 组装 rinfo 时顺带填充；
- GBuffer 录制路径从该字段取全部格式；现有 Renderer3D/Renderer2D 用首视图的
  代码可保持不动。

## 5. 设计

### 5.1 GBuffer 布局（4 附件，28 B/px + 深度）

| 附件 | 格式 | R | G | B | A | 清屏值 |
|---|---|---|---|---|---|---|
| G0 | RGBA8_UNORM | albedo.r | albedo.g | albedo.b | **着色模型标志**（0=天空哨兵，1/255=Blinn-Phong，2/255=PBR） | (0,0,0,0) |
| G1 | RGBA16F | worldNormal.x | .y | .z | 预留（AO） | (0,0,0,0) |
| G2 | RGBA16F | worldPos.x | .y | .z | scalarA：PBR=roughness / BP=shininess | (0,0,0,0) |
| G3 | RGBA16F | emissive.r | .g | .b | scalarB：PBR=metallic / BP=specularStrength | (0,0,0,0) |
| 深度 | 复用视口深度图（D32 一类，不变） | | | | | 清屏 1.0 |

要点：

- **albedo 存线性 UNORM**（不是 sRGB 附件）：GBuffer 片元里 texture 采样已被
  硬件解码到线性，tint 相乘后写入线性值；Lighting 读回直接用，避免双重解码。
- **法线是世界空间、已含法线贴图扰动**（GBuffer 期做 TBN 变换，光照期拿到
  即用），与现有 `mesh_pbr.frag:183-186` 的计算完全一致，只是换了执行时机。
- **自发光在 GBuffer 期算完**：`emissiveTexture.rgb × emissiveFactor.rgb`
  （`mesh_pbr.frag:237` 的乘积前移），Lighting 期直接加色。
- **Blinn-Phong 与 PBR 双分支靠标志 + 两个标量槽**：两套光照模型各需两个标量
  （BP: shininess/specularStrength；PBR: roughness/metallic），共用 G2.w/G3.w，
  按标志选择语义。RGBA16F 对 shininess 原值存储无精度问题。
- **天空哨兵 = G0.a == 0**：GBuffer 清屏 (0,0,0,0)，几何像素恒写标志 ≥ 1/255。
  Lighting 判 `a < 0.5/255` 走天空分支（unorm 量化误差安全余量）。
- 4 附件 ≤ Vulkan 保证的 `maxColorAttachments` 下限 4，老设备贴边但合规；
  桌面普遍 8。带宽写+读各 28B/px，1080p 每帧约 115MB 往返，可接受。

### 5.2 Lighting Pass

全屏三角形（无顶点缓冲，参考 `skybox.vert` 的反投影方案）：

- **天空分支**（G0.a == 0）：invView/invProj 重建视线方向，采样等距柱状全景图
  （`EnvironmentMap::GetSkybox()`），**直接输出、不 tonemap** —— 保持现状语义
  （原 DrawSkybox 是深度测试关的背景三角形，延迟下没有"先画"的时机，并入光照
  分支是自然归宿）。`m_SkyboxEnabled == false` 时输出 clearColor。
- **几何分支**：读 G0~G3 → 移植 `mesh_pbr.frag` 的 Cook-Torrance 数学
  （`calcDirectLight / calcDirectionalLight / calcPointLight`，:99-169），
  按 G0.a 标志选 PBR 或 Blinn-Phong 光照，加常量环境光与自发光，尾部 ACES
  （`acesToneMap`，:88-91）→ 输出。
  行为等价性：BRDF 数学逐行照搬，不透明画面应与前向基本逐像素一致。
- 常量环境光放 Lighting UBO（新结构：invView/invProj/clearColor + FrameUBO 的
  光照字段裁剪版）；点光源 SSBO 布局复用 `LightGPU`（32B 不变）。
- **IBL 延迟光照不做**（阶段 2）：PBR 环境光暂用常量环境光近似，`HAS_IBL`
  变体仍只在透明前向管线生效。文档记录此已知差异。

### 5.3 Transparent Pass（透明混合管线保留）

透明段逐像素光照在半透明混合下做延迟重建代价高且混合序无法批次化，业界通行
做法就是混合管线并存。本引擎透明段已具备：远→近排序（SortKey depthBits 取反）、
逐实例成批、混合附件状态、深度写关（`Renderer3D.cpp:539-548`）—— 全部复用：

- 批次：排序后首个 Blend 批次之后的段（现有切分逻辑原样）；
- 管线：现有 BlinnPhong/PBR/IBL/蒙皮前向管线不动；
- 附件：颜色 eLoad + 深度 eLoad（遮挡正确），混合与深度写状态由
  `ConfigureMeshPipeline(transparent=true)` 预置（现状不变）。

### 5.4 渲染图屏障核对（预期零改动，RenderDoc 复核一次）

现有推导（`RenderGraph.cpp:259-507`）对延迟链的关键转换：

| 转换 | 触发声明 | 推导结果 |
|---|---|---|
| G0~G3: ColorAttachment → ShaderReadOnly | GBuffer pass 写，Lighting `readImages` 读 | 写 ColorAttachmentOutput → 读 FragmentShader，布局转换，✅ |
| 视口颜色: Lighting 写 → Transparent 附件写 | 双方均 ColorAttachment 用法 | 同布局仅内存排序屏障，✅ |
| 深度: GBuffer 写 → Transparent/Scene2D 附件读 | 均为 DepthStencilAttachment | Early/Late 阶段屏障，✅ |
| 视口颜色 finalLayout = ShaderReadOnly | Scene2D 已声明 | 收尾转换已有（:453-506），✅ |

### 5.5 前向回退开关

`Renderer3D` 增加 `SetDeferred(bool)`（默认 false）。SceneLayer 按开关声明
单 pass 前向链（现状）或三 pass 延迟链。价值：调试对比、RenderDoc A/B、
异常时立即回退。

## 7. Renderer3D 内部拆分

```
FlushScene(ctx)                    现状（前向路径保留，整体不动）
  └ SortMeshes → 上传 → 天空盒 → 不透明段 → 透明段 → clear

FlushGBuffer(ctx)                  [延迟] GBuffer pass 回调
  ├ FlushRetiredEnvironments / SortMeshes / CollectBatches
  ├ 上传 FrameUBO + instance SSBO（lights 不需要），缓存到成员
  ├ 切分批次（首个 Blend 批次），缓存两段批次到成员
  └ ConfigureGBufferPipeline（MRT 4 格式取 ctx.colorAttachmentViews）
     → 录制不透明段（gbuffer 管线路由：PBR 位 + 蒙皮位，动态 cull 复用）
  （不清 m_Meshes —— 透明 pass 还要用）

FlushLighting(ctx)                 [延迟] Lighting pass 回调
  └ 全屏三角形：绑定 LightingUBO + lights SSBO + G0~G3 + 全景图
     （天空分支/几何分支在 shader 内）

FlushTransparent(ctx)              [延迟] Transparent pass 回调
  ├ 取缓存的透明段批次 + 已上传 buffers（同帧帧池仍有效）
  └ ConfigureMeshPipeline(transparent=true) → DrawMeshInstances（现状逻辑）
  └ 消费完：m_Meshes.clear() + 清缓存（替代原 :490 的清空时机）
```

边界情形：

- 空场景 / 全不透明：GBuffer 照常清屏，Lighting 全屏输出天空/clearColor，
  Transparent 无批次空过；
- 全透明场景：GBuffer 无批次但深度/附件仍清屏，Lighting 输出背景后透明段叠加；
- `m_Meshes` 的清空从 FlushScene 尾部（:490）移到 FlushTransparent 尾部，
  防止"GBuffer pass 消费后透明 pass 拿到空队列"。

## 8. 实施步骤（每步可独立构建验证）

**S1 基础设施（无视觉变化）**
PassExecuteContext 加 `colorAttachmentViews` 并在 Execute 填充；新建 GBuffer
管理类；Renderer3D 加 `m_Deferred` 开关与三个 Flush 函数占位（延迟路径暂时
仍走 FlushScene）。验收：前向画面零变化，验证层无报错。

**S2 GBuffer Pass**
写 `mesh_gbuffer.frag`；实现 FlushGBuffer（排序/合批/上传/不透明段 + GBuffer
管线路由，含蒙皮与动态剔除）；SceneLayer 延迟模式下声明 GBuffer pass（此时
Lighting/Transparent 还没接，可临时让 Lighting 之前用前向单 pass 对照）。
验收：RenderDoc 检查 4 张附件内容正确（albedo/法线/位置/自发光+标志），
MASK discard、doubleSided、蒙皮均正确落盘。

**S3 Lighting Pass**
写 `deferred_lighting.vert/.frag`；实现 FlushLighting + LightingUBO；
SceneLayer 声明 Lighting pass（读 G0~G3，写视口颜色 eClear）。天空分支一并做
（等距全景采样、不 tonemap、开关关闭时输出 clearColor）。
验收：不透明画面与前向逐像素基本一致；天空盒开关两态正确；无天空盒时背景色正确。

**S4 Transparent 接线**
FlushTransparent + 批次缓存生命周期调整；SceneLayer 声明 TransparentPass。
验收：透明物体正确叠在光照结果上、深度遮挡正确、远→近序不变；
蒙皮/双面透明物体正常。

**S5 开关收尾与回归**
SceneLayer 按开关分派两条链；RenderStatsPanel 展示延迟链统计（可选）；
全量回归：glTF 蒙皮模型、透明材质集、MASK/双面、天空盒开关、视口 resize
（GBuffer 重建 + 限流）、RenderDoc 帧捕获对比两模式。
验收：`SetDeferred` 双向切换均正确，验证层零报错。

## 9. 风险与注意

1. **G0.a 哨兵的 unorm 量化**：写 `n/255.0`，读回有 ±0.5/255 误差，判断用
   `< 0.5/255` 阈值而非 `== 0`。
2. **worldPos 用 RGBA16F 的精度**：常规场景（< 数百单位）亚毫米级，够用；
   大世界场景将来换深度重建（需 Lighting 采样深度图）或 RGBA32F，本文不展开。
3. **透明混合发生在 ACES 之后**：延迟下不透明结果已 tonemap，透明前向管线
   自身也 tonemap 后再混合 —— 与前向现状行为一致（前向同样是各自 tonemap 后
   混合），非回归，记录为已知妥协。
4. **4 附件贴 Vulkan 保证下限**：`maxColorAttachments` 最小保证恰为 4，老设备
   可用但无余量；如需 5 附件（独立 AO 槽）需运行时查上限。
5. **GBuffer 重建与视口限流**：沿用 SceneLayer 现有 0.25s 限流（SceneLayer.cpp:184-188），
   GBuffer.Prepare 内部对尺寸无变化直接跳过。
6. **调试体验**：图/pass/资源 debug name 全链路已具备，RenderDoc 中
   GBuffer/Lighting/Transparent 按名可查；哨兵与标量槽建议在计划落地时同步写
   进 shader 注释。

## 10. 后续阶段（本计划书不做）

- **IBL 延迟光照**：Lighting 分支接入 irradiance/prefilter/BRDF LUT 三件套
  （数据已由 EnvironmentMap 持有，纯 shader 工作）；
- **HDR 中间缓冲**：Lighting 输出 RGBA16F + 独立 tonemap pass，为 bloom/曝光
  铺路（同时解决 §9.3 的妥协）；
