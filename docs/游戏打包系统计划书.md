# 游戏打包系统计划书

> 状态：**计划中（未开工）**
> 目标：让引擎能把一个（或多个）`.scene` 连同它依赖的全部资产，产出一份**可脱离开发机、脱离仓库目录结构**独立运行的发行版。落地顺序：运行时播放器 exe → 资产路径决定论 → 依赖收集与打包 CLI → 编辑器内一键构建；进阶再做单文件 `.gepak` 资源包与虚拟文件系统。
> 前置：现状——`GE_Editor` 是**唯一**的可视化 exe（另一个 `gemesh` 是离线转换工具，`CMakeLists.txt:252` / `:268`），不存在"游戏可执行文件"；资产根是写死的相对字符串 `"assets"`（`AssetManager.h:183`），`SetAssetRoot()` 有定义但**全仓库零调用**，实际路径按**进程工作目录**解析；场景文件里混着四种路径形态，还有指向**仓库外**的引用（`2.scene:264` 指向 `C:\Users\Lenovo\Desktop\models\shayv\...`）。
> 关联：`项目架构总览.md`、`计算管线实现计划书.md`（离线 CLI 目标的组织方式可参考）、`FollowCamera第三人称相机计划书.md`（运行时相机层可直接复用）

## 0. 一句话架构

```
   编辑器内「构建」──┐
   或命令行直接调    ├──► gepack (CLI)
                    │      1. 读入口 .scene
                    │      2. 走依赖图 → 收集资产清单
                    │      3. 校验：绝对路径 / 缺失 / 未烘焙 / 越界引用
                    │      4. 拷贝到 <输出>/assets + 写 manifest.json
                    └──────────────────────┬───────────────────────
                                           ▼
                    <输出>/                          ← 整个文件夹拷走即可运行
                      ├─ GE_Runtime.exe             ← 阶段 B 新增的播放器
                      ├─ *.dll                      ← VC 运行时（/MD）
                      ├─ game.cfg                   ← 入口场景 / 窗口 / 图标
                      ├─ manifest.json              ← 资产清单 + 引擎版本 + 校验和
                      └─ assets/                    ← 只含被引用到的资产
```

**关键约束**：打包的正确性建立在**路径决定论**上——同一份发行版，放在任意目录、以任意工作目录启动，都必须解析到同样的资产。当前引擎两条都不满足（根按 CWD 解析 + 场景内嵌绝对路径），所以**阶段 A 是一切的前提，不能跳**。阶段 A 独立交付的价值也足够明显：把 `bin/` 和 `assets/` 一起拷到别处就能跑，不再要求"必须从仓库根启动"。

## 3. 阶段 A：资产根决定论 + 路径规范形

### 3.1 资产根：从"工作目录"改到"可执行文件目录"

`AssetManager` 已有 `SetAssetRoot()`（`AssetManager.cpp:38`）但从未被调用，根固定为 `"assets"`。而 `CMAKE_RUNTIME_OUTPUT_DIRECTORY = ${CMAKE_SOURCE_DIR}/bin`（`CMakeLists.txt:16-19`），`bin/` 下**没有** `assets/`，`build.bat` 也不拷贝 assets——所以现在**只有从仓库根启动才能跑**，从 `bin/` 启动全部资产路径失效。

改动：

1. 新增 `PlatformUtils::GetExecutableDirectory()`（放 `GE/include/GE/Platform/Windows/WindowsPlatformUtils.h`，实现走 `GetModuleFileNameW`；非 Windows 分支后续补）。
2. `Application` 构造函数内**在构造 `Renderer` 之前**完成根决策，并把结果**注入 `Renderer` 构造函数**：

```cpp
// 优先 exe 同级 assets（发行版布局）；不存在则回退 CWD/assets（开发期从仓库根启动）
std::filesystem::path root = PlatformUtils::GetExecutableDirectory() / "assets";
if (!std::filesystem::exists(root))
    root = std::filesystem::current_path() / "assets";   // 开发回退
m_Renderer = std::make_unique<Renderer>(*m_Window, root);   // 注入，而非构造后设置
```

> **为什么必须注入构造函数（实现时修正）**：本文初稿判断"构造后再 `SetAssetRoot` 即可，中间窗口期足够安全"，**该判断不成立**。`Renderer` 构造的最后一步会 `ImGuiLayer::OnAttach()`（`Renderer.cpp:64-65`），而它立刻用资源根解析字体（`ImGuiLayer.cpp:41-42` 取 `AssetPaths::Fonts + "/OpenSans-Regular.ttf"`）。构造函数返回时字体已加载完毕，此后设置资源根已太晚。故 `Renderer` 构造函数签名加一个 `assetRoot` 参数，在创建 `AssetManager` 之后、ImGui 初始化之前调用 `SetAssetRoot`。`Renderer` 全仓库只有 `Application.cpp` 一处实例化，改动收敛。

3. 同时修掉两处**绕过 `ResolvePath` 的硬编码根**：
   - Lua 脚本目录：`ScriptEngine.Init(this, "assets/scripts")` 写死在 `Scene.cpp:282`，改为 `AssetPaths::Scripts` 拼资源根（或新增 `AssetPaths::Scripts` 常量，与 `AssetManager.h` 的 `AssetPaths` 命名空间并列）。
   - 文件对话框初始目录：`FileDialogs::OpenFile(filter, "assets/scenes")` 写死在 `SceneLayer.cpp:1196`（实现 `WindowsPlatformUtils.cpp:14`），改为由资源根拼出。

**验收**：把 `bin/`（exe + 依赖）与 `assets/` 并排放进 `D:\test_dist\`，从 `C:\` 作为工作目录启动 `D:\test_dist\GE_Editor.exe`，默认场景 `2.scene` 正常加载、贴图/音频/脚本齐全。当前**必定失败**，这是阶段 A 的核心验收点。

### 3.2 路径规范形

定义**唯一规范形**（写入新的 `GE/include/GE/Render/AssetPathUtil.h`）：

- **资产引用** = `<相对资源根>/<子路径>`，**正斜杠**，**无 `assets/` 前缀**，**无盘符**，不含 `.`/`..`（`lexically_normal` 后）。
- **伪键** `builtin:*` / `solid:*` 原样保留，不参与文件解析（沿 `AssetManager.cpp:49` 现有语义）。
- **例外**：`ScriptPath` 保持"相对 `assets/scripts`"（现语义，是独立挂载点，不改以免动序列化语义），但在校验阶段一并检查。

三个函数：

```cpp
namespace AssetPathUtil {
    // 绝对/带前缀/带反斜杠 → 规范形；无法归一到根内时返回空 optional（校验报错用）
    std::optional<std::string> ToCanonical(const std::string &raw,
                                           const std::filesystem::path &assetRoot);
    // 规范形 → 绝对路径（= ResolvePath，交由 AssetManager 做）
    bool IsPseudoKey(const std::string &p);          // builtin: / solid:
    bool IsUnderRoot(const std::filesystem::path &abs, const std::filesystem::path &root);
}
```

### 3.3 加载期自愈（向后兼容旧场景）

`ResolvePath`（`AssetManager.cpp:43-66`）当前对绝对路径**直接返回**（`p.is_absolute() → p.lexically_normal()`）——这正是旧场景能带病运行的原因。改为：

- 绝对路径**若在资源根之下** → 转成规范形再解析（相对化）。这样 `2.scene:62` 的 `F:\...\assets\textures\Checkerboard.png` 无需改文件即可正确加载，且**换机器仍有救**（只要资产在包内相对位置一致）。
- 绝对路径**若在资源根之外** → 记一条 `GE_CORE_ERROR`（含原始串与场景文件提示），返回原路径。**这是打包校验必须拦下的情况**，见 §5.3。
- **唯一绕过 `ResolvePath` 的资产消费者已在本次一并接上**：`AnimationClipManager::LoadByKey` 把源键的文件路径部分直接喂给 `GLTF::LoadModel`（`AnimationClipManager.cpp:131-138`），不经资源根；且 `.geanim` 烘焙产物路径由该键派生，落点也跟着错。若不修，`Clip:` 一旦归一成相对路径，发行版就读不到模型。现改为在 `LoadByKey` 内先 `ResolvePath`。其余消费者（网格/纹理/声音）本就走 `AssetManager::LoadMesh / LoadTextureAsync / LoadSound`，天然解析——**这条是排查"还有谁没走资源根"时的通用检查方法**：看它是否经 `Renderer::GetAssetManager()`。
- 新增"根内绝对路径 → 规范形"的**写回**：见下。

### 3.4 序列化归一（治本）

`SceneSerializer::Serialize` 在写每个资产引用前统一过 `ToCanonical`，把绝对路径/带前缀形态落成规范形。这样打开一次旧场景再保存，脏路径即被洗净——是成本最低的批量迁移手段。

**涉及文件**：`GE/include/GE/Platform/Windows/WindowsPlatformUtils.h`（实际落在 `GE/include/GE/Utils/PlatformUtils.h`）、`GE/src/Platform/Windows/WindowsPlatformUtils.cpp`、`GE/src/Core/Application.cpp`、`GE/include/GE/Render/Renderer.h`、`GE/src/Render/Renderer.cpp`、`GE/src/Render/AssetManager.cpp`、`GE/include/GE/Render/AssetManager.h`、新增 `GE/include/GE/Render/AssetPathUtil.h`（+ 可选 .cpp）、`GE/src/Scene/SceneSerializer.cpp`、`GE/src/Scene/Scene.cpp`、`GE/src/Animation/AnimationClipManager.cpp`、`GE_Editor/src/SceneLayer.cpp`。

### 3.5 验收

- §3.1 的跨目录/跨工作目录启动通过。
- 载入 `2.scene`（含 5 处绝对路径 + 2 处根外引用），根内引用全部命中；根外引用在日志里有明确 ERROR，不静默失败。
- 另存为 `2_canonical.scene`，grep 确认新文件中**零**盘符、零 `assets/` 前缀（`builtin:`/`solid:` 除外）；重新加载该文件表现与原文一致。

## 4. 阶段 B：运行时播放器 `GE_Runtime`

### 4.1 为什么必须新增 exe

打包的产物不应包含编辑器。`GE_Editor` 挂着 DockSpace、层级面板、资源面板、ASM 图、Gizmo、Stats 等一大堆编辑器层（`EditorApp.cpp:16-42` 一次性 push 了 7 个 layer），既臃肿又暴露编辑器 UI。引擎已有干净的入口抽象：`EntryPoint.h:10-19` 生成 `main()`，各 exe 只需定义 `CreateApplication`（编辑器版在 `EditorApp.cpp:47`）。

新增 target `GE_Runtime`（`CMakeLists.txt` 追加，参照 `:227-259` 的 `Editor_SRC` 写法），源码放 `GE_Runtime/src/`：

- `RuntimeApp.cpp`：`RuntimeApp : Application`，只 push **一个** `GameLayer`，并定义 `CreateApplication`。
- `GameLayer.cpp/.h`：非编辑器游戏层——加载入口场景、驱动游戏相机、处理输入、无 ImGui 面板。

### 4.2 启动配置 `game.cfg`

发行版根目录放一份 YAML（复用已链接的 yaml-cpp），`GameLayer::OnAttach` 读取：

```yaml
# game.cfg
scene: scenes/2.scene        # 相对资源根，规范形
window:
  title: "我的游戏"
  width: 1600
  height: 900
  vsync: true
  fullscreen: false
rendering:
  tonemap: true
  bloom: true
  culling: true
environment: environments/DayEnvironmentHDRI107_4K   # IBL 是运行时固定集合，不在场景里
```

**命令行覆盖**（`ApplicationCommandLineArgs` 已在 `Application.h:23-31` 备好、经 `GetCommandLineArgs()` 可取，但当前**全仓库无人读 `Args[1]`**）：

```
GE_Runtime.exe [--scene <规范形路径>] [--fullscreen] [--editor-camera]
```

`--scene` 覆盖 `game.cfg`，是"编辑器里点运行 → 立刻看效果"的最短回环（见 §7）。

### 4.3 与编辑器共享启动逻辑（防漂移）

窗口 / 音频 / `Renderer` / ImGui 的初始化都在 `Application` 基类里（`Application.cpp:25-53`），`RuntimeApp` 直接继承即可复用。**唯一需要抽出来共享的是"从文件加载场景"**：现在该逻辑长在 `SceneLayer::OnAttach`（`SceneLayer.cpp:94-120`）里，与编辑器状态恢复混在一起。建议把"解析入口场景路径 → `SceneSerializer::Deserialize`"提炼为 `Scene::LoadFromFile(path)` 之上的一个薄函数（`SceneLoader::LoadEntryScene`），编辑器与运行时各自调用，避免两份加载逻辑各自演化。

> **相机**：`FollowCamera第三人称相机计划书.md` 里的相机若已落地，`GameLayer` 直接复用；否则先用现有的 `Camera` 自由视角，不阻塞本阶段。

### 4.4 验收

- 命令行 `bin\GE_Runtime.exe --scene scenes/2.scene` 能起窗口、加载场景、按 `game.cfg` 的渲染开关出图，无任何编辑器 UI。
- `--fullscreen` / `--scene` 覆盖生效；未知参数打 WARN 不崩。
- 与编辑器同场景对比：模型、材质、光照、音频、脚本行为一致（脚本系统在运行时同样初始化）。

**涉及文件**：`CMakeLists.txt`、新增 `GE_Runtime/src/RuntimeApp.cpp`、`GE_Runtime/src/GameLayer.cpp`、`GE_Runtime/src/GameLayer.h`、`GE_Editor/src/EditorApp.cpp`（仅当抽取共享加载函数时）、`GE/src/Scene/*`（共享 `SceneLoader`）。

## 5. 阶段 C：依赖收集 + 打包 CLI `gepack`

### 5.1 目标与形态

新增 CLI target `gepack`（`CMakeLists.txt` 追加，参照 `:262-273` 的 `gemesh` 写法：链接 `${GE_NAME}`，复用引擎的 `SceneSerializer` 与各 Manager 来读场景，**不重复实现一套解析**）。

```
gepack --project game.cfg --config release --out dist/ [--strict] [--pack]
```

职责：读入口场景 → 依赖图 walk → 校验 → 拷贝 → 写 manifest。

### 5.2 依赖图：边的定义

场景里的资产引用形态已由 `SceneSerializer` 读写两端确定，逐条列明收集规则：

| 源字段 | 序列化位置 | 反序列化/加载 | 收集动作 |
|---|---|---|---|
| `MeshRenderer.Mesh` | `SceneSerializer.cpp:774-779` | `:1402-1405` → `LoadMesh` | 若 `builtin:*` 跳过；否则收 `.gemesh`（若仍是 `.obj`/`.gltf` 先走烘焙，见 §5.4） |
| 精灵 `SpriteTexture` | `:759-764` | `:1385-1391` | 收纹理（`.png`/`.jpg`/`.ktx2`） |
| 材质覆写（内联形态） | `SceneSerializer.cpp` `SerializeMaterialNode` → `MaterialSerializer::WriteMaterialNode` | `DeserializeMaterialNode` → `MaterialSerializer::ApplyMaterialNode` | 收该节点的 Albedo/Normal/MetallicRoughness/Emissive 四槽贴图 |
| 材质覆写（引用形态） | `SceneSerializer.cpp` 覆写写出端：材质有源文件时只写 `Material: materials/x.gemat` | `AssetManager::LoadMaterial` → `MaterialManager::Load` | **先把 `.gemat` 收进来，再按它各槽贴图收纹理**（见下注） |
| `Audio.SoundPath` | `:870` | `:1514`，实际加载 `AudioWorld.cpp:434` | 收音频（`.wav`/`.mp3`） |
| `Script.ScriptPath` | `:1074` | `:1765` | 见 §5.3 的 Lua 闭包问题 |
| 动画 `Clips` | `:709` 附近 | `AnimationClipLoader.cpp:112/:154` | 收 `.geanim`（或其源 glTF + 骨骼链） |
| 环境 / IBL | 不在场景里 | `Renderer3D_Lifecycle.cpp:425,449-451` | 由 `game.cfg` 的 `environment` 显式指定 |
| 字体 | 不在场景里 | ImGui 字体 | 固定收（体积小） |
| 着色器 | **不在场景里** | `Renderer3D_Lifecycle.cpp` **30 处** + `Renderer2D.cpp:41,48` 写死文件名 | 固定收（见下） |

> **`.gemat` 必须递归展开。** 材质改为可独立落盘后，一个材质的贴图引用可能**只存在于 `.gemat` 文件里**——场景文件里只看得到一行 `Material: materials/x.gemat`。收集器必须把 `.gemat` 当节点读开，再按其各槽贴图收纹理；只扫场景会漏掉这些贴图。
>
> **本表的行号引用已随重构漂移**（材质序列化整体抽出到 `Render/MaterialSerializer.*`，`SceneSerializer.cpp` 内位置也变过）。**以符号名为准，行号只作线索**；后续宜逐步换成符号名引用。

**两个"不在场景里"的特例必须显式处理**：

1. **着色器按文件名写死在代码里**（30 处 `ResolvePath(AssetPaths::Shaders + "/xxx.vert.spv")`），场景不引用它们，依赖图无法发现。初版策略：**全量收 `assets/shaders/glsl/*.spv`**（体量小，当前约 60 个，安全优先）。运行期只需 `.spv`，`.glsl` 源文件不必打包（`ShaderSource` 读的也是 `.spv` 路径）。后续可做"按渲染特性裁剪"作为体积优化。
2. **IBL 环境**由编辑器设置选择，不在场景里 → 由 `game.cfg` 显式声明（§4.2）。注意 `assets/environments/<env>/` 下 `source.exr` 与 `preview.png` 是**编辑期资产**，打包排除；运行时只需 `skybox.ktx2` + `prefilter.ktx`。`brdf_lut.png`（`assets/environments/` 根）为共享资产，固定收。

**排除项**（写在 `gepack` 的规则文件里，支持 glob）：`assets/Screenshot/`、`assets/shaders/**/*.glsl`、`assets/environments/**/source.exr`、`assets/environments/**/preview.png`、`assets/cache/`（实为空壳，无任何代码引用，见 §9.4）、`*.ilk`/`*.pdb`。

### 5.3 Lua 脚本闭包问题（必须正视）

脚本按 `ScriptPath` 能收到**入口文件**，但 Lua 的 `require` 会在运行期沿 `package.path`（`ScriptEngine.cpp:921-922`，根为硬编码的 `"assets/scripts"`）拉入任意依赖，**静态分析不可靠**。初版策略：**整个 `assets/scripts/` 目录全量打包**（脚本是文本，体积可忽略），并在 manifest 里标记为 `scripts: "whole-dir"`。等脚本规模上来再做 `require` 图扫描。

### 5.4 校验（`gepack` 最有价值的部分）

打包前扫一遍，问题分级输出：

| 级别 | 检查项 | 处理 |
|---|---|---|
| **Error** | 资产引用解析后落在资源根**之外**（如 `2.scene:264` 的 `C:\Users\...\Desktop\...`） | 列出文件:行 + 原始串，`--strict` 下构建失败 |
| **Error** | 引用的文件不存在 | 同上 |
| **Error** | 绝对路径**在根内但无法相对化**（如跨盘符） | 同上 |
| **Warn** | 网格仍是 `.obj`/`.gltf`（非 `.gemesh`） | 调既有的 `BakeSourceToGemesh`（`SceneSerializer.cpp:393`）/ `ResolveMeshSerializedPath`（`:460`）先烘焙再收 |
| **Warn** | 未使用资产（场景未引用） | 仅报告不剔除，避免误伤动态加载 |
| **Info** | 收集到的资产总数 / 总字节 / 按类型分布 | 打日志 |

> 遗留数据的处理建议：`2.scene:264,266` 与 `4.scene` 的根外引用，先在阶段 A 用 `ToCanonical` 报错定位，**人工把文件搬进 `assets/models/shayv/`** 后重新保存场景（`gepack` 不自动搬运，避免在打包工具里藏副作用）。

### 5.5 manifest

输出 `<out>/manifest.json`：

```json
{
  "formatVersion": 1,
  "engineVersion": "0.1.0",
  "builtAt": "<ISO8601，由调用方传入或工具内取>",
  "entryScene": "scenes/2.scene",
  "assets": [
    { "path": "textures/Checkerboard.png", "size": 12345, "sha256": "…" },
    { "path": "shaders/glsl/mesh.vert.spv", "size": 1024, "sha256": "…" }

```

用途：运行时启动自检（缺资产早失败）、增量打包（比 `sha256` 决定是否重拷）、以及阶段 D 的包索引来源。

### 5.6 验收

**涉及文件**：`CMakeLists.txt`、新增 `tools/gepack/gepack_main.cpp`、新增 `tools/gepack/Packager.cpp/.h`（依赖收集 + 拷贝）、新增 `tools/gepack/AssetDependencyGraph.cpp/.h`、新增 `tools/gepack/gepack_rules.yaml`。

## 6. 阶段 D（可选）：单文件资源包 `.gepak` + 虚拟文件系统

> **明确说明**：阶段 A–C 做完就已经"能发布"（一个文件夹）。本阶段解决的是**单文件分发**、轻微防篡改、以及"海量小文件拷贝慢"的问题。**不是必需的**，慎开工。

### 6.1 格式

```
.gepak
├─ Header   : magic "GEPK" + formatVersion + entryCount + indexOffset + indexSize
├─ Entries  : 逐条原始字节（可选 LZ4/deflate 压缩）
└─ Index    : entryCount × { pathHash | path | offset | size | rawSize | flags }
```

初版不加密（若后续需要，就是在 entry 层加一层对称变换——**只留接缝，不先实现**）。索引常驻内存，支持 `ReadFile(name) → std::vector<byte>`。

### 6.2 VFS 层（本阶段的主要工作量）

当前引擎**没有 I/O 抽象**：`FileSystem.h` 全部内容只有一个 `ReadBinaryU32`（唯一消费者 `VulkanShaderModule.cpp:73`），其余约 20 处 loader 各自直接开文件：

| loader | 当前调用 | 迁移目标（内存变体，均已存在） |
|---|---|---|
| stb 图像 | `stbi_load`（`Texture.cpp:385,589`） | `stbi_load_from_memory` |
| KTX | `ktxTexture_CreateFromNamedFile`（`Texture.cpp:309,422,559,809`） | `ktxTexture_CreateFromMemory` |
| tinygltf | `LoadBinaryFromFile`（`GLTFLoader.cpp:389,391`） | `LoadBinaryFromMemory` |
| tinyobj | `LoadObj`（`OBJLoader.cpp:37`） | istream 重载 |
| miniaudio | `ma_decoder_init_file`（`SoundAsset.cpp:22`） | `ma_decoder_init_memory` |
| yaml-cpp | `YAML::LoadFile`（`SceneSerializer.cpp:1279`） | `YAML::Load(std::string)` |
| 自研二进制 | `std::ifstream`（`GEMeshLoader.cpp:393,416`、`AnimationClipLoader.cpp:134,155`、`FileSystem.cpp:10`） | 走 VFS |
| Lua | `ReadFileContents`（`ScriptEngine.cpp:117`）+ `require` 的 `package.path` | 走 VFS **并需自定义 Lua searcher**（见风险 §8.2） |

设计：

```cpp
// GE/include/GE/FileSystem/VirtualFileSystem.h
class VirtualFileSystem {
public:
    static bool MountPack(const std::filesystem::path &pak);   // 挂载 .gepak
    static void UnmountAll();
    static bool Exists(const std::string &assetRelPath);
    static std::optional<std::vector<char>> ReadBinary(const std::string &p);
    static std::optional<std::string>       ReadText(const std::string &p);
    // 未挂载 pak 时天然回退真实文件系统 → 开发期零感知
};
```

**关键设计点**：`ReadBinary/ReadText` 在**未挂载任何 pak** 时直接走真实 FS。这样开发期（编辑器、`--scene` 回环）完全不受影响，VFS 成为纯粹的发行期加速层——这是本阶段能低风险推进的核心。

### 6.3 验收

- 不打 pak（开发期）：编辑器与运行时行为与阶段 C 完全一致（回归零差异）。
- `gepack --pack` 产出单个 `assets.gepak` + 不带 `assets/` 目录的 `dist/`，运行时能完整加载场景（模型/贴图/音频/脚本/着色器全通）。
- 加载耗时对比：小文件多的场景（如 `shayv` 模型目录）打成单包后启动应更快。

**涉及文件**：新增 `GE/include/GE/FileSystem/VirtualFileSystem.h`、`GE/src/FileSystem/VirtualFileSystem.cpp`、新增 `GE/include/GE/FileSystem/AssetPack.h`、`GE/src/FileSystem/AssetPack.cpp`，以及上表全部 loader 的调用点。

## 9. 风险与开放问题

1. **根外引用是遗留数据债，不是代码问题**：`2.scene:264,266` 指向 `C:\Users\Lenovo\Desktop\models\shayv\*.gltf`，`4.scene` 与 `2.scene` 另有多处根内绝对路径。代码侧只能"报错 + 自愈根内那条"，**根外那两条必须人工把文件搬进 `assets/` 后重新保存场景**。建议阶段 A 一落地就先跑一遍 `gepack --dry-run` 把清单拉全，别等到发布前才发现。

2. **Lua `require` 闭包静态收集不可靠**：`package.path` 是运行期机制（`ScriptEngine.cpp:921-922`），任何静态扫描都会漏。初版全量打包 `assets/scripts/` 规避；阶段 D 引入 VFS 后，Lua 的 `require` 会绕过 VFS 直接命中真实文件系统，**必须补一个自定义 Lua searcher** 从 VFS 读，否则打成 pak 后脚本全失效。这是阶段 D 最容易被漏掉的一处。

3. **着色器与场景解耦**：30 处硬编码文件名（`Renderer3D_Lifecycle.cpp`），依赖图看不见。全量收录是当前唯一稳妥解；若日后要做体积裁剪，得先把这批字符串改成一份集中的"管线→着色器"表（这本身是个值得独立做的小重构，但**不要和打包捆在一个阶段里**）。

4. **`assets/cache/` 是空壳**：只有空的 `assets/cache/shader/opengl/` 目录，全仓库零引用（grep `assets/cache`/`ShaderCache` 无命中）。打包直接排除；它原本大概是想做着色器缓存但没落地——**别误以为是可用的缓存机制**。

5. **`.gemesh` 是否自包含需在实现时确认**：`GEMeshLoader.cpp:414` 的 `ParseGEMesh` 若引用了外部贴图/附属文件，依赖图要多一条边。当前假设自包含，**阶段 C 开工第一件事就是验证这一点**（拿 `people.gemesh` 单独移出目录加载）。

6. **`.geanim` 与源 glTF 的关系**：场景里 `Clips` 存的是 `people.gltf#0` 这类源路径（`AnimationClipLoader.cpp:271-273` 会派生出同名 `.geanim`），但运行期实际读的是哪一个分支需确认——若读 `.geanim`，则依赖图要收派生的 `.geanim` 而非源 `.gltf`。同 §5.2 表格里标了"待确认"。

7. **编辑器/运行时启动逻辑漂移**：`RuntimeApp` 与 `EditorApp` 共享 `Application` 基类，但"加载入口场景"若各写一份，迟早不一致。§4.3 抽出 `SceneLoader::LoadEntryScene` 共享是低成本的预防。

8. **`GE_EDITOR_BUILD_SCENE_FROM_CODE` 编译开关**（`SceneLayer.cpp:41`、`:103`）：这是程序化建场景的开发开关，与"从文件加载"互斥。打包路径**必须**走文件加载分支，构建发行版时应断言该开关为 OFF，避免产出"没有场景文件依赖"的假通过。

9. **平台目标**：当前只有 Windows（`EntryPoint.h` 整个 `main` 包在 `#ifdef _WIN64` 里，`Platform/Windows/` 独占）。本计划只承诺 Windows；`GetExecutableDirectory` 等平台相关的点做条件编译预留，不做 Linux/macOS 实现。
