# 延迟渲染（Deferred Rendering）方案计划书

- 日期：2026-09-04
- 状态：待评审
- 涉及范围：`GE` 引擎模块（`GE/src/Render`、`GE/include/GE/Render`、`GE_Editor/src/SceneLayer.cpp`、`GE/src/Render/SceneRenderer`）、`assets/shaders/glsl/`

## 1. 背景与现状

### 1.1 目标

在现有**前向（Forward）单 Pass 直写颜色附件**的 3D 场景渲染之上，引入**延迟渲染**：把几何光照解耦为「GBuffer 几何 Pass（MRT 多目标写 G-Buffer）→ 光照 Pass（全屏采样 G-Buffer + 光参数）」。目标不是替换，而是**并存**——为后续点光源数量上升、光量级增长（编辑器场景点光源已可到数百个，见 `LightParams::pointLights` 无编译期上限设计）时提供不随光源数线性增加片段开销的光照路径。

### 1.2 现状渲染路径

编辑器场景渲染目前是**两段式前向**，编排点全部在 `GE_Editor/src/SceneLayer.cpp`：

```
SceneLayer::OnUpdate (SceneLayer.cpp:234-288) 每帧向 Renderer 托管的本帧帧图注册：
  Pass0 "Scene3D"   ── 颜色 eClear（暗底 0.1,0.1,0.15）+ 深度 eClear
                       execute → Renderer3D::FlushScene：DrawSkybox → ConfigureMeshPipeline
                                  → BindSharedUniforms → DrawMeshInstances
  Pass1 "Scene2D"   ── 颜色 eLoad + 深度 eLoad（读 Scene3D 深度做遮挡）
                       execute → Renderer2D::FlushScene：叠加世界/UI 精灵
                       finalLayout → eShaderReadOnlyOptimal（供 ImGui 采样上屏）
```

- `Renderer3D` 是「采集器」形态：`BeginScene` 收集批次到 `m_Meshes`，`EndScene` 只结束采集，命令录制延后到帧图 pass 的 execute 回调里调 `FlushScene`（Renderer3D.cpp:451-515）。
- `Renderer3D` 光照：**前向 Blinn-Phong + PBR(Cook-Torrance)**，一次 draw call 里既跑几何也跑光照；点光源经 `set 0 binding 1` SSBO 在片元里循环，光源数不设上限但**每像素 × 光源数**的复杂度天然随光源上升。
- 天空盒（`DrawSkybox`，Renderer3D.cpp:632）在 `RecordScene` 里**先于网格**作为背景绘制，关闭深度测试/写入。
- 光照数据集中在 `Renderer3D::LightParams`（方向光 + 点光源数组 + 环境光 + IBL 参数），全部经 `FrameUBO`/SSBO 一次性上传。

### 1.3 现有渲染图（RenderGraph）能力边界

本计划书依赖的渲染图是 `RenderGraph.h/.cpp` **当前已落地**的能力，逐条核对过：

| 能力 | 现状 | 对延迟渲染的意义 |
|---|---|---|
| `Import(VulkanImageView*)` 外部图 | 支持（RenderGraph.cpp:177） | 视口 RT 的 color/depth 已是外部图 |
| `AddPass` 声明序执行 | 支持，声明序即执行序（RenderGraph.cpp:200） | GBuffer → Lighting → Scene2D 依序注册 |
| **多颜色附件（MRT）** | 支持：`colorAttachments` 是 vector，Execute 逐个 AddColorAttachment（RenderGraph.cpp:299-301、400-414） | **GBuffer 三张图**同属一个 pass 的颜色附件 |
| 动态渲染 begin/end | 支持（RenderGraph.cpp:432-434） | 无需 render pass，MRT 直接可用 |
| 写后转读（finalLayout） | 支持（RenderGraph.cpp:436-495） | GBuffer 三张图写后 → ShaderReadOnlyOptimal |
| 深度保留 | 支持：同一资源多个 pass 读/写，跨 pass 屏障自动（RenderGraph.cpp:333-372） | GBuffer pass 写深度 → 光照/合成读深度 |
| 虚拟资源 | **仅登记不分配**（RenderGraph.cpp:191-198，计划书 §6「v1 不分配」） | **GBuffer 三张图需真实分配，本轮走 RenderTarget 而非虚拟资源** |

**关键边界**：RenderGraph 只编排同步、不分配图（计划书 §404「图只认 View / 虚拟句柄，不识别 RenderTarget」）。故 GBuffer 三张中间图本轮**不**用 `CreateVirtualResource`（它给不了真图），而由持有一个专用 `GBufferTarget`（详见 §3）经 `Import` 接入 —— 这是本计划与「等虚拟资源阶段2 落地」的主要取舍，见 §6.1。

### 1.4 业务方影响面

- 编辑器的 `SceneLayer`：目前是场景帧图**唯一编排者**。延迟渲染引入后场景 pass 数变多，若继续堆在 `SceneLayer` 会把「GBuffer 布局、光照 Pass、深度处理」的引擎着色知识固化在编辑器层，将来引擎侧真正运行时/游戏视口将无法复用。
- 引擎 `Renderer`：只编排 `UIPass`（写 swapchain），不涉及场景 pass；本轮**不动**。
- `Renderer3D`：需增加 GBuffer 输出变体（几何写 G-Buffer），同时保留前向路径（透明物体仍需前向，见 §3.4）。

## 2. 现状梳理结论

以下判断直接决定改动范围，实现前先确认（§5）：

1. **场景渲染编排应先下沉进引擎**：把「场景 pass 集合（GBuffer/Lighting/Scene2D）」从 `SceneLayer` 抽到新的引擎组件 `SceneRenderer`，由它持有 GBuffer 目标并向帧图 builder 注册场景 pass；`SceneLayer` 退化为只喂 Scene/相机/编辑或运行态。否则延迟 pass 会散落在编辑器层且引擎无法复用。
2. **GBuffer 本轮不依赖虚拟资源**：虚拟资源现仅登记不分配，故 GBuffer 用真实 `RenderTarget`（一组 3 色 + 1 深度）承载，经 Import 接入。等虚拟资源「阶段2」能真分配后再评估迁入（§6.1）。
3. **天空盒在延迟路径归属光照 Pass**：天空盒当前是无光照背景。延迟后场景颜色是「光照 Pass 合成」，天空盒应作为光照 Pass 之后（或合成中）的背景帧——否则会写进 GBuffer 位置图，污染后续光照。细分归属见 §3.4。
4. **Scene2D 的深度遮挡需从 GBuffer 旁路**：现状 Scene2D 靠 Scene3D 的深度做遮挡。延迟后几何深度在 GBuffer，而光照 Pass 一般不写深度。要让精灵继续正确遮挡，需把 GBuffer 深度**复制/采样到视口深度**（见 §3.6）——这是延迟改造中最易漏、最难做对的点，务必按 §3.6 处理。

## 3. 目标架构

### 3.1 模块归属与数据流

新增引擎侧 `SceneRenderer` 组件，持有 GBuffer 目标并在帧图内编排场景 pass：

```
GE_Editor / 运行时宿主
        │  每帧：SetScene(Scene*) / 相机 / 光照参数
        ▼
SceneRenderer  (GE/src/Render/SceneRenderer.h/cpp，新增)
        │  持有 GBufferTarget（3 色 + 深度，真实分配）
        │  向 Renderer 的本帧 builder 注册：GBuffer → Lighting → (可选半透明) → Scene2D
        ▼
Renderer 持帧图 → EndFrame 追加 UIPass → Execute（声明序：GBuffer/Lighting/Scene2D/UIPass）
```

依赖方向单向：宿主 ─▶ `SceneRenderer` ─▶ `Renderer`(帧图) ─▶ `RenderGraph`。`SceneLayer` 不再直接 AddPass（场景 pass 的注册从 SceneLayer.cpp:234-288 移入 `SceneRenderer`）。

### 3.2 GBuffer 布局（MRT，一套视口尺寸）

| 附件 | 格式 | 内容 | 采样需求 |
|---|---|---|---|
| GColor  | `R8G8B8A8Unorm` | 反照率（albedo）rgb + 保留（或材质标记） | 光照 pass 采样 |
| GNormal | `R16G16B16A16Snorm`（或 `R8G8B8A8Snorm`） | 世界/视图空间法线 xyzw | 光照 pass 采样 |
| GData   | `R8G8B8A8Unorm` | metallic(r)/roughness(g)/自发光标记(b)+ 预留(a) | 光照 pass 采样 |
| 深度     | 现有视口深度格式 | 几何深度（供光照早测试 + 合成遮挡） | 旁路给 Scene2D |

> 三色三图 + 深度共用一个专用 `GBufferTarget`（扩展 `RenderTarget` 为多颜色附件，见 §4.2）。位置/金属度编码可用「位置存深度重建」避免存 view 空间位置图（几何 pass 输出减少），细节 §6.2。

### 3.3 延迟 pass 时序（SceneRenderer 向帧图注册）

```
Pass A "GBuffer"      颜色 MRT = {GColor, GNormal, GData}，eClear；深度 eClear+eStore
                       execute → Renderer3D::FlushGBuffer：只走几何（写 G-Buffer，不做光照）
                       finalLayout(每色) → eShaderReadOnlyOptimal
Pass B "Lighting"     颜色 = 视口 RT 颜色（eClear 暗底），读 GColor/GNormal/GData（ShaderRead）
                       execute → Renderer3D::FlushLighting：全屏三角形采样 G-Buffer + 光参数，
                                                             逐光源累加；写颜色附件
Pass C "Scene2D"      （原有）颜色 eLoad + 深度（旁路后的视口深度）eLoad
                       execute → Renderer2D::FlushScene
Pass D "UIPass"       （Renderer 恒有，写 swapchain，不动）
```

- **声明序即执行序**：A→B→C→D 依序注册，RenderGraph 自动在 A 写后转读、B 读 G-Buffer、C 读旁路深度等跨 pass 插屏障。
- **A 的 MRT**：`GBuffer` pass 颜色附件是 3 个 `AttachmentDesc`（同 resource 集合中 GColor/GNormal/GData），渲染时 `AddColorAttachment` 依次加入，全部 eClear 后作为统一清屏 —— 复用 RenderGraph 已有的多颜色附件支持。
- **光照数据流**：B 的全屏 pass 只读 G-Buffer + 光照参数。光照参数仍来自 `Renderer3D::LightParams`（方向光 + 点光源数组），由 `FlushLighting` 从同一份上传的 UBO/SSBO 读取 —— 复用 §1.2 的 `UploadFrameUBO/UploadLightBuffer`，避免双份数据源。

### 3.4 前向 / 延迟分工（并存）

延迟不是全量替换，两种物体需要分离（沿用 `SortKey` 的 pipelineId 高位，见 Renderer3D.h:32-35 的 `kSkinPipelineBit` 先例）：

| 类型 | 归属 | 原因 |
|---|---|---|
| 不透明 PBR / Blinn-Phong | **延迟**（写 GBuffer） | 延迟的主目标，逐像素光照移出几何 pass |
| 半透明 | **前向保留**（现状路径不变，几何+光照一次） | 半透明需逐片元正确混合，延迟无排序混合能力；透明已有独立计划书 |
| 天空盒 | **光照 Pass 之后的前向背景**（保留 `DrawSkybox` 路径，归光照 pass 后段或独立小 pass） | 不写进 GBuffer；作为场景最远背景在颜色附件上先画（关闭深度测试/写入，同 Renderer3D.cpp:632 现状） |
| 精灵（2D） | **前向，Scene2D 不变** | 已在 Scene2D pass，读深度做遮挡 |

> 实现上为「同一次 `m_Meshes` 采集，EndScene 按 pipelineId 分派」：不透明批次进 GBuffer pass，半透明批次进前向小 pass。**分离点**要按材质是否透明（`Material` 类型/混合开关）在采集期就标记进 `SortKey`，否则两种光照路径无法在 pass 间正确分流 —— 这是并行架构的关键，见 §6.3。

### 3.5 现有几何数据/光照数据复用

- **几何**：`m_Meshes` 采集、`CollectBatches`、`UploadInstanceBuffer`、顶点缓冲/索引绑定全部原样复用 —— 延迟只改「片元输出到哪」与「顶点着色器之后是否仍做光照」，顶点阶段不动。
- **光照 UBO/SSBO**：`UploadFrameUBO`、`UploadLightBuffer`（Renderer3D.cpp:528-630）完全复用，`FlushLighting` 直接消费同一份 BufferAllocation。
- **环境 IBL**：PBR 的 IBL 三件套（prefilter / irradiance / BRDF LUT，set1 binding 5/6/7）在光照 Pass 里作为环境光来源复用，几何 Pass 不需要它们（GBuffer 只存材质，环境在光照阶段采样）。

### 3.6 深度旁路（Scene2D 遮挡的关键）

延迟后几何深度在 GBuffer 深度附件。让 Scene2D 精灵继续按深度遮挡：

- 方案优先：**光照 Pass 同时把 GBuffer 深度**（渲染早期测试用）**拷贝/解析一份到视口深度附件**（`vkCmdCopyImageToImage` 或 RenderGraph 加一个 Copy pass 用 `TransferDst`/`TransferSrc`）。Scene2D 的 `depthAttachment` 引用这份旁路深度，`eLoad` 读遮挡 —— 与 SceneLayer.cpp:279-284 现状完全对齐。
- 备选：光照 pass 直接以视口深度为附件并写深度=1（合成处不遮挡精灵），则 Scene2D 深度恒等于视口远平面、精灵永远被几何遮挡，违背现状 —— **不取**。
- 该旁路依赖 RenderGraph 支持**同帧同一资源既作附件又作拷贝源/目的**的声明（深度在 GBuffer 写、Lighting 后拷贝）。RenderGraph 现以声明序插屏障，GBuffer 深度作为外部图，能被 Lighting pass 后续的 Copy 正确衔接 —— 需在 §4.6 为 RenderGraph 补一个轻量 Transfer/Copy pass 声明（或直接在 execute 回调里录拷贝，但要让 RenderGraph 认知该资源的「读」语义以生成屏障）。归属 §6.4 作为待确认的最小渲染图扩展。

## 4. 实施步骤

### Step 1 — 新增 `SceneRenderer` 引擎组件（下沉编排）
1. 新建 `GE/include/GE/Render/SceneRenderer.h`、`GE/src/Render/SceneRenderer.cpp`。
2. `SceneRenderer` 持有：`GBufferTarget`（§4.2）、场景 pass 编排逻辑、`SceneLayer` 现注册 Scene3D/Scene2D 的那段移入。
3. `SceneLayer` 改为：创建 `SceneRenderer`，每帧注入 Scene/相机/编辑或运行态，调 `SceneRenderer::Render(相机,光照)`（内部向 builder 注册场景 pass），不再直接 AddPass。

### Step 2 — `RenderTarget` 支持多颜色附件（GBufferTarget）
现状 `RenderTarget` 单色+深度（SceneLayer.cpp:245-246 只 Import color/depth 两个 view）。为 GBuffer 3 色 + 深度：
1. `RenderTarget` 增加「多颜色附件」能力：`colorViews`（原单一 color 改为 vector），`Create` 支持一次分配多张颜色图 + 各自 view。
2. 新增 `GBufferTarget` 子类/或直接扩展现有 `RenderTarget`：创建 GColor/GNormal/GData/Depth 四张图，暴露 `GetColorView(i)` 供 `SceneRenderer` Import。
3. 视口 RT（`SceneViewport`）不强制改多附件，但接口若统一为 vector，SceneLayer/SceneRenderer 两侧 Import 都要跟随。

### Step 3 — Renderer3D 几何输出变体（FlushGBuffer）
几何照旧采集，但片元改输出 G-Buffer（多颜色附件）而非直接光照：
1. 新增 GBuffer 片元着色器 `gbuffer.frag`（采样反照率/法线/MR 贴图 → 写 GColor/GNormal/GData）与对应管线布局/`VulkanPipelineLayout` 组合。GLSL 放入 `assets/shaders/glsl/` 即自动进编译（CMakeLists glob，见 `assets/shaders/glsl/CMakeLists.txt`）。
2. 新增 `FlushGBuffer(VulkanCommandBuffer&, VulkanRenderFrame&)`：按现 `RecordScene` 排序/上传/录绘制，但动态渲染的附件是 GBuffer MRT，片元管线切到 gbuffer 变体。
3. 采集/合批/上传全复用，只换「最终管线 + 输出附件集合」。

### Step 4 — 全屏光照 Pass（FlushLighting）
1. 新增全屏三角形着色器 `deferred_lighting.vert/.frag`：顶点只画全屏三角形，片元从 G-Buffer 采样重建几何，逐光源（方向 + 点光源，循环 SSBO）累加，输出到视口颜色附件。
2. `FlushLighting(VulkanCommandBuffer&, VulkanRenderFrame&)` 录制：绑定 G-Buffer 三张图为采样输入（set），绑定光照 UBO/SSBO（复用 `UploadFrameUBO/UploadLightBuffer`），画全屏三角形。
3. 光照数学从现 `mesh.frag / mesh_pbr.frag / mesh_pbr_ibl.frag` 提取共用函数（BRDF、光源衰减）到公共 `.glsl` 片段，延迟/前向共用避免漂移。

### Step 5 — 天空盒归属与 Scene2D 深度旁路
1. 天空盒：从 `RecordScene` 的网格段挪到光照 Pass 之后的前向背景（保持关闭深度写，作为最远背景）——保证天空盒不进 GBuffer、不被光照 pass 二次照亮。
2. 深度旁路：光照 pass 后把 GBuffer 深度拷贝到视口深度附件（或按 §3.6/§6.4 的渲染图 Copy pass 方案），Scene2D 读旁路深度保持精灵遮挡语义。

### Step 6 — 编译接入与编辑器装配
1. `CMakeLists`：新增 `SceneRenderer.cpp` 进 `GE_SRC`。
2. `SceneLayer.cpp`：把 AddPass(Scene3D/Scene2D) 段替换为 `SceneRenderer::Render`，保留相机/清色选择逻辑（SceneLayer.cpp:207-232）。
3. 着色器自动编译：`glslc` 对新增 .vert/.frag 生效；运行时 `AssetPaths::Shaders` 加载 `.spv`（同 Renderer3D.cpp:49-54 的 RequestShaderModule 范式）。

### Step 7 — 验证项
- Debug + Release 各构建一次（MSVC + Ninja，`build.bat`），无编译/链接错误。
- 运行 GE_Editor：视口渲染延迟结果与先前**逐像素一致**（同场景同光照，反照率/法线/金属度采样路径与 PBR 数学等价），validation layer 无新报错。
- 点光源数量拉升（数百）验证帧率优势；天空盒/精灵/透明物体遮挡关系正确。
- resize 主窗口/视口时 GBuffer 与深度旁路尺寸随视口同步，无陈旧尺寸。

## 5. 待确认事项

1. **天空盒在延迟路径的确切位置**：光照 Pass 后作为颜色附件背景（推荐，保持现关闭深度写语义），还是独立小 pass？取决于延迟时是否仍想让天空盒被光照/雾影响 —— 见 §3.4。
2. **G-Buffer 编码**：法线用 `R16G16B16A16Snorm` 还是压缩到 `R8G8B8A8Snorm`；是否存 view 空间位置还是深度重建 —— 精度与带宽取舍，见 §6.2。
3. **深度旁路走哪种**：光照 Pass 内顺带拷贝，还是给 RenderGraph 加 Transfer/Copy pass（让深度资源被图认知、屏障自动）。后者更贴合帧图语义但需小扩展 —— §6.4。
4. **GBuffer 用独立 `GBufferTarget` 类还是扩展现有 `RenderTarget`**：见 §4.2/§6.1。倾向后者（多颜色附件本就是 RenderTarget 的自然扩展）。
5. **前向/延迟分流点**：材质透明标记何时写入 `SortKey`（采集期 vs 录制定），决定 Scene2D/前向小 pass 正确分组 —— §6.3。

## 6. 风险与备选

### 6.1 虚拟资源与 GBuffer 承载
RenderGraph 的虚拟资源目前只登记不分配（RenderGraph.cpp:191）。GBuffer 用真实 `RenderTarget` 承载的代价：GBuffer 尺寸跟随视口，resize 时要重建三张图 + 深度（与现状视口 RT 重建同代价）。等「虚拟资源阶段2」落地后，GBuffer 若迁入虚拟资源需 RenderGraph 能真实分配 + 生命周期管理，收益是每帧可能复用、布局流转更内聚。本轮**不引入虚拟资源分配**，避免本计划拖入渲染图内存管理的复杂度。

### 6.2 G-Buffer 带宽/精度
- 位置：若不存位置图而用深度重建 view 位置，光照 pass 要多一次矩阵运算、省一张图带宽。实现简单、带宽友好，倾向不存位置图（§3.2 的 GData 即无位置）。
- 法线：`R16G16B16A16Snorm` 精度稳妥，但带宽大；若配合法线压缩（`R8G8B8A8` + 重构 w）可省带宽。初版取 16 位，后续可按带宽压力再压。

### 6.3 前向/延迟物体分流
**判定来源已具备**：`Material::AlphaMode`（Opaque/Mask/Blend）数据层已落地（`Material.h`，见 `透明物体渲染计划书.md` 阶段 1，2026-09-04）。**只有 `alphaMode == Blend` 才是半透明（走前向）；`Opaque` 与 `Mask` 都是不透明（可写 G-Buffer，Mask 的 discard 在 GBuffer pass 做即可）。** 本计划需做的是在**采集期**就把「Blend 与否」烙进 `SortKey`（类似 `kSkinPipelineBit`），否则两种光照路径在 pass 间无法分流：半透明必须走前向（延迟不能排序混合），不透明才写 GBuffer。建议在 `SortKey.pipelineId` 增加「半透明位」，`RecordScene/FlushScene` 按位分派到 GBuffer 或前向段 —— 透明物体的采样顺序、混合状态沿用现有透明计划书（其阶段 2 双 pass 仍在计划中），不在此重做。实施前须先完成透明计划书阶段 2（`MaterialUBO.params.z` 承载 alphaCutoff、shader 输出真 alpha、不透明/透明双段管线）。

### 6.4 RenderGraph 小扩展（深度旁路可选路径）
若走「Copy pass 让深度被图认知」，需给 RenderGraph 加 `Transfer`/`Copy` pass 声明（计划书 §7 已列 `TransferDst/TransferSrc` 用法，但 Execute 现只支持 Raster）。最小实现：新增 `PassType::Copy`，execute 内录 `vkCmdCopyImageToImage`，`ReadStage/WriteStage` 表已含 Transfer —— 改动收敛到 RenderGraph.cpp 的 pass 类型分发与一次 Copy 录制。这是本计划**唯一的渲染图改动**，其余全部在 Renderer3D/SceneRenderer 层。

### 6.5 前向路径保留成本
透明 + 天空盒仍走前向，意味着保留两条管线族（前向 Blinn/PBR + 延迟 GBuffer/光照）。代价是管线变体数上升（shader/pipeline layout 缓存会覆盖，Renderer3D.h 已有三族 layout 先例）。收益是透明/天空不受延迟局限、引擎覆盖更广。若未来希望减少变体，可评估「透明延迟（排序混合/双向反射）」这类后续工程，本轮不做。
