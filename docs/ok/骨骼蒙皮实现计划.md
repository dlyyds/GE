# 骨骼蒙皮实现计划（详细）

> 状态：**实现中 —— A 阶段（数据层）已完成（2026-08-25），B~E 阶段待做**
> 目标：为 GE 引擎引入 glTF 骨骼蒙皮（skinning）支持，让带骨架的角色贴模型（buster_drone、adamHead 等）经 `GLTFSceneImporter` 导入后能跟随骨骼权重正确变形渲染。
> 前置依赖：`glTF模型导入计划书.md`（阶段 1/2 已完成）、`Mesh类拆分重构方案.md`（已完成）、`Mesh内置格式.gemesh方案.md`（v1 已落地，v2 需扩顶点流）。
> 定位：本阶段**只做骨骼蒙皮**（joint + inverse bind + 权重 + GPU 蒙皮顶点着色器），**不做动画**（clip / keyframe 采样）。动画是下一阶段（阶段 4），本计划为其预留骨架/关节数据与接口。

> **A 阶段完成情况（2026-08-25）**：`Vertex` 扩为 80B（`JointIdx`/`Weight` 两个蒙皮字段，`operator==`/`hash` 同步纳入）；`MeshData` 增 `skinIndex`；`GLTFLoader::BuildMesh` 读取 `JOINTS_0`/`WEIGHTS_0`（含 normalized u8/u16 解码，越界钳 0，权重重量化 + 合法性日志）；`Renderer3D` 网格管线 `setVertexInputFromShader` 传入 `sizeof(Vertex)` 作为权威 stride（mesh.vert 反射求和 48B 会错，必须显式覆盖）；`.gemesh` 写端升 v2（80B），读端兼容 v1（48B→80B 升格补 0）。

## 0. 术语与 glTF 蒙皮数据模型

glTF 的 skin 由三部分组成，理解这三者是实现的前提：

```
skin {
  "joints": [nodeIndex, ...],   // 关节节点列表（按索引 0..N-1）
  "inverseBindMatrices": accessor, // 每关节一个 mat4=全局逆绑定矩阵（把网格顶点从骨空间换回模型空间）
  "skeleton": nodeIndex,          // 可选，根关节（供查找用，实现可忽略）
}
```

- **inverseBindMatrices（IBM）**：是「关节节点全局矩阵 的逆 在绑定姿态下的快照」。顶点着色器把它与关节的当前全局矩阵相乘，得到关节对顶点的变换。
- **JOINTS_0**：每顶点 4 个无符号整数（`VEC4` of `UNSIGNED_BYTE` / `UNSIGNED_SHORT`），即影响该顶点的 4 个关节索引。
- **WEIGHTS_0**：每顶点 4 个 float（`VEC4` of `FLOAT` / `UNSIGNED_BYTE` normalized），与 JOINTS_0 一一对应，权重和通常为 1。
- **primitive 归属**：`mesh.primitive` 上的 `skin` 索引挂在 **node 层**（node.skin），一个 node 引用 mesh + skin；同一个 primitive 只会被一个皮肤驱动（glTF 限制：一 primitive 一 skin）。

**顶点蒙皮公式**（顶点着色器内）：

```
// 关节变换矩阵：将顶点从模型空间换到骨空间(IBM)，再换到当前关节全局空间
// jointMatrix[j] = globalJointMatrix[j] * inverseBindMatrix[j]
// 合并的顶点 = Σ_j weight_j * (jointMatrix[j] * position)
// 法线同理，用 jointMatrix 的 3×3 部分（忽略平移）
```

关键实现点：**`globalJointMatrix`（关节节点当前全局矩阵）由引擎每帧计算**，而不是存在某个静态数据里——这决定了我们必须在 Scene 层维护「关节的全局变换」，并把统一计算好的 `jointMatrix = global * inverseBind` 传给着色器（每帧上传一套矩阵 SSBO）。

## 1. 现状与差距分析

根据对现有代码的调研，列出每个相关模块的现状与蒙皮引入后的差距：

| 模块 | 现状 | 蒙皮需要的改动 | 破坏性 |
|---|---|---|---|
| `Mesh.h` `Vertex` | 48B：Position/Normal/TexCoord/Tangent，location 0-3 | 增加 `uvec4 jointIdx` + `vec4 weight`（location 4/5）| **高（布局 48B→80B）** |
| `MeshData` | 只存 vertices/indices/subMeshes/materialData | 需携带每个子网格的：关节索引流、权重流 | 中（结构扩展，向后兼容）|
| `GLTFLoader::BuildMesh` | 读 POSITION/NORMAL/TEXCOORD/TANGENT | 读 `JOINTS_0`/`WEIGHTS_0` 填入顶点 | 中 |
| `GLTFSceneImporter::Import` | 建 node→实体、mesh→MeshRendererComponent、父子层级 | 解析 `skin`：为关节节点存 joint 身份、把 IBM + joint 顺序挂到皮肤根 | 高（场景数据模型要加） |
| `Scene` / `TransformComponent` | worldMatrix 每帧 DFS 算好 | 蒙皮关节需**在渲染用到的矩阵之前**完成全局矩阵计算；畸形矩阵（负行列式）需补偿 | 中 |
| `Renderer3D` | pipelineId 0=Blinn/1=PBR，`mesh.vert` 顶点输入从着色器反射；set0=Frame/Light、set1=材质纹理、set2=InstanceData SSBO | 新增 `mesh_skinned.vert` 蒙皮顶点着色器 + 新增关节矩阵 SSBO 绑定 + 按「是否蒙皮」路由管线 | 高（多一套管线布局与绑定）|
| `SceneSerializer` | YAML 序列化各组件 | 序列化 SkinComponent（含关节引用、IBM 加载源）| 中 |
| `.gemesh` v1 | 顶点流固定 48B Vertex | v2 需支持带蒙皮顶点布局（或蒙皮网格不走 .gemesh 烘焙）| 高 |
| shader 构建（`glsl/CMakeLists.txt`）| glob `*.vert/*.frag` 自动编译 | 新增 `mesh_skinned.vert` 自动纳入 | 无 |

**关键决策点（已定，见 §9）**：`Vertex` 布局 48B→80B 是全项目最 "伤筋动骨" 的一处，波及所有模型加载（OBJ/glTF/内置几何体）、`.gemesh` v1 顶点流、以及所有用 `Vertex` 的地方。经用户拍板采用 **方案 A（统一扩展 Vertex 到 80B）**：所有网格统一携带蒙皮字段、无第二套顶点路径，改动集中但一次性；代价是 **`.gemesh` v1 顶点流必须升级到 v2**、且静态网格每顶点多携带 32B（80B/顶点）内存。下文 §3 各阶段按方案 A 展开。

## 2. 总体架构设计

```
┌───────────────────────── 加载期（离线/运行时）─────────────────────────┐
│  GLTFLoader::BuildMesh                                                 │
│    读 JOINTS_0 / WEIGHTS_0 → 填入统一 Vertex 的蒙皮字段（80B）           │
│    返回 MeshData（含 skinIndex 标记，无独立 skinned 通道）               │
├───────────────────────── 场景层（运行时每帧）──────────────────────────┤
│  GLTFSceneImporter::Import                                              │
│    建 node 实体树；发现 node.skin → 生成骨骼实体 + SkinComponent        │
│    SkinComponent 记录：关节实体句柄列表 + IBM 数组 + 关联的 Mesh        │
│  Scene::UpdateWorldTransforms 之后 → UpdateSkins                       │
│    为每个 Skin 计算 jointMatrix = globalJoint * IBM，写入 SSBO          │
├───────────────────────── 渲染层（GPU）──────────────────────────────────┤
│  Renderer3D                                                             │
│    mesh_skinned.vert：location4/5 关节索引/权重 + set2 binding1 关节矩阵 │
│    DrawSubMesh 走蒙皮管线当且仅当 (mesh, submesh) 被骨骼驱动            │
│    pipelineId 增加蒙皮维度（如 Blinn+蒙皮 / PBR+蒙皮）                  │
└──────────────────────────────────────────────────────────────────────────┘
```

**设计原则**：
1. **蒙皮是渲染属性，不是网格属性**：同一份网格可能同时被两个皮肤驱动（罕见但 glTF 允许）。因此蒙皮决定权放在**绘制时**（SkinComponent 与 mesh 关联），而非网格创建时写死。
2. **关节全局矩阵由 Scene 统一维护**：复用现有 `TransformComponent::worldMatrix` DFS 结果。蒙皮变换本质上就是「关节实体各自的 world 变换」× IBM，所以关节节点就是普通实体，只是额外打了 `JointComponent` 标记 + 被 SkinComponent 引用。
3. **每帧上传一套每-Skin 关节矩阵**：一帧内 Joint SSBO 从 BufferPool 按需分配，每个 skin 一块连续区间（类似现有 InstanceData SSBO 的做法）。

## 3. 分阶段实施

按「先让一个角色转起来 → 再并行化/健壮化 → 再序列化/烘焙」的节奏拆成 5 个可独立交付的小阶段，每个阶段结束都能编译可运行、可回退。

### 阶段 A：数据层 —— 带蒙皮顶点 + glTF 解析

**目标**：让 `GLTFLoader` 能把 buster_drone 的蒙皮顶点 + 关节序 + IBM 读取出来，验证数据链路正确。此阶段结束时**仅数据可打印/单测**，不渲染。

**A1. 顶点结构（决策：方案 A——统一扩展 Vertex 到 80B）**
- `Mesh.h` 的 `Vertex` 增加两个字段（内存布局由着色器反射紧密打包，location 顺序必须严格一致）：
  ```cpp
  struct Vertex {
      glm::vec3 Position{0.0f};       // location 0 (12B)
      glm::vec3 Normal{0.0f};         // location 1 (12B)
      glm::vec2 TexCoord{0.0f};       // location 2 ( 8B)
      glm::vec4 Tangent{0,0,0,1};     // location 3 (16B)
      glm::uvec4 JointIdx{0};         // location 4 (16B) 关节索引(0..N-1)
      glm::vec4  Weight{0,0,0,0};     // location 5 (16B) 权重(和≈1)
  };
  // 总大小 48B → 80B
  ```
- `operator==` 与 `hash<Vertex>` 需把 `JointIdx`/`Weight` 纳入（Quantize 清洗 Weight；JointIdx 整数无需清洗）。权重默认 (0,0,0,0) 使非蒙皮顶点在着色器里退化为恒等（见 C1 归一化说明）。
- `MeshData` 不引入独立 skinned 通道：所有顶点统一走 `vertices`（现在是 80B）。`MeshData` 增 `int skinIndex = -1` 标记该 mesh 是否被皮肤驱动（-1=静态）。
- `.gemesh` v1 顶点流被破坏 → **升级 v2**（见阶段 E2）。

**A2. glTF 读取**
在 `GLTFLoader.cpp` 的 `BuildMesh` 内，检测 primitive 是否含 `JOINTS_0` 且 `WEIGHTS_0`（两者必须同时存在才算蒙皮mesh，否则按静态处理）：
1. 找不到 `Render/GLTFLoader.h` 中 `BuildMesh` 当前签名是 `(model, meshIndex, filepath, MeshData&)` —— 需扩展，让调用方能感知「这个 mesh 是否被皮肤驱动」。**方案**：`BuildMesh` 增加出参 `std::optional<int>* outSkinIndex` 或在 `MeshData` 里加 `int skinIndex = -1`。
2. 每顶点读 `JOINTS_0`（`UNSIGNED_BYTE`/`UNSIGNED_SHORT`，用现有 `ReadFloatAttr` 思路扩一个 `ReadUintAttr`）与 `WEIGHTS_0`（`FLOAT`，量化清洗）。
3. 顶点量化/去重：现在去重表用 `std::unordered_map<Vertex,...>`。方案 B 下需要 `hash<SkinnedVertex>` + `operator==`（关节索引、权重都参与）。缺 `JOINTS_0`/`WEIGHTS_0` 的 primitive 仍走静态 `Vertex` 路径。
4. 数据校验：`JOINTS_0` 的关节索引必须是 `[0, joints.size())` 内合法值，越界钳制为 0（与现有 `ReadIndex` 越界兜底一致）。

**A3. 单测 / 验证脚本（可选）**
写一个小的验证路径：用 buster_drone.glb，打印其 mesh 是否自带 `skin`、`joints` 数量、IBM 矩阵条目数是否与 joints 一致、某一顶点的 JOINTS_0/WEIGHTS_0 是否在 [0,1] 且和为 1。**不必写成自动化单测**（项目无测试框架），放进临时工具或日志验证即可。

**退出标准**：能在日志输出 buster_drone 的蒙皮数据（关节数 N、IBM 矩阵验证、权重合法），且所有现有非蒙皮模型（OBJ、内置几何体）加载、渲染完全不受影响。

### 阶段 B：场景层 —— 骨骼实体 + SkinComponent + 每帧关节矩阵

**目标**：让骨骼在场景中「被管理」起来，每帧算出每个 skin 的关节矩阵并写进 GPU 缓冲。此阶段结束时关节矩阵可在调试工具中查看（但网格尚未用上）。

**B1. 组件定义**（`Components.h`，放在物理组件段之前、网格渲染组件之后）
```cpp
/// 枚举皮肤顶点格式（决策 §9 后择一）
enum class SkinVertexFormat : uint8_t { Static = 0, Skinned = 1 };

/// 关节标记组件：挂在 glTF node 对应的实体上，标出它是骨骼关节
struct JointComponent {
    int jointIndex = 0;          // 该关节在 skin.joints 里的索引（0..N-1）
    JointComponent() = default;
    explicit JointComponent(int idx) : jointIndex(idx) {}
};

/// 皮肤组件：挂在「带 mesh 且被骨骼驱动的 node」实体上
/// 记录驱动它的关节链 + 逆绑定矩阵 + 关联的蒙皮网格
struct SkinComponent {
    std::vector<Entity> joints;            // 关节实体句柄（有序，索引=skin.joints 序）
    std::vector<glm::mat4> inverseBindMatrices; // IBM（与 joints 一一对应）
    Mesh* MeshPtr = nullptr;               // 被本皮肤驱动的网格（可选，可从绘制时取）
    bool  RequiresJointUpload = true;      // 脏标记：需要重新上传关节矩阵（首次/关节变换变化）

    SkinComponent() = default;
    // ...
};
```
> 注意：`Components.h` 里不能直接用 `Entity`（类型不完整问题）。方案：SkinComponent 存 `std::vector<entt::entity>`（原始句柄）+ 一个便捷查询接口在 Scene 层；或在头文件里 forward declare `class Entity`（`Components.h` 已有 `class Entity;` 前向声明的先例——见文件头部）。`glm::mat4` 需要 `#include <glm/glm.hpp>`（已包含）。

**B2. GLTFSceneImporter 扩展**
当前 `Import(scene, meshMgr, filepath)` 逐 node 建实体、设父子、挂 MeshRendererComponent。扩展为：
1. 预先收集 `model.skins`：对每个 skin，解析 IBM accessor（`BuildMesh` 阶段 A 已保证有 `glm::mat4`）。
2. 建实体时：若 `node.skin >= 0`（有皮肤），则该 node 实体挂 `SkinComponent`，其 `joints` 填 `skin.joints` 各 node 对应的实体句柄。
3. 给每个 **出现在 skin.joints 里的 node** 所对应实体挂 `JointComponent`（标记 jointIndex）。这些关节实体本身若有 mesh 也照常渲染（glTF 中关节 node 通常无 mesh，但保留通用性）。
4. **关键顺序约束**：必须**先为全局 node 建完所有实体并 SetParent 完成层级**，再填 `SkinComponent.joints`（否则关节实体可能还没建出来、句柄无效）。分两遍：第一遍建全部实体 + 层级 + MeshRenderer；第二遍遍历 `model.skins` 回填皮肤引用。
5. 空洞校验：skin.joints 里的 node 索引找不到实体（如 node 无任何组件被裁剪）时容错跳过。

**B3. Scene 每帧更新蒙皮（Skins）**
在 `Scene::OnUpdate3D` 中、`UpdateWorldTransforms()`（DFS 算好所有实体 worldMatrix）**之后**调用新增的 `UpdateSkins()`：
```cpp
void Scene::UpdateSkins(VulkanRenderFrame &frame, BufferPool &pool, VulkanCommandBuffer &cmd);
```
对每个实体的 `SkinComponent`：
1. 对每个关节 `joints[i]`，取它的 `TransformComponent::GetWorldMatrix()`（阶段 B1 后已完成）。
2. 计算 `jointMatrix[i] = world[i] * IBM[i]`（model 空间→骨空间→当前全局）。
3. 从 `BufferPool` 动态分配一块 `N * sizeof(mat4)` 的 SSBO 区间，`update` 写入。
4. `BindBuffer` 到 set 2 binding 1（见阶段 C 布局约定），随后即将绘制的蒙皮网格读它。

> 这里有个**两遍依赖**：`UpdateSkins` 必须在 DFS worldMatrix 之后、且在同一次 command 录制里把关节 SSBO 绑好。由于关节矩阵是「骨骼每一帧的相对姿态」，若某帧不动关节、仅相机动，也可缓存 SSBO 跳过重算——`RequiresJointUpload` 服务于优化，首版可从简（每帧都重传，代价小）。

**退出标准**：导入 buster_drone 后，场景里能检出 SkinComponent、JointComponent，关节实体各带正确 worldMatrix，`UpdateSkins` 能算出并上传关节矩阵 SSBO（可临时在 mat 调试可见）。

### 阶段 C：渲染层 —— 蒙皮顶点着色器 + 管线路由 + 关节 SSBO 绑定

**目标**：让被皮肤驱动的网格真正用蒙皮顶点着色器渲染，关节矩阵生效。

**C1. 新增 `assets/shaders/glsl/mesh_skinned.vert`**
复制 `mesh.vert` 并在其基础上：
```glsl
#version 460
// 复用静态路径的全部 FrameUBO / InstanceData 定义

layout (location = 0) in vec3 inPos;
layout (location = 1) in vec3 inNormal;
layout (location = 2) in vec2 inUV;
layout (location = 3) in vec4 inTangent;
layout (location = 4) in uvec4 inJointIdx; // 关节索引（0..N-1）
layout (location = 5) in vec4  inWeight;   // 权重（和≈1）

// 关节矩阵 SSBO：set2 binding1。每个皮肤一块连续区间，由 CPU 按绘制顺序填好。
layout (set = 2, binding = 1, std430) readonly buffer JointBuffer
{
    // 变长数组；CPU 端记录当前皮肤在缓冲里的 baseJoint（首个矩阵偏移）
    mat4 joints[];
} jointBuffer;
// CPU 侧经 push constant 或额外实例字段传入 baseJoint；首版可用
// gl_InstanceIndex 无济于事，需在 DrawSubMesh 时把 baseJoint 塞进
// InstanceData SSBO 或专门一个 per-draw 值。见 C2 说明。

void main() {
    outUV = inUV;
    outColor = instanceBuffer.instances[gl_InstanceIndex].color;

    mat4 model = instanceBuffer.instances[gl_InstanceIndex].model;

    // 蒙皮：四关节加权
    mat4 skin = inWeight.x * joints[baseJoint + inJointIdx.x]
              + inWeight.y * joints[baseJoint + inJointIdx.y]
              + inWeight.z * joints[baseJoint + inJointIdx.z]
              + inWeight.w * joints[baseJoint + inJointIdx.w];

    vec4 skinnedPos = skin * vec4(inPos, 1.0);

    mat4 mvp = frame.projection * frame.view * model;
    gl_Position = mvp * skinnedPos;

    vec4 worldSkinned = model * skinnedPos;
    outWorldPos = worldSkinned.xyz;

    // 法线：用 skin 的 3×3（含权重缩放），再经 model 的法线矩阵
    mat3 skinNormal = mat3(skin);
    vec3 n = normalize(skinNormal * inNormal);
    mat3 normalMatrix = mat3(inverse(transpose(model)));
    outNormal   = normalMatrix * n;
    outTangent  = normalMatrix * normalize(skinNormal * inTangent.xyz);
    outBitangent = cross(outNormal, outTangent) * inTangent.w;

    outViewVec = frame.viewPos.xyz - worldSkinned.xyz;
}
```
> **`baseJoint` 的下发方案**（需要决策，备选 3）：
> - (i) 在 `InstanceData` SSBO 里每个实例加一个 `int baseJoint` 字段 → 每实例 80B→96B，改动已知、直观。缺点：非蒙皮网格也携带。
> - (ii) 为每个 skin 单独绑定一次 Joint SSBO（`BindBuffer` 时 count 用 `joints.size()`，`glCmdSetPushConstant` 传 baseJoint=0）→ 每个 skin 一次 `vkCmdBindDescriptor`/一次 push constant，绘制循环里按皮肤切——**推荐**，开销低且清晰，天然贴合「一个皮肤 = 一个 SSBO 区间 + 一次绑定」。
> - (iii) 把 `baseJoint` 编码进 `InstanceData` 的 color.w 等未用位 —— hack，不推荐。
> 首版选 (ii)：绘制循环里对「当前皮肤」绑定一次 Joint SSBO + 一次 push constant，随后同皮肤的所有 submesh 复用。这也与 `SortKey` 加入「皮肤/管线维度」呼应。

**C2. 管线布局与顶点输入**
`Renderer3D` 现在 `ConfigureMeshPipeline` 用 `ps.setVertexInputFromShader(*m_VertShader)`（从着色器反射自动生成顶点输入）。蒙皮顶点着色器反射出的 location 0-5 会自动生成 80B 顶点输入结构——**前提是 `Vertex`（方案 A 已统一为 80B）的布局与着色器 location 顺序严格一致**。静态路径与蒙皮路径共用同一 80B `Vertex` 结构与同一顶点缓冲，仅顶点着色器不同（mesh.vert 忽略 location 4/5，mesh_skinned.vert 使用它们）。

新增：
- 成员 `VulkanShaderModule* m_VertShaderSkinned` → `RequestShaderModule(mesh_skinned.vert.spv)`。
- 管线布局：蒙皮顶点着色器 + 现有三种片元着色器（Blinn / PBR / PBR-IBL），共 3 套蒙皮布局：
  - `m_PipelineLayoutSkinned{ mesh_skinned.vert, mesh.frag }`
  - `m_PipelineLayoutSkinnedPBR{ mesh_skinned.vert, mesh_pbr.frag }`
  - `m_PipelineLayoutSkinnedPBR_IBL{ mesh_skinned.vert, mesh_pbr_ibl.frag }`
- `RequestPipelineLayout` 会自动反射出 set2 binding1 的 Joint SSBO（从着色器 `layout(set=2,binding=1)`）。

**C3. pipelineId 扩展（蒙皮维度）**
现在 `pipelineId`：0=Blinn、1=PBR。蒙皮叠加后需区分「静态 vs 蒙皮」。**方案**：用 `SortKey.pipelineId` 的`位 2`（值 2/3）表示「蒙皮 Blinn / 蒙皮 PBR」，即：
```
0 = Blinn 静态
1 = PBR 静态
2 = Blinn 蒙皮
3 = PBR 蒙皮
```
`GetPipelineId` 需改为接收 `bool skinned`（或由 mesh 的顶点格式决定）。**注意**：现有代码 `ConfigureMeshPipeline`/`DrawMeshInstances` 里 `pipelineId == 1` 的判断要同步改为按 (skin, pbr) 两个维度判断，否则蒙皮 PBR 会漏绑 IBL/MR 纹理。

> 更清晰的做法：不把蒙皮硬叠进 pipelineId 位，而是**在 `MeshInstance`/`RenderBatch` 里加 `bool skinned` 字段 + 独立的 `skinKey`**，排序键按 `{pipeline, skinned?, ...}` 分组。为控制改动面，计划采用「pipelineId 位 2 = 蒙皮」的线性扩展，改动集中在 `DrawMeshInstances` 的管线路由一处。

**C4. 绘制入口**
`DrawSubMeshImpl`/`DrawSubMesh` 需要知道「该 submesh 是否蒙皮 + 是哪个皮肤」。当前签名只有 `(transform, mesh, firstIndex, indexCount, material, color)`。扩展：
- 新增 `DrawSkinnedSubMesh(transform, mesh, submesh, material, color, SkinComponent* skin)`，内部与静态路径汇总到同一个实例队列，但：
  - `MeshInstance` 增加 `bool skinned` + `SkinComponent* skin`（或 `uint32_t skinId`）。
  - `ComputeSortKey` 在蒙皮时把 pipelineId 加上蒙皮位，并按 `skin` 指针分组（同皮肤集中，便于 C1(ii) 一次绑定）。

与 Scene 的衔接：`Scene::RenderMeshes3D` 在遍历 MeshRendererComponent 时，如果该实体/其关联有 SkinComponent 且 mesh 对应该皮肤 → 调 `DrawSkinnedSubMesh`；否则走现有 `DrawSubMesh`。

**退出标准**：buster_drone 导入后以**绑定姿态**正确显示（各关节矩阵=IBM，加权后顶点位置与静态网格绑定姿态一致）。这一步是「蒙皮先动起来」的关键里程碑。

### 阶段 D：验证与健壮性 —— 绑定姿态正确性 + 混合测试

**目标**：确认蒙皮在半动/全动下正确，且与静态物体、PBR/IBL、多 skin 共存无误。

**D1. 静态验证**：所有关节矩阵 = world × IBM，当 world = 绑定姿态下的全局矩阵时，`jointMatrix` 应恒等 → 顶点回到未蒙皮的绑定姿态。导入 buster_drone 且不做任何关节动画时，显示应与静态 glTF 网格一致（可对照阶段 1/2 的非蒙皮导入结果）。

**D2. 手动驱动（无动画阶段的可视化验证）**：临时在编辑器或 debug 路径给某个 `JointComponent` 的 Transform 加一个赋值（如绕某轴旋转 30°），确认该关节下游的网格跟随旋转、且法线/切线方向正确（光照不破）。**注意**：这是验证用，正式版不留该 hack。

**D3. 混合场景回归**：同场景同时存在 静态OBJ网格 + 蒙皮角色 + PBR 材质 + IBL 环境。确认：
- 排序/合批不串（静态批次不误绑 Joint SSBO、蒙皮批次正确绑）。
- 蒙皮网格参与深度/剔除正确（关节矩阵驱动下的包围盒暂用网格静态 AABB 兜底，后续可用 skin 包围盒优化）。

**D4. 畸形矩阵防御**：关节缩放含负值（负行列式）时，法线的 `inverse(transpose)` 在着色器里已处理；确保 CPU 侧上传不改写这些矩阵。

**退出标准**：绑定姿态显示正确，手动旋转关节可见合理蒙皮，混合场景无渲染错误。

### 阶段 E：序列化 + 世俗化（.gemesh / 编辑器入口 / 动画预留）

**目标**：让蒙皮角色可被场景保存/加载，并为下一阶段动画铺路。

**E1. SceneSerializer 扩展**
`SceneSerializer.cpp` 序列化 `SkinComponent`：
```yaml
# 全局节
Skin:
  joints: [entityUUID1, entityUUID2, ...]   # 关节实体的 UUID（跨文件稳定引用）
  inverseBindMatrices: [...]                 # 4x4 矩阵展开（或存 glTF 源路径 + skin 索引，反序列化重算）
  mesh: "path#N"                             # 关联网格的加载键
```
`JointComponent` 序列化为 `jointIndex`。反序列化：先建全部实体 + 层级，再二次遍历 `Skin` 列表，按 UUID 把 joints 句柄接回（与现有「先全建→记ID→再二次接 parent」的 UUID 两遍流程一致，见 `Component.h` IDComponent 注释）。

> IBM 的持久化取舍：**存 glTF 源路径 + skin 索引**更轻、不持久化矩阵快照（避免文件膨胀与漂移）；反序列化时重跑阶段 B 的 Import 逻辑取 IBM。但若网格已烘焙或源文件不在，需 fallback。首版**存矩阵展开**（简单、自洽、可回退），后续可优化为引用源文件。

**E2. `.gemesh` 升级 v2（方案 A 的必做项）**
- `Vertex` 扩到 80B 后，`.gemesh` v1 的 VERTICES chunk 顶点流不再匹配 → 格式版本从 1 升到 2。
- `GEMeshLoader::SerializeGEMesh/ParseGEMesh` 需按 v2 读 80B `Vertex`（含 JointIdx/Weight）；写端在读端同构升级。
- 版本兼容策略：读端读到 v1 时**拒绝加载并报错**「顶点布局已升级，需重新烘焙」（不静默按 48B 读——那是确定性错误）。项目内烘焙脚本/离线资产需重新导出。
- 反向可行：所有现有已烘焙 `.gemesh` 资产需重跑 `ConvertToGEMesh`。
- 若后续发现升级负担过重，可回退为「蒙皮网格不烘焙、静态走 v1、动态走 glTF 直载」的混合策略（此为本版的权宜方案，默认按整格式升级 v2）。

**E3. 编辑器入口**
「导入 glTF 场景」已支持 `.glb/.gltf`；确认导入路径自动识别皮肤并建 SkinComponent（阶段 B 已做），无需新 UI。可选：编辑面板展示关节数量/是否蒙皮。

**E4. 动画预留接口**
- `TransformComponent` 已天然可被动画写入（只写局 TRS）。
- 下一阶段（阶段 4 动画）只需：`AnimationComponent`（clip 引用 + 采样时间轴）、`AnimatorSystem`（每帧按键帧写关节 Transform 的 Translation/Rotation/Scale）→ `UpdateTransforms` DFS → `UpdateSkins` 自动生效。**本阶段不实现动画**，但保证 `UpdateSkins` 每帧读**当前 worldMatrix**，使得将来动画写入 Transform 后蒙皮立即跟随，无需再改蒙皮链路。

**退出标准**：一个含 buster_drone 蒙皮角色的场景能 Serialize→Deserialize 往返，保存后重载网格仍正确蒙皮（绑定姿态）。

## 5. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| **Vertex 布局 48B→80B 破坏 .gemesh v1 + 全项目** | 高 | **已由用户拍板选方案 A**（统一扩展，见 §9.1）。对策：一次性升级 `.gemesh` 到 v2 并重烘焙资产；静态网格每顶点多 32B 内存属可接受代价，换来单一路径、无第二套顶点代码 |
| 顶点输入/着色器反射不匹配导致渲染错乱 | 中 | `setVertexInputFromShader` 从蒙皮着色器反射自动生成，唯要求 SkinnedVertex 布局与 location 顺序严格一致（写 static_assert + 注意力对齐）|
| 蒙皮/静态批次互串绑定（Joint SSBO 污染）| 中 | pipelineId 蒙皮位分组 + 每个皮肤单独绑定（C1(ii)）；排序保证同皮肤连续 |
| glTF 数据异常（缺 JOINTS、权重非规格化、索引越界）| 低 | 与现有 accessor 越界兜底一致：缺一即当静态、越界钳 0、权重不强制归一（由 shader 顺带归一）|
| 角色规模大时每帧上传全套关节矩阵开销 | 低（影响小）| 首版每帧重传（骨骼数通常 <100，mat4×100=6.4KB）；`RequiresJointUpload` 优化留后续 |
| 关节矩阵参与包围盒/剔除不准确 | 低 | 首版用网格静态 AABB 兜底；后续用皮肤 AABB 优化 |

## 9. 决策记录

本节记录编码前已拍板的 3 个设计取舍（9.1 已定，9.2/9.3 的默认推荐项已标注，不阻塞编码）。

**9.1 Vertex 布局方案 —— ✅ 已定：方案 A（统一扩展 Vertex 到 80B）**
- **A（已选）**：统一扩展 `Vertex` 到 80B（Position/Normal/TexCoord/Tangent + JointIdx + Weight）。所有网格统一带蒙皮字段，无第二套顶点路径，改动集中；代价是 **破坏 `.gemesh` v1 顶点流 → 必须升 v2**，且所有静态网格每顶点多携带 32B 内存（80B/顶点）。已按此展开全计划。
- B（未选）：独立 `SkinnedVertex` + 独立缓冲，静态路径、`.gemesh` v1 零破坏、可回退；代价是渲染/装配链多一套蒙皮顶点处理（局部代码分叉）。

**9.2 Skin 与 Mesh 的绑定关系持久化**
- A. 序列化时存 IBM 矩阵展开（自洽，重载不依赖源文件）。
- B. 存 glTF 源路径 + skin 索引（轻、不漂移，但源缺失需 fallback）。
- **推荐 B**（更贴近当前已用「path#N」网格加载键的持久化惯例），首版可退到 A。

**9.3 Joint SSBO 的 baseJoint 下发**
- (i) 塞进 InstanceData（简单，但每实例 +16B 普惠）
- (ii) 每皮肤单独绑定 + push constant baseJoint=0（**推荐**，清晰、开销低）
- (iii) 编码进未用位（hack，不推荐）
- **推荐 (ii)**。

> §9.1 已定（方案 A）；§9.2/§9.3 即便暂时按默认（均为推荐项）走，也不阻塞编码，可边做边定。
