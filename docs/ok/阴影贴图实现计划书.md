# 方向光阴影贴图实现计划书（Shadow Map Pass 插入 GBuffer 之前）

> 现状基准：延迟渲染链（GBuffer → Lighting → Transparent → Scene2D）与 RenderGraph
> 声明式同步均已落地（《延迟渲染实现计划书》，S0~S5 完成）；本计划书在其上接入方向光
> **阴影贴图**。范围限定**单个方向光、单张 Shadow Map**；CSM / PSSM、软阴影、
> 百分比近邻滤波（PCF）增强等列为后续阶段（见 §9）。透明物体不产生也不接收阴影。

> 阴影贴图是《延迟渲染实现计划书》§10「后续阶段」明确列的待办；计划书里「延迟链 =
> GBuffer → Lighting → Transparent → Scene2D」的全链路由此扩展为：

```
延迟：ShadowMap ──→ GBuffer ──→ Lighting ──→ Transparent ──→ Scene2D → UIPass
      仅深度       MRT+深度    全屏光照（含阴影采样）
      深度写入      深度 eClear   读阴影深度做比较
```

---

## 1. 目标与范围

在场景有方向光且延迟渲染开启时，让**不透明/裁剪（Opaque/Mask）几何在方向光上投出
阴影**：

- 新增一张由方向光视角渲染的**深度图（Shadow Map）**，pass 插在 GBuffer 之前；
- Lighting pass 的 PBR 与 Blinn-Phong 方向光分支都做**阴影遮蔽**；
- 阴影只影响方向光直接光照项，不影响点光源 / 环境光 / 自发光；
- MASK 裁剪材质在阴影 pass 里同样裁剪（否则树叶镂空会投出实心方块影）。

**阶段 1 不做**：CSM/PSSM、PCF 之外的软阴影方案、阴影贴图立方体贴图（点光源阴影）、
点光源/聚光灯阴影、自阴影开启的蒙皮动画阴影的 LOD/距离裁剪、PCSS。渲染目标/视口
Recreation 时阴影深度图随池 LRU 复用即可。

接入面尽量收敛：**不动 RenderGraph 图本体**（深度独享附件语义已具备，见 §4），
改动集中在 Scene 采集点、Renderer3D 的三个 Flush 与 Lighting shader。

## 2. 现状梳理：一帧里的光照数据从哪来

要实现阴影，必须先知道「当前方向光朝哪照、光照方程在哪一行应用」。现状：

- **方向光参数在 `Renderer3D::m_LightParams`**（`LightParams.dirLightDirection` 指向
  光源方向、`dirLightColor`），由 `Scene::UpdateLightParams()` 每帧从第一个
  `DirectionalLightComponent` 实体采集（`Scene.cpp:683-741`）。
  方向光实体 = `TransformComponent` + `DirectionalLightComponent`。
  `dirLightDirection = normalize(-lightDir)`，其中 `lightDir` 是实体前向（旋转后的
  -Z）。**方向光的方向（从表面指向光源）因此可直接用于搭阴影相机的朝向。**
- **延迟下光照方程在 `assets/shaders/glsl/deferred_lighting.frag`**：方向光 PBR 分支
  `calcDirectionalLightPBR`（:101）、Blinn 分支 `calcDirectionalLightBlinn`（:117）。
  阴影遮蔽就加在这两处（乘一个 visibility 因子）。
- **阴影 pass 需要的可见几何**与 GBuffer pass 是同一批：都渲染不透明段
  （Opaque + Mask），且都要**蒙皮变形**（`mesh_skinned.vert`）。批次已在
  `FlushGBuffer` 里切成 `m_OpaqueBatches`（`Renderer3D.cpp:568-590`）。阴影 pass 要
  么复用这套批次，要么在最前面共享一次排序/切分。
- **几何 draw 与渲染目标耦合**：批次录制在 `FlushGBuffer` 期，先从 `m_Meshes` 消费；
  GBuffer pass 打开动态渲染时用 `ctx` 提供的附件格式与 `SetViewport` 尺寸。阴影 pass
  的渲染目标尺寸 ≠ 视口尺寸，必须在 Flush 内显式设视口/剪刀。

**接入顺序的推演**：阴影 pass 要画的批次和 GBuffer pass 相同，且 Lighting pass 要读
阴影深度。把阴影 pass 插在 GBuffer **之前**，则 `m_Meshes`（帧内 EndScene 采集、延迟
三条 pass 共享、在 FlushTransparent 尾部才清空）仍在，可直接复用「排序 → 切不透明
段」的结果，只多画一次深度。这正是《延迟渲染实现计划书》§10 预定的插入位置。

## 3. 核心思路：从「光源视角」记录深度，再从「相机视角」比较

### 3.1 原理（一句话版）

用方向光作为「第二台相机」摆一个正交投影：从光的方向看向场景，把深度（到光的
距离）写进一张图。之后 Lighting pass 里，每个片元把自身世界坐标投到这张图上，比较
「我记录的深度」vs「图里最近挡光面的深度」——若我更深，说明有物体挡在光和我之间，
该片元收不到直接光。

### 3.2 方向光的「正交投影」为什么成立

方向光是平行光：光线的方向处处相同，没有起点。因此从光的角度看，遮挡关系与距离无关
（只与光方向的先后有关），用**正交投影**即可——投影后的远近就是「沿光方向离光源的
远近」，与相机无关。这与点光源（用透视投影、立方体贴图 6 面）不同。

方向光阴影的关键参数就两个：

- **朝向**：光的视线 = 从目标看向「光源方向的反方向」。已有
  `dirLightDirection`（表面→光源），故光视矩阵 `view` 的 -Z（GLM 相机惯例）要对准
  `-dirLightDirection`（即光线行进方向）。
- **覆盖范围**：正交视锥在光空间包住「相机视锥可见的那部分世界」，即所谓的
  **Light Space AABB**（后文 §6.3 详述）。范围太小 → 阴影裁切（应看到阴影的区域
  没有采样数据）；范围太大 → 深度精度摊薄、阴影抖动/锯齿。方向光阴影的成败几乎全在
  这一步的取舍。

### 3.3 为什么插在 GBuffer 之前：避免 Light Space AABB 依赖 GBuffer 深度重建

方向光阴影要把「可见世界范围」收进一张正射图里。业界（如 Doom 3、诸多延迟实现）有
「先画 GBuffer → 重建相机深度 → 取近裁剪深度框定光空间范围」的做法——能精确贴合
可见表面。但这把阴影 pass 推到了 GBuffer **之后**，且需要额外的深度重建步骤。

本引擎用更简单的前置方案（插在 GBuffer 之前）：

- 用**相机视锥 8 角点**在世界空间框定范围（无需先画任何东西，纯数学：`view-proj`
  逆变换角点 → 转光空间 → 取 AABB），见 §6.3；
- 阴影 pass 和 GBuffer pass 共享同帧批次，先画深度不增加批次消费复杂度（`m_Meshes`
  还没被消费）。

取舍：视锥包出的范围可能略大于实际可见表面（如空旷天空区域），代价是阴影贴图分辨率
利用率略降；换来的是**不依赖 GBuffer、不需要第二次几何重建**，链路简单直接。范围
过大的精度问题由 §6.3 的近远裁剪与后续 CSM 收敛。

### 3.4 采样时的深度比较：投影坐标 → 阴影图 UV/深度

Lighting 片元拿到了世界坐标 `worldPos`（G2 已存），把 `worldPos` 乘光空间
`lightViewProj`（就是阴影 pass 用来算 `gl_Position` 的**同一个矩阵**）：

```glsl
vec4 shadowCoord = lighting.lightViewProj * vec4(worldPos, 1.0);
vec3 proj = shadowCoord.xyz / shadowCoord.w;      // 正交投影 w==1，除不除皆可
vec2 uv  = proj.xy * 0.5 + 0.5;                   // NDC [-1,1] → 纹理坐标 [0,1]
float fragDepth = proj.z * 0.5 + 0.5;             // NDC z → 深度 [0,1]
```

> **为什么不需要手动翻转 V 轴**：阴影深度图「写入」时用 `gl_Position =
> lightViewProj * worldPos`，「读取」时用同一矩阵把 `worldPos` 投影成 UV —— 写与读
> 走同一条 NDC → 纹理坐标映射，Vulkan 光栅化把 NDC 行写进 framebuffer 的约定与
> 采样器按 V 取纹理行的约定在往返中抵消，`uv = ndc*0.5+0.5` 恰好指到该片元实际被
> 写入的 texel。这个自洽性只要求**写与读用同一个矩阵**；若将来做 CSM 重投影 /
> 稳定化让「写入用矩阵 A、读取用矩阵 B」，二者必须保持同一剪裁与深度约定，否则需
> 补翻转（届时用 RenderDoc 第一帧核对一次）。

之后 `texture(shadowMap, uv).r` 是**光空间里最近挡光面的深度**，`fragDepth` 是该片元
自己的深度：

```glsl
float vis = (fragDepth <= shadowDepth) ? 1.0 : 0.0;   // 自己更近 → 被照亮
```

再加偏差与 PCF，见 §5.6/§5.7。偏差点在于：**投影落在光视锥之外**（UV 出 [0,1] 或
深度出 [0,1]，即物体超出光的覆盖范围 / 近远裁剪）时应判定为受光（不投射阴影），
而不是当成全黑。

## 4. 前置能力核对：现有渲染图与录制路径能否承载「深度独享 pass」

这一步要确认不用先改框架就能加 pass。逐项核对（都可从现状直接复用）：

| 能力 | 现状 | 对阴影 pass 的意义 |
|---|---|---|
| **无颜色附件的 pass** | `RenderPassDesc` 的 `colorAttachments` 可为空；`VulkanRenderingInfo` 只设 `SetDepthAttachment`，`rinfo.Begin` 照常（`RenderGraph.cpp:547-578`） | 阴影 pass 就是「零颜色 + 一深度」的动态渲染 |
| **深度只写不读** | 已有 `AttachmentDesc.loadOp=eClear, storeOp=eStore` 声明（延迟 GBuffer/Transparent 均在用） | 深度图一帧画完、下一帧前被清 |
| **虚拟资源池分配任意尺寸/格式的深度图** | `CreateVirtualResource` 已按 `desc.extent` 池化分配，且不要求与视口同尺寸（《渲染图虚拟资源池计划书》S1+S2） | 阴影图 2048² 独立于视口，池按 `(desc, usage)` 复用，**无需为阴影建独立管理器** |
| **深度图在之后 pass 被采样** | 资源用法的「读」路径已支持 `ShaderRead`（Lighting 读 G0~G3 即此路径） | `ShadowMap` pass 后由 Lighting `readImages` 声明读，自动插入「深度写 → 采样读」屏障 |
| **同一 pass 内绑定外部 cubemap / 2D** | `BindImage` 按 (set, binding) 直接绑 | Lighting 在现有 set 1 后追加影子深度 binding |
| **录制时显式改视口/剪刀** | `cmd.SetViewport`/`SetScissor` 逐块覆盖（`Renderer3D.cpp:1161-1177` 全屏三角形已在用） | 阴影 pass 视口 = 阴影图尺寸，非视口尺寸 |

真正要动框架的只有一处潜在边界：**收尾布局**。阴影深度图写后要停靠
`eDepthStencilAttachmentOptimal`（给同资源加 `readImages` 时图会自行转
`ShaderReadOnlyOptimal` 并加屏障），**不需要**把深度图长期停在深度附件布局（与视口
深度不同，它下一帧是被 `eClear` 的，不要求跨 pass 保持旧深度）。所以：
`depthAttachment.finalLayout` 保持默认 `eDepthStencilAttachmentOptimal` 即可——它本
帧被后续 Lighting 读时，由「附件写 → ShaderRead」的常规推导把布局转过去（现状已支持，
见《延迟渲染实现计划书》§5.4 同一张表的「G0~G3 转换」行）。**图本体零改动。**

## 5. 详细设计

### 5.1 新数据流

```
Scene::UpdateLightParams()  [改动：方向光采集处同时算阴影相关量]
  └ 方向光实体 → m_LightParams.shadow* 字段（存在与否、正交矩阵、近远、密度）

Renderer3D
  ├ FlushShadow(ctx)  [新：ShadowMap pass execute]
  │   复用 m_OpaqueBatches + 上传的实例 SSBO → 绑定 m_ShadowLayout
  │   → 逐批次绑定材质（只绑纹理 Albedo + 材质 UBO）→ Draw
  ├ FlushGBuffer(ctx)  [不变，仍在 m_Meshes 未清前消费]
  ├ FlushLighting(ctx) [改动：追加绑定阴影深度图 + 上传含 lightViewProj 的 UBO]
  │   └ UploadLightingUBO 一并填充新字段，见 §5.3
SceneLayer::RecordScenePasses  [改动：延迟分支里，GBuffer 前插入 ShadowMap pass 声明]
```

### 5.2 ShadowMap Pass 声明（SceneLayer，插在 GBuffer 之前）

在 `SceneLayer.cpp:198` 的延迟分支内、`CreateVirtualResource(G0..G3)` 之后、
GBuffer pass 声明之前加：

```cpp
// ShadowMap 深度图：虚拟资源，独立尺寸（例 2048²），格式 D32F。
RenderGraphResourceDesc shadowDesc;
shadowDesc.extent = vk::Extent2D{kShadowMapSize, kShadowMapSize};
shadowDesc.samples = vk::SampleCountFlagBits::e1;
shadowDesc.format = vk::Format::eD32Sfloat;
ResourceHandle hShadow = b.CreateVirtualResource(shadowDesc);

RenderPassDesc &shadowPass = b.AddPass("ShadowMap");
shadowPass.renderArea = vk::Rect2D{{0, 0}, shadowDesc.extent};
AttachmentDesc shadowDepth;
shadowDepth.resource = hShadow;
shadowDepth.usage = ResourceUsage::DepthStencilAttachment;
shadowDepth.loadOp = vk::AttachmentLoadOp::eClear;   // 每帧清空重画
shadowDepth.storeOp = vk::AttachmentStoreOp::eStore; // 保留给 Lighting 采样
shadowPass.depthAttachment = shadowDepth;
shadowPass.execute = [](PassExecuteContext &ctx) { Renderer::Get3DRenderer().FlushShadow(ctx); };

// …随后原有的 GBuffer pass 声明不变……
```

> **若场景无方向光或方向光阴影关闭**：整段不声明（图里没有 ShadowMap pass，也没有
> `hShadow` 资源），FlushShadow 永远不被调用；Lighting UBO `shadowParams.z`（阴影
> 开关）置 0，shader 跳过比较，回到现状。方向光存在性是 Scene 侧知道的事实，由
> `UpdateLightParams` 在阴影开关字段里如实反映。

### 5.3 阴影深度图 / 数据落点

| 数据 | 存放 | 说明 |
|---|---|---|
| 阴影深度图（图像+视图） | 虚拟资源池（图内瞬态，帧帧复用） | `hShadow` 经 `readImages` 暴露给 Lighting |
| 光空间矩阵 + 开关 | Renderer3D 成员（每帧 `UpdateLightParams` 后算好） | 随延迟 Lighting UBO 上传 |
| 阴影图尺寸/密度 | Renderer3D 成员（常量或可调） | 传给采样 shader 做像素尺寸 |

**新增 UBO 字段**：在现有延迟 `LightingUBO` 块（C++ `Renderer3D.h:341-353` 的结构体
与其 shader 侧 `deferred_lighting.frag:7-19` 的 `uniform LightingUBO { ... } lighting`
是同一份 std140 布局）的**尾部**追加字段。C++ 结构与 GLSL 块**同步增删**，保持字段
名一致，追加后仍 16B 对齐：

```cpp
glm::mat4  lightViewProj;   ///< 光空间 view-proj（世界 → 光裁剪空间）
glm::vec4  shadowParams;    ///< x = 阴影贴图尺寸（像素），y = 偏差，z = 阴影开关(0/1)，w = PCF 半径
```

把 `lightViewProj` 放进**延迟 Lighting UBO** 而非 FrameUBO：阴影只被 Lighting 消费，
避免动前向路径所有 shader 的 FrameUBO 布局。

`LightingUBO` 的 CPU 端由 `UploadLightingUBO`（`Renderer3D.cpp:904-942`）填充，那里
正好持有 `m_LightParams` 与 `m_CachedLightBuffer`，加这几行即可。

### 5.4 Lighting pass 接线

- `FlushLighting`（`Renderer3D.cpp:605-672`）里，在绑定 G0~G3 之后追加：
  ```cpp
  cmd.BindImage(*shadowImageView, shadowSampler, /*set=*/1, /*binding=*/7);
  ```
  `shadowImageView` 从 `ctx.readImageViews` 取（图已把 `readImages` 顺序映射到
  `PassExecuteContext.readImageViews`）。当前绑定 G0~G3 用的是 `readImageViews[0..3]`
  （`Renderer3D.cpp:638-642`），阴影深度图就是 `readImageViews[4]`（需先把
  SceneLayer 的 Lighting pass `readImages` 声明**追加**上 `hShadow`）。
- `deferred_lighting.frag` set 1 追加 `binding = 7` 的 `sampler2D samplerShadowDepth`；
  Lighting UBO 块内追加 `lightViewProj` + `shadowParams`（与 C++ 结构体同步，§5.3）。
  阴影开关优先用 `shadowParams.z`（flags 已语义化给天空盒/IBL，不复用）。

### 5.5 FlushShadow：录制阴影深度

阴影 pass 的 `execute` 回调里做：

1. **不做附件格式推断**（无颜色附件），直接 `ConfigureShadowPipeline` 设置：
   - `ps.setRenderingFormats({}, depthFormat)`（深度格式 = 阴影图格式 D32F）；
   - 视口/剪刀 = 阴影图尺寸（`ctx.renderArea.extent`）；
   - 深度测试/写入开、比较 `eLess`；**Cull 沿用材质 doubleSided 动态值**（复用现有
     `DrawMeshInstances` 的 per-batch 逻辑）;
   - 顶点输入用蒙皮/静态对应顶点着色器反射，与现有逐批次切换一致。
2. **画不透明段**：`DrawMeshInstances(cmd, frame, m_OpaqueBatches, m_CachedInstanceBuffer,
   /*gbuffer=*/false)` 但走**专用阴影管线路由**。由于阴影 pass 不写颜色、只用材质
   Albedo 纹理与 alphaCutoff，需要一个精简绑定集：
   - 复用 `DrawMeshInstances` 的管线路由骨架，但片元着色器换成**阴影专用变体**
     `depth_only.frag`（只采样 Albedo + discard），顶点着色器仍复用 `mesh.vert` /
     `mesh_skinned.vert`——顶点级输出是超集，多出的 varying 在只有深度输出的管线里
     不影响编译（`mesh.vert` 的输出 varyings 多于 depth_only.frag 输入，合法）。
   - 蒙皮批次照常绑 Joint SSBO（`SetSkinJointBuffer` 注册的同帧缓冲），保证动画角色
     的阴影跟随骨骼。
3. **空批次/空场景**：若 `m_OpaqueBatches` 为空（全透明场景、场景无 3D），不画任何
   东西，但**深度图仍被 pass 声明的 eClear 清干净**——Lighting 读到全 1.0 深度，
   所有片元都判为受光，效果等同无阴影。无需特判。

**关键点**：`FlushShadow` 必须**共享 FlushGBuffer 已经算好的批次与已上传缓冲**，不能
各自重新 `SortMeshes`/`CollectBatches`。实现上让 `FlushGBuffer` 的批次切分逻辑提前到
一个公共入口（见 §7），或让 `FlushShadow` 在 `m_HasDeferredBatches == false` 时先做
一次和 `FlushGBuffer` 相同的「排序 + 切分 + 上传」缓存（幂等：第二次调用直接复用
缓存）。推荐后者的公共入口方案（S3 详述）。

### 5.6 采样侧：深度偏差与自阴影

把深度图直接比较会立刻出现两种瑕疵：

1. **自阴影（Shadow Acne / 表面自身抖花斑）**：片元自身表面深度 ≈ 阴影图里同一表面
   的深度，由于深度缓冲量化误差与浮点，二者会随机地你比我小、我比你大 → 表面出现
   闪烁的明暗斑点。
2. **Peter Panning（漏光/物体漂浮感）**：为了消除 Acne 加大偏差，物体会显得没接触
   地面。

对策（组合）：

- **常量深度偏差**：比较时 `fragDepth <= shadowDepth + bias`，`bias` 与阴影图分辨率 /
  斜率相关（`shadowParams.y` 可调）。斜率越陡的表面需要的偏差越大——若只做常量偏差
  会「平表面够、陡表面仍闪烁」或反之。缓解：**法线偏移**（在光空间沿表面法线方向把
  `worldPos` 推远一点再投影，`bias` 同时进入光空间投影），业界常用，成本低。
- 采样深度图用**最近邻**（`nearest`）防止把「遮挡深度」插值成软边界（PCF 前不该
  平滑深度值）；或者完全交给后续 PCF/软阴影处理。阶段 1 用 `nearest` + 常量偏差 +
  可选法线偏移。

### 5.7 PCF（阶段 1 简版）——盒式滤波让硬边不闪

单点比较产生逐像素锯齿硬边，随相机移动会闪烁。阶段 1 用**定尺寸 3×3 盒式 PCF**：
把同一片元投到阴影图，在 UV 邻域做 3×3 次深度比较取平均。平均后 0~1 的浮点就是
「半影强度」，直接乘到方向光项上，锯齿被平滑成梯度，消除抖动。

```glsl
float PCFShadow(vec3 worldPos, float bias) {
    vec4 sc = lighting.lightViewProj * vec4(worldPos, 1.0);
    vec3 proj = sc.xyz / sc.w;
    vec2 uv = proj.xy * 0.5 + 0.5;
    float depth = proj.z * 0.5 + 0.5;
    // 出界（超出光覆盖/近远裁剪）= 该片元不在光视锥内，视为受光
    if (uv.x < 0 || uv.x > 1 || uv.y < 0 || uv.y > 1
        || depth < 0 || depth > 1) return 1.0;
    float texel = 1.0 / lighting.shadowParams.x;      // 单像素 UV 宽
    float vis = 0.0;
    for (int x = -1; x <= 1; x++)
    for (int y = -1; y <= 1; y++) {
        float sd = texture(samplerShadowDepth, uv + vec2(x, y) * texel).r;
        vis += (depth <= sd + bias) ? 1.0 : 0.0;      // 逐 tap 硬比较再平均 = 盒式 PCF
    }
    return vis / 9.0;
}
```

> 注意这里**没有** `uv.y = 1.0 - uv.y` —— 写入与读取用同一个 `lightViewProj`，V 轴
> 在往返中抵消（见 §3.4）。PCF 的每个 tap 仍是**硬比较**（深度不可插值），9 个
> 0/1 的平均产生软过渡的 0~1 梯度，这就是盒式滤波的全部原理。

> 完全**不做**的是用「双向线性滤波直接采样深度」——深度值不可线性插值，会把硬边界
> 抹成错误的半遮挡。这也是为什么阶段 1 明确「深度采样最近邻 + PCF 盒式」，而不是把
> 软边交给采样器滤波去平滑。

### 5.8 阴影是否影响「天空像素 / 透明物体」

- **天空像素**：G0.a==0 走天空分支，直接 return，不碰阴影。
- **透明物体**：仍在 Transparent 前向 pass 里画，不接受阴影（半透明物体本身不投、
  也不计算投影；若要「透明天花板投阴影」需另外的深度贡献，超出范围）。透明物体的
  alpha 混合与深度写关的现状不因本计划改变。

### 5.9 前向路径

阴影只接到**延迟链**。前向 Scene3D pass（开关关闭时）保持现状不动，避免给前向
shader 增加绑定与 UBO 负担。将来若要前向也投阴影，是给 FrameUBO 加同样的字段与
采样器的问题，不在本期。

## 6. 正交光空间矩阵与覆盖范围（本计划最值得讲清的一段）

### 6.1 手写光 view / proj 而非用 Camera

`Camera` 类只提供轨道 / FPS / 透视投影，没有「正交、从任意方向盯住一个 AABB」的语义。
阴影相机要「从任意方向正交看场景、且范围随光空间 AABB 动态变」，手算矩阵更直接：

- 光 view：`glm::lookAt(eye, target, up)`。取视线方向沿光传播方向
  `forward = normalize(-dirLightDirection)`；`up` 取与 `forward` 不平行的固定轴
  （如 `abs(forward.y) < 0.99 ? vec3(0,1,0) : vec3(1,0,0)`），由 `forward × up` 推出光
  空间右/上基。**正交投影的深度分辨率只由 zNear/zFar 跨度决定，与 `eye` 放在哪无关**
  ——把 ortho 的近远面设为 §6.3 AABB 的 zMin/zMax 即可，`eye = target - forward * d`
  取固定 `d`（把场景中心摆进 near/far 内）只是方便 GLM lookAt 组装，深度结果与 `d`
  无关。
- 光 proj：`glm::ortho(left, right, bottom, top, zNear, zFar)`，把 Light Space AABB
  正好框住（`zNear/zFar` 即该 AABB 在光空间深度轴的 min/max）。

### 6.2 语义对齐：dirLightDirection 到底是哪边

- `m_LightParams.dirLightDirection` 是**光传播方向（光源→被照物）**（`Scene.cpp:705`：
  `normalize(-lightDir)`；`lightDir` 是实体前向 = 旋转后的 -Z = **朝光源方向**）。
- 光 lookAt 的视线方向（GLM 相机惯例取 -Z）要对准**朝光源方向**
  `forward = normalize(-dirLightDirection)`：光从 `+forward` 一侧（光源所在侧）照来，
  沿 `-forward` 射向场景。
- 光照 shader 里 `L = normalize(-dirLightDirection)` = 物体朝光的方向，与光传播方向
  **相反**。也就是说：光 view 的 -Z 指向 `forward`，片元投进光空间后「离 eye 越近」
  = 沿 `forward` 越靠前 = 离光源越近，深度比较语义正确（§3.4）。阴影投影与光照用
  同一套方向约定，保证「片元投到光空间」与「光实际怎么照」一致。

### 6.3 Light Space AABB：用相机视锥角点（不依赖 GBuffer）

算法（纯 CPU，每帧更新方向光参数后执行）：

1. 取当前相机 `viewProjection = projection * view`（`SceneLayer::OnUpdate` 已有
   `view`/`projection`）。
2. 逆变换视锥 8 角点：NDC 立方体 8 个角点经 `inverse(viewProj)` 变到世界空间。
3. 对这 8 个世界角点，用光 view（§6.1）转到光空间，取 X/Y/Z 的 min/max → 光空间
   AABB。
4. 为阴影深度留出余量：把 AABB 的 Z 范围沿光方向两端各放宽一点（如
   `zMin -= (zMax - zMin) * 0.05`、`zMax += (zMax - zMin) * 0.05`），避免近平面恰好
   切到遮挡物 / 可见表面顶到远平面被裁。这个 AABB 的中心给 lookAt 当 target、
   AABB 尺寸直接喂 `glm::ortho`（§6.1）。

> **为什么不把 AABB 做成「场景全部物体 AABB」**：场景里可能有大片远离相机的物体，
> 全场景 AABB 会浪费分辨率；用相机视锥角点天然只覆盖「当前看到的区域」。代价是——
> 相机转身时 AABB 变化，阴影贴图每帧重投影，属正常（方向光阴影本就要逐帧更新）。

### 6.4 分辨率与密度

一张 `kShadowMapSize`（阶段 1 取 2048，低端可 1024）的深度图覆盖相机视锥的横截面。
**密度 = 场景单位长度 / 图分辨率**：视锥越宽、分辨率越低，每像素对应的世界尺寸越大
→ 阴影越「糊」（锯齿被放大 + PCF 采样覆盖更多世界面积）。密度可直接由
`fragDepth` 到 `uv` 的梯度换算成 texel 世界尺寸，用于把偏差/PCF 半径按密度缩放——
阶段 1 简化为常数偏差 + 固定 3×3 PCF，可调参数暴露，不自动缩放。

## 8. 风险与注意（先想清楚再动手）

1. **深度精度**：D32F + 正交视锥拉得很远时，远近两端精度仍均匀（浮点），但视锥若
   覆盖过远会摊薄每像素密度。补救：范围贴着 §6.3 的 AABB（收紧 zMin/zMax），或
   Depth Bounds / 反向 Z。阶段 1 用 AABB 紧包 + 手动近远即可。
2. **UV 坐标方向自洽性**：阴影深度图写入与采样用同一个 `lightViewProj`，V 轴翻转在
   往返中抵消（§3.4），**不需要**手动 `uv.y = 1.0 - uv.y`。但若将来写/读用了不同矩阵
   （CSM 重投影、texel 稳定化改变了裁剪约定），翻转必须重新核对——届时用 RenderDoc
   第一帧查「阴影整体是否上下颠倒」。
3. **Light Space AABB 的「相机抖」**：相机轨道移动时 8 角点 AABB 每帧变，阴影贴图
   内容随之逐帧重投影——正常。想消除「阴影边缘缓慢爬动」的视觉噪声需要稳定化
   （把 AABB 对齐到 texel 网格），阶段 1 不做，记录为已知。
4. **常偏差对陡峭表面的局限**：表面与光接近平行时（掠射），投影后深度差随像素剧烈
   变化，常偏差不够 → 仍会 Acne。阶段 1 接受，调参窗口留够即可；后续可上「斜率缩放
   偏差 + 法线偏移」或 CSM 每级独立偏差。
5. **透明度 / alphaCutoff 在阴影 pass 的语义**：只对 Mask 材质做 `discard`
   （采样 Albedo 的 alpha），Opaque 材质 alpha 直接忽略（无需采样）。Blend 材质整批
   跳过（不在 m_OpaqueBatches）。若材质把「全透明镂空」放 Blend 里做，阴影会画成实心
   ——这是 Blend 与 Mask 语义边界问题，非本计划引入。
6. **阴影深度图不参与「透明深度测试链」**：阴影图只在 Lighting 被采样；透明 pass 仍
   用视口深度图做遮挡。不要把阴影深度误接进透明 pass 的深度附件。
7. **性能**：阴影 pass 多画一次全场景不透明几何（含蒙皮顶点变换 ×2）。阶段 1 不做
   Shadow LOD / 距离裁剪；中等场景可接受，超大场景的优化放后续（CSM 本身会带
   裁剪策略）。
8. **`m_HasDeferredBatches` 幂等缓存**：FlushShadow 在 GBuffer 前执行，必须先「算批次
   + 上传」，GBuffer 复用缓存。切忌 FlushGBuffer 里重排 `m_Meshes` 造成与阴影 pass
   取到的批次不一致（蒙皮关节矩阵是同一份缓冲，无冲突）。

## 9. 后续阶段（本计划书不做）

- **CSM / PSSM**：一套深度图在相机近/中/远分段各自投影，解决大场景近处密度不足与
  远景裁剪；同时引入「阴影相机 + 稳定化」；
- **软阴影增强**：PCSS（百分比近邻软阴影，按遮挡物距离动态扩大 PCF 核）、VSM/ESM
  或 Moment Shadow Mapping（消除 Acne 需要的偏差、可带滤波深度）；
- **点光源 / 聚光灯阴影**：立方体贴图 + 6 面或双抛物面深度（需图支持立体视图或
  geometry shader 路径）；
- **前向路径阴影**：FrameUBO 追加同一套字段 + 采样器，供前向单 pass 也投阴影；
- **阴影预算 / 相机剔除整合**：阴影 pass 复用相机视锥剔除结果 + 按光 AABB 二次剔除，
  避免重复 draw 不可见物体。
