# 渲染图虚拟资源池计划书

> 为延迟渲染（以及后续 SSAO / HDR / shadow map 等瞬态目标）补上 RenderGraph
> 的"帧内虚拟资源真实分配"能力。本文是《延迟渲染实现计划书》§4.1 的替代方案：
> 虚拟资源池落地后，GBuffer 走图内虚拟资源，不再用 GBuffer 管理器持久纹理。

---

## 1. 背景与目标

当前 `RenderGraph::CreateVirtualResource` 只登记描述、不分配 GPU 内存：
执行期对非 external 资源全部跳过（屏障 `RenderGraph.cpp:313-317`、附件组装
`RenderGraph.cpp:405-410/423-433`、帧末布局写回 `RenderGraph.cpp:510-519`）。
凡"帧内瞬态图像"（GBuffer、将来的 SSAO 深度/法线、HDR 中间目标）都只能走
图外持久的 GBuffer 管理器模式，渲染图对这些资源一无所知。

本计划目标：**让虚拟资源成为渲染图的一等公民** —— 按描述惰性分配、跨帧复用、
布局记忆自动维护、随图析构释放。范围严格限定（见 §3.5）：

- 仅 **Image** 类型（v1 图本就只有 Image）；
- **空闲复用池**（free-list），**不做帧内别名 / 内存子分配 / 复用**。

## 3. 设计决策

### 3.1 池模型：空闲复用池（free-list），按描述复用

每帧 `Reset()` 清空资源表、`CreateVirtualResource` 被 OnUpdate 逐帧重新调用，
**句柄是帧局部的**，因此池不能按句柄复用，必须按描述（format/extent/samples）匹配：

- 池维护一组 `PooledImage`（含 desc + 忙碌标记 + VulkanImage + View）；
- 请求时取**一个匹配 desc 的空闲条目**标忙，无则新建；
- 帧末 `Reset()` 把所有条目标记回空闲（**不销毁**）；
- **同一描述在一帧内多个句柄 → 各自独立图像**：同帧两张 RGBA16F 附件
  （如未来 GBuffer 两个同格式槽）不会共享同一张图。

> 弃选：每帧全新分配/释放（灾难）；按 desc 去重共享（同帧 MRT 两个同格式
> 附件指向同一张图 = 校验错误/互相覆盖）。

### 3.2 布局记忆：与 external 统一

分配出的虚拟 `VulkanImage` 与 external 一视同仁：

- 帧首布局起点 = `VulkanImage::get_layout()`（跨帧记忆）；
- 屏障推进、帧末布局写回（`RenderGraph.cpp:510-519` 的循环）把虚拟资源也纳入
  写回 —— 池条目跨帧存活，上一帧写回的布局对下一帧精确有效；
- 某帧未使用的池条目：该帧不触碰其 layout，下帧直接用存储值，天然正确。

> 执行期判据从 `rec.external != nullptr` 改为"**已有可用的 VulkanImageView**"
> （external 或池分配二者其一），三处跳过分支统一替换。

### 3.3 设备入口与分配时机

- **device 入口**：图新增 `SetDevice(VulkanDevice *)`（在首次 `Compile/Execute`
  之前注入，Engine 构造 Renderer 时完成）—— 比从 Execute 的 frame 临时拿更稳。
- **分配时机**：`Execute()` 开头新增 `ResolveVirtualResources(frame)`：
  按本帧 pass 声明把用到的虚拟资源全部解析到池图像并记入资源表，再进入
  逐 pass 屏障/录制循环。`Compile()` 不分配（无 device 且 extent 声明期才定）。

### 3.4 用法标志：从 pass 声明推导

`RenderGraphResourceDesc` 目前没有 usage 字段。分配虚拟图所需 usage = 本帧
所有 pass 对它的访问并集，由 `ResolveVirtualResources` 扫描 `m_Passes` 推导：

- 出现在 `colorAttachments` → `COLOR_ATTACHMENT`；
- 出现在 `depthAttachment` → `DEPTH_STENCIL_ATTACHMENT`；
- 出现在 `readImages` → `SAMPLED`。

GBuffer 三图 → `COLOR_ATTACHMENT | SAMPLED`；深度（未来被采样）→
`DEPTH_STENCIL_ATTACHMENT | SAMPLED`。推导失败（无任何 pass 使用）→ 告警 + 跳过。

### 3.5 范围界定（明确不做）

- 不做 Buffer 类型虚拟资源（compute/transfer 仍属渲染图阶段 2）；
- 不做帧内别名 / VMA 子分配 / 内存复用（收益在当前单视口、无多视图下趋零，
  复杂度却集中在生命周期）；
- 不做虚拟资源与 external 的自动等价/去重（各自独立）；
- 不做"资源池上限/淘汰"（池只增不减，单场景几个到几十个条目，无害）。

## 4. 接口与数据结构

```cpp
// RenderGraph 私有（跨 Reset 存活）
struct PooledImage {
    RenderGraphResourceDesc desc;      // 匹配键（format/extent/samples）
    VulkanImagePtr           image;    // VMA RAII
    std::unique_ptr<VulkanImageView> view;  // 供 MRT / 采样
    bool busy = false;                 // 本帧已被某个句柄占用
};

std::vector<PooledImage> m_VirtualPool;
VulkanDevice *m_Device = nullptr;      // SetDevice 注入
```

```cpp
// 公开接口
void SetDevice(VulkanDevice *device);           // Renderer 构造时调用
void Shutdown();                                 // 释放池（Renderer 析构体显式调用）

// 既有接口语义变化
ResourceHandle CreateVirtualResource(const RenderGraphResourceDesc &desc);
// 仍只登记描述；真实分配延后到 Execute 的 ResolveVirtualResources。
```

`ResourceRecord` 增加：

```cpp
VulkanImageView *pooledView = nullptr;   // 本帧解析出的池视图（external 路径为 null）
// 存在性判据：external != nullptr || pooledView != nullptr
```

## 5. 执行期接线改动（逐处）

1. **`Execute()` 开头**：在布局状态初始化（`:266-276`）之后插入
   `ResolveVirtualResources(frame)`：
   - 遍历资源表，对每条虚拟资源：查池取匹配 desc 的空闲条目标忙
     （无则 `VulkanImageBuilder(extent).with_format(...).with_usage(...).build_unique(device)`
     新建，命名走资源名或 "virtual"）；
   - 把 `pooledView` 填入 `ResourceRecord`；
   - 布局表对虚拟资源与 external 同法播种 `image->get_layout()`；
2. **屏障生成（`:313-317`）**：跳过条件改为 `!rec.external && !rec.pooledView`；
3. **附件组装（`:405-410`、`:423-433`）**：同上，`rec.pooledView` 与 external 同等
   参与 rinfo 与 `firstColorView/depthView` 透传；
4. **帧末布局写回（`:510-519`）**：循环纳入 `rec.pooledView`（`isFrameSwapchain`
   判定仍只对 WSI 图）；
5. **`Reset()`（`:221-225`）**：清表 + `m_VirtualPool` 全部 `busy=false`（不销毁）。

`PassExecuteContext::colorAttachmentViews`（延迟计划 §4.2）对虚拟附件同样生效，
无需区分来源。

---

## 6. 生命周期与析构顺序（重点坑）

图是 `Renderer` 值成员（`Renderer.h:204`），成员销毁在析构体**之后**，晚于
`m_VulkanContext.reset()`（`Renderer.cpp:82`）—— 若池图像随成员销毁，会
在 device/VMA 销毁后释放 = 悬垂。

**对策**：`Renderer::~Renderer` 在 `m_VulkanContext.reset()` 之前显式调用
`m_FrameGraph.Shutdown()` 释放池（`Renderer.cpp:82` 前插入）。池图像经 VMA
RAII 释放，需 device 仍存活。

resize 重建：池按描述匹配，extent 变化自然产生新条目，旧条目留在池内
（跨帧不再被匹配、可被将来复用），无需显式销毁逻辑 —— 池只增不减策略下
自动正确。

## 7. 与延迟渲染的关系

- 本计划**替代**《延迟渲染实现计划书》§4.1 的 GBuffer 管理器方案：GBuffer 三张
  图（G0~G3）改为 `CreateVirtualResource` 声明 + Lighting pass `readImages`
  采样，深度仍复用视口外部深度图；
- 好处：GBuffer 从"图外的特例"变成"图内瞬态资源"，SSAO / HDR / shadow 落点时
  零新机制；
- 《延迟渲染实现计划书》§4.1 决策段同步更新为本方案（见 §10）。

## 8. 实施步骤（每步可独立构建验证）

**S1 池骨架（无行为变化）**
`SetDevice` / `Shutdown` / `m_VirtualPool` / `Reset` 标闲。验收：前向渲染零变化，
验证层零报错；`Shutdown` 走通且无 device 销毁顺序告警。

**S2 接线**
`ResolveVirtualResources` + 三处跳过分支替换 + 布局播种与写回纳入虚拟资源。
验收：既有 external 路径（视口颜色/深度、swapchain）行为不变；
新增一个临时虚拟 GBuffer 附件（仅登记不接线 pass）验证分配/复用/写回，
RenderDoc 可见该图。

**S3 GBuffer 迁入（配合延迟渲染 S2/S3）**
`延迟渲染实现计划书` 的 GBuffer 三图改虚拟资源声明，SceneLayer 去掉 GBuffer
管理器相关 Import，改由虚拟句柄 + `readImages`。验收：RenderDoc 确认三图内容
正确；断点/日志确认跨帧命中池（第二帧起不新建）；resize 后新 extent 条目出现。

**S4 收尾（可选）**
虚拟资源 debug name 落到 `VulkanImageBuilder`（命名 "virtual/GBuffer0" 等）；
未被任何 pass 使用的虚拟资源告警（Resolve 时未推导到 usage）；池条目数打点进
RenderStatsPanel。

## 9. 风险与边界

1. **同帧同 desc 多句柄**：空闲复用池天然隔离（各取各的图），不会同帧共享 ——
   这是选 free-list 而非 desc 去重的根本原因；
2. **跨帧布局记忆**：依赖"池条目不跨角色复用 + 帧末写回 + 未用帧不触碰"三条
   约定；若将来允许池条目角色漂移，需在换角色时以 `eUndefined` 作 oldLayout
   丢弃内容（附件均 eClear 时无感知）；
3. **虚拟资源被读但从未写**（如 Lighting 读了一个未写的 GBuffer 槽）：内容未定义，
   靠声明纪律 + S4 的"未被写"可选告警兜底；
4. **池只增不减**：resize 抖动会产生孤儿条目，量级小（数条/每尺寸），可接受；
5. **`SetDevice` 必须在首次 Execute 前**：漏设时 Resolve 直接断言，避免隐式错误。
